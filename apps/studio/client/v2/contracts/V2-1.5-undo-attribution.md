# V2-1.5 — Unified undo and AI attribution

Spike: V2-1.5 (Phase 1). Builds in: S5 (AI chat), S2 (Editing), S1 / V2-1.9 (Version history), the hub
kernel extension shipped ahead of any rc (V2-2.18). Status: proposed, for the lead to merge and record as a
DDR. Depends on V2-1.4 (element ids) for element-scoped entries.

## 1. Question

> One op log for user + AI; one AI run = one step; per-user stacks; Undo history; map ACP edits to
> artboard ids (rings, queue, Made by AI).

It must reconcile three statements that BREAKER flagged:
- CONTRACT §2 "⌘Z / ⇧⌘Z — Undo / Redo (includes changes made by AI)";
- per-user stacks: 14 `ed-edge-undo` "Tereza's changes are hers to undo", 03 `ai-history` "Tereza's changes are never in your ⌘Z";
- "one AI run = one version" (A13, 03 `ai-history` "Every AI change is a version you can compare and restore").

The plan's starting point: one AI run = one version via the held AI stage; artboard attribution by
`DCArtboard id=` line ranges; no merge of AI writes into the client undo stack; "AI works here" via
`collab/ai-activity.ts` + `artboard-activity-overlay.tsx`. Constraints: Gate 0 A4, A5, A8, A10, A13, C5,
C17, C27, C30. Deliverables: the op-log model, the interleaving test matrix (you · AI · Tereza,
out-of-order "Undo this chat"), and what the client undo stack does when an AI run lands.

## 2. What exists today

**Two undo systems, chosen by the project's save mode.**

1. **Client stack (DDR-050 rev 2):** `undo-stack.ts` + `use-undo-stack.tsx`, inside the canvas iframe.
   - It is per canvas and session-scoped, kept in `window.top.__maude_undo_stacks`.
   - Records are serializable `CommandRecord`s:
     - `move-artboards`;
     - `annotation-ops`;
     - `edit-source`: a CSS / text / attr edit addressed by **positional** `data-cd-id`, guarded by a `from` precondition (`client/apply-edit-request.ts`);
     - `reorder` and the structural kinds: whole-file `{before, after}` in the server's `reorderLog` (`api.ts` `logUndo` / `reorderRevert`). A swap is refused with 409 when the file changed since.
   - ⌘Z in the shell posts `dgn:'undo'` to the iframe.
   - An external `.meta.json` change clears the stack (DDR-050 rule 6).
   - **AI writes never enter this stack.**
2. **Accepted revisions (DDR-241), synced projects in `transactions` mode only:**
   - The hub kernel (`apps/hub/src/project-transactions/kernel.mjs`) records every accepted change as an **action**: actor, kind, label, `origin {deviceId, sessionId, client}`, and per-lane **effects** with before / after content hashes.
   - `history.undo` (`opUndo`) compensates **one** action, **only the caller's own** (`forbidden` otherwise). It is effect-aware: when a later effect owns the lane, it rebases the revert through every later effect (three-way, ABA-safe), skips conflicting lanes, and refuses with `undo-conflict` when nothing applies. Redo = undo of the undo.
   - Restore is always a new action.
   - Routes: `/_api/project/{history,restore,undo}`, main origin only. A **local project answers `legacy`**: it has no history and no undo for anything outside the client stack.
   - In this mode a reorder's ⌘Z goes through the kernel (`reorderRevert` → `acceptedActionForContent` → `acceptedUndo`).

**The held AI stage (`sync/action-stage.ts`, plan T16).**
- `begin(key, label)` / `end(key, 'done' | 'failed')`: watcher-seen file writes made while an action is open are staged, then published together as **one** action with `kind: 'ai'`.
- On `failed` (error, cancel, token limit, lost heartbeat) the stage is **held** in `_state/ai-stage.json`. It survives a restart, and the person publishes or discards it (`/_api/project/ai-action`).
- A person's edit on a staged file waits behind the stage (`dependents`).
- Callers:
  - the ACP tracker (`acp/index.ts` `createAgentActivityTracker`, key `acp:<chatId>` per turn);
  - `/_api/ai/start|end` (key `edit:<file>`, `/design:edit`).
- It exists only in `transactions` mode (`sync/index.ts` `beginAiAction` returns early otherwise).
- **There is one stage per project.** All concurrent participants publish as one action, by design (`test/sync-action-stage.test.ts` "two participants": `acp:c1` + `edit:ui/a.tsx` → one action).

**Attribution and presence.**
- `activity.ts` `diffArtboardIds`: a regex region diff of `<DCArtboard id="…">…</DCArtboard>` bodies. Any change outside an artboard body returns `null`, and every artboard lights.
- `collab/ai-activity.ts`: per-file AI banners with a 30 s TTL.
- `artboard-activity-overlay.tsx`: the rim and badge, driven by `use-canvas-activity.tsx` `matchesArtboard`.
- Nothing records "Made by AI".

**kg / DDRs (read as data):**
- DDR-050: the command stack and its frozen interface;
- DDR-241: kernel, effects, personal undo, the stage (T16), fencing;
- `decision:maude/v2-…` "maude-v2 co-editing: soft lock per object, one AI run = one undo step (proposed)";
- RCA "undo/redo coverage gaps": three disconnected history mechanisms; a forwarded ⌘Z popped the wrong record;
- I-substrate-audit #6 (missing: out-of-order "Undo this chat", inverse ops rebased over others' ops, a test matrix);
- H-ai-parity N17 / R5 (G-UNDO-1: agent writes do not form a run-scoped step).

**Spec (topic owners).**
- 14 `ed-edge-undo`:
  - "⌘Z steps back through your changes and your AI's, in order."
  - Menu › Edit › Undo history… lists rows, newest first: "Footer — 14 changes, one step · AI · now", "Headline text · You · 1 min ago".
  - Pointing at a row lights what it would undo: "Would undo · 14 changes".
  - The foot reads "Tereza's changes are hers to undo." Then Version history ⌥⌘H.
- 14 `ed-edge-ai`: AI owns only the object it is changing; you keep typing in the headline.
- 14 `ed-edge-ask`: ⌘/ on a selection is one step.
- 03 `ai-history`:
  - Version history filters All · Made by AI · People;
  - an AI row "Make it greener · Post 1:1 · 14:32 · Made by AI" with **Undo this chat** and **Restore**;
  - "Bigger date · Story 9:16 · Tereza's AI".
- 03 `ai-done`: "Undo takes the whole change back".
- 03 `ai-quit`: "Everything AI finished so far is kept as a version".
- 03 "Several AI chats at once": different artboards of one canvas run side by side.

## 3. Options

**Option 1 — the plan's default, taken literally.** One AI run = one version through the held stage; the
client stack never sees AI.
- Fails CONTRACT §2 (⌘Z must step through AI runs).
- Fails 03 "Several AI chats at once": two of your chats on one canvas become one action, and "Undo this chat" can't separate them.
- Fails local projects: they have no stage, no version and no AI undo.

**Option 1′ — the default, refined (recommended).**
- The **op log is the kernel's action log**, for every project. A synced project uses the hub kernel; a local project runs the same kernel in-process.
- **⌘Z is a per-person projection of that log**: your own actions on this canvas, made this session, with each of your AI runs as **one entry pointing at one action**. This is the default's "no merge of AI writes", kept: the run's N tool writes never enter a stack.
- The stage becomes **one stage per run**.
- The kernel gains **multi-target undo** for "Undo this chat" and "undo to here".
- Attribution moves from the regex to an AST reference closure.
- Cost: hub additive change, per-run stages, local in-process kernel, shell-owned stack.
- Breaks: the DDR-050 iframe stack retires in op-log mode.

**Option 2 — put AI runs into the DDR-050 client stack** (a `ai-run` record holding whole-file before / after).
- Undo is a whole-file swap: it erases a peer's later change or is refused (409). It is not peer-safe.
- It dies on reload, does not exist in Version history, and is not per-person on a shared project.
- Rejected; kept only as the local-project fallback (Q5).

**Option 3 — publish every AI write as it lands, tagged with `runId`; group in the projection.**
- Peers see half-done runs, and a canvas can be accepted against a module the agent has not written yet. This is exactly what T16 prevents.
- It creates many versions per run, and still needs multi-target undo.
- Rejected; it is the fallback if per-run composition (§5.5) proves fragile.

**Option 4 — `Y.UndoManager` per person** (DDR-050 rule 4's forward path).
- In `transactions` mode clients are read-only replicas and the kernel writes accepted content with a server origin (DDR-241 §7). A client-side Yjs undo manager can't own undo.
- Rejected.

**Option 5 — git as the op log** (cell autocommit + revert).
- Non-git local projects have no git, there is no per-person undo, and history is file-grained.
- Rejected.

## 4. Decision (DDR draft)

**Title:** One op log (kernel actions) for every project; ⌘Z is your own actions projected per canvas, an
AI run is one action and one step; per-run AI stages; multi-target undo for "Undo this chat".

**Context.** v2 promises that ⌘Z includes AI, that each person undoes only their own changes, and that an
AI run is one version and one step. Today these live in two systems that never meet: the iframe stack (no
AI, positional ids, whole-file swaps) and the kernel (peer-safe, per-actor, but single-target, synced
projects only). The single project-wide AI stage merges concurrent runs, which A4 and 03 allow on one
canvas.

**Decision.**
1. **The op log is the kernel's action log** (DDR-241 actions + effects).
   - Synced projects use the hub kernel, unchanged.
   - Local projects run the **same** `kernel.mjs` + `store-core.mjs` in the studio process over `bun:sqlite` at `<designRoot>/_state/project-store.sqlite`. This is per machine, and `_state/` is already runtime in all four DDR-115 lists. Acceptance is immediate. The disk stays the working copy. An outside write (git checkout, an editor) is proposed by the watcher as `kind: 'outside'`.
   - **Every** edit that reaches a canvas file, from you or from AI, is an action. Viewport and selection never are (DDR-050 rule 3).
2. **Reconciling the three statements.**
   - Each action has an **actor** (the person) and a **kind**.
   - Your AI's run is an action whose actor is you and whose kind is `ai`. It runs on your Mac with your credentials (A5), and the kernel already records the person as actor.
   - So:
     - **your ⌘Z** = your actions, including your AI's runs;
     - **per-person stacks** = the kernel's existing "undo targets your own actions" rule;
     - **one AI run = one version = one step** = one run publishes one action.
   - Tereza's edits and Tereza's AI are her actor: never in your ⌘Z, and refused if you try.
3. **⌘Z is a projection, owned by the shell.** It holds your actions that touch this canvas and were made since it opened in this app session (DDR-050 rev 2 scope), in **the order you made them**.
   - For a gesture, the order key is the gesture time.
   - For an AI run, the order key is the time the run landed. That is `origin.madeAt`, not the acceptance order: an edit you made during a run is published after the run, behind its stage, but happened before it.
   - ⌘Z sends `history.undo` for the newest entry still done. The kernel rebases the inverse over every later change of anyone's.
   - A fully conflicting entry turns **stale**. It is skipped with one toast naming who changed it since.
   - ⇧⌘Z redoes. A new entry clears redo.
   - The iframe no longer owns a durable stack.
4. **One stage per run.**
   - A run is one prompt turn of one chat (ACP), one terminal Claude prompt (hooks, V2-1.11), or one `/design:edit`.
   - A run's writes are composed **separately from every other run's** on the same file (§5.5) and published as one action: `kind: 'ai'`, `label` = the prompt (shortened), `origin.runId` / `chatId` / `madeAt`.
   - Two of your chats on two artboards of one canvas become two actions.
   - Outcomes:
     - `done` publishes;
     - `stopped` (Stop in the chat, or Quit / close-tab after the dialog, A5) publishes with `partial: true` — 03 `ai-quit`: "what it finished is a version";
     - `failed` (error, token limit, lost heartbeat, crash) **holds** (T16), and the person keeps or discards it.
5. **Multi-target undo.**
   - The kernel's `history.undo` / `history.redo` accept `actionIds[]`: every lane ends up **as if those actions had never happened**, rebased through every other later effect.
   - This gives **Undo this chat** (all your published runs of one chat, from any session) and **undo to here** (Undo history) as **one** new action, one version, one ⌘Z step.
   - Today two undo ops in one proposal re-apply the newer run (proved, §6).
6. **Attribution is AST-based.** `attributeArtboards(file, before, after)` marks:
   - the artboards whose own JSX changed;
   - plus every artboard whose JSX **transitively references** a changed declaration;
   - and falls back to the whole file only for imports or module-level changes.
   It drives live rings, the run's touched set, the Undo history highlight, Version history rows and Made by AI.
7. **Made by AI is derived, never stored.** An artboard shows "Made by AI" while the newest action that changed it is an `ai` action (anyone's AI; Tereza's shows her face). The next person's change to it clears it. There is no new field in any versioned file, so v1 peers are unaffected.
8. **C17 / C5.**
   - ⌫ on an object is an ordinary edit action.
   - Deleting an artboard, canvas, asset or token is a `kind: 'trash'` action (removal + a trash record, S1). ⌘Z restores it in place.
   - Restore and "Undo this chat" are new actions. Both are entries, so ⌘Z takes them back too.

**Consequences.**
- Positive:
  - one history under ⌘Z, Undo history, Version history and "Undo this chat";
  - peer-safe undo everywhere (local too);
  - concurrent runs stay separable;
  - rings name the right artboards (≈ 25 % of artboards lit for an out-of-artboard change, against 100 % today, measured).
- Negative:
  - a local project now keeps a SQLite op log under `_state/`;
  - the hub gains an additive operation shape and keeps three new origin keys. Old hubs drop them today (§6), so "Undo this chat" needs the updated hub (V2-2.18);
  - per-run composition needs a three-way merge per staged write;
  - the DDR-050 iframe stack and `reorderLog` survive only for projects not yet on the op log.
- Amends DDR-050: in op-log mode the stack is a shell-side projection, not an iframe store; rule 6 "external edit clears the stack" is replaced by "an outside write is someone else's action".
- Extends DDR-241: multi-target undo, three origin keys, per-run stages, and local in-process acceptance.

**Rejected:** Options 1 (literal), 2, 3, 4, 5 (§3).

## 5. Contract

### 5.1 Op log record (kernel action — existing fields + additive ones)

```ts
interface ActionRow {               // GET /_api/project/history row (AcceptedHistoryRow), extended
  revision: number;
  actionId: string;                 // 'a_…'
  actor: string;                    // the person (an AI run is its person's)
  mine: boolean;
  kind: 'edit' | 'ai' | 'undo' | 'redo' | 'restore' | 'outside' | 'trash' | 'comment' | string;
  label: string | null;             // words per CONTRACT §3–§4 ("Headline text", the AI prompt)
  committedAt: number;              // acceptance time (hub clock)
  undoes: string[] | null;          // NEW: array (today a single id string; readers accept both)
  canvases: string[];
  origin: {                         // stored by the kernel
    deviceId?: string; sessionId?: string; client?: string;
    runId?: string;                 // NEW  /^[A-Za-z0-9_-]{1,64}$/
    chatId?: string;                // NEW  /^[A-Za-z0-9_-]{1,64}$/
    madeAt?: number;                // NEW  ms, the person's clock: gesture time / run landing time
  };
  partial?: boolean;                // NEW  a stopped run (label gets " — stopped")
}
```

### 5.2 Kernel extension (hub, additive, v1-compatible; ships before any rc — V2-2.18)

- `parseEnvelope` keeps `origin.runId`, `origin.chatId` (pattern above) and `origin.madeAt` (safe integer).
  Today it keeps only `deviceId`, `sessionId` and `client` (§6).
- `history.undo` and `history.redo` take **either** `actionId` (today) **or** `actionIds: string[]`
  (1–50, distinct, every one the caller's own → else `forbidden`).
- **Semantics for `actionIds`:**
  - lanes: for each `(entry, lane)` touched by any target, start from the before-content of the **oldest** target effect on that lane, then rebase it through every later effect on that lane **except the targets' own** (three-way, as `opUndo` does today). A conflict skips that lane (reported in `skipped`);
  - manifest and dir effects: compensated newest first, as today;
  - nothing applies → `undo-conflict`;
  - one action results, `kind: 'undo' | 'redo'`, `undoes: actionIds`.
- `store-core.mjs` gains `run_id` and `chat_id` columns on `actions` (additive migration, indexed), so the
  hub can answer "this person's actions of chat X" without scanning `origin`.
- A v1 studio never sends `actionIds`. A v2 studio against an old hub gets `invalid` back and shows
  "Undo this chat needs the team server to be updated" (Q2).

### 5.4 The projection (your ⌘Z stack)

```ts
interface UndoEntry {
  actionId: string | null;          // null while pending behind an AI stage (§5.5)
  pendingTx?: string;
  who: 'you' | 'ai';                // your gesture, or your AI's run
  label: string;                    // "Footer — 14 changes, one step" for an AI run
  madeAt: number;
  canvas: string;
  artboards: string[];              // §5.7
  elements?: ElementRef[];          // V2-1.4, when the edit addressed objects
  changes?: number;                 // V2-1.9 "what changed" count
  runId?: string; chatId?: string;
  state: 'done' | 'undone' | 'stale';
  undoneBy?: string;
}
```

**Membership.**
- Included: actions with `actor = you` that touch this canvas, made since the canvas opened in this app session, with `kind ∈ {edit, ai, trash, restore}`.
- Also included: `undo` actions this session made through **Undo this chat**, **Undo history** (undo to here) or **Version history**. They are entries, so ⌘Z takes them back.
- An `undo` / `redo` made by ⌘Z / ⇧⌘Z adds no entry: it flips the target's `state`.
- Excluded: `comment` (a message, not an edit), `outside`, other people's actions.
- At most 100 entries; older ones stay in Version history.

**Keys.**
- **⌘Z**:
  1. Take the newest `done` entry by `madeAt` (tie: revision) and `POST undo { actionId }`.
  2. If accepted, mark it `undone`; it goes to redo. When `skipped` is non-empty, toast "Undid <label> — <n> parts were changed by <name> since, kept".
  3. On `undo-conflict`, mark it `stale` and toast "Can't undo <label> — <name> changed it since". The next ⌘Z continues below it.
- **⇧⌘Z**: redo the newest `undone` entry, **only if** no new entry was added after it.
- A new entry, including your AI run landing, clears redo.

**Undo history** (14 `ed-edge-undo`):
- rows are entries, newest first;
- pointing at a row lights `artboards` / `elements` with the tag "Would undo · <changes> changes";
- clicking row *k* sends **one** `POST undo { actionIds: [entries 0..k] }`, one new version;
- the foot reads "<Name>'s changes are theirs to undo." when the canvas has other actors in the session.

**When an AI run lands** (the question's last ask):

| Event | Your stack on that canvas |
| --- | --- |
| Your run lands (`done` / `stopped`) | One new entry: `who: 'ai'`, label = prompt (+ " — stopped"), "N changes, one step", artboards from §5.7. Redo cleared. Same action as the chat result card's **Undo**. |
| Your run fails (held) | Nothing yet. **Keep** publishes it, and it becomes an entry. **Undo** discards it: it was never published, so there is no entry. |
| Your run touches several canvases | It is one entry in each canvas's stack. ⌘Z in any of them undoes the **whole** run (Q1). |
| Tereza's edit or Tereza's AI lands | No entry. Yours stay. A later ⌘Z on an entry she overlapped applies only what is still yours and lists the rest. |
| You edit while your run is open on the same file | An entry at once (pending, `actionId: null`), published right behind the run, ordered by your gesture time. |
| ⌘Z while your run is open | Undoes your newest entry, pending or published. On a pending entry, it proposes the inverse as another pending edit. It **never** touches the running run's staged writes; Stop is in the AI chat. |
| Canvas reload / HMR | The stack survives: it is shell-owned and keyed by canvas. |
| App restart | Empty, by session scope. Version history and "Undo this chat" still reach older runs. |
| Outside write (git, editor, terminal Claude without the studio) | An `outside` action. It is not yours, so it is not an entry; your entries rebase over it. |

### 5.5 Runs and per-run stages (`sync/action-stage.ts` → run stages)

```ts
interface RunStage {
  runId: string; chatId?: string; actor: string;
  label: string;                    // the prompt, ≤ 120 chars
  state: 'open' | 'held';
  since: number; endedAt?: number;
  lanes: Map<string /* slug|lane */, {
    base: string;                   // accepted content when this run first touched the lane
    mine: string;                   // base + this run's deltas ONLY
    writes: number;
  }>;
  touched: Record<string /* canvas */, string[] /* artboards */>;
}
```

- **Write → run.** A staged write belongs to the run whose tool reported writing **that exact content**. For an in-app chat, that is the ACP `tool_call_update` with `status: completed`, path and hash. For terminal Claude, it is the PostToolUse hook `maude act edit.touched --run <id> --file <f> --hash <h>` (V2-1.11). A watcher write that no open run claims is a person's or an outside write, never staged.
- **Composition.** On a write by run R that changes the disk from `d0` to `d1`:
  `R.mine = merge3(base: d0, ours: d1, theirs: R.mine)` (`sync/source-merge.ts`).
  Other runs' `mine` don't change. If the merge fails, R and another open run changed the same characters (shared component code). The PostToolUse check refuses R's write with `run-overlap` (A13 rollback), and the message names the other run and offers "wait" or "Run on a copy".
- **Publish R:** `lane.replace { content: R.mine, baseContent: R.base }` for each lane, all in one proposal, with `kind: 'ai'`, `label`, `origin { runId, chatId, madeAt: endedAt }` and `partial` when stopped. The kernel merges R onto the head, which may already hold other runs or people. Dependents (person edits made on top of staged bytes) go out right behind it, as today.
- **Held stages** persist in `_state/ai-stage.json` as `{ v: 2, runs: RunStage[] }`. A v1 file is read as one held run.
- **Crash:** every open run comes back **held** (never published without the person). The C37 callout lists them with Keep / Undo.

### 5.6 Local projects (no hub)

- The same kernel module and store core run in the studio over `bun:sqlite`: one SQL adapter (`exec`, `transaction`), the shape `store-core.mjs` already takes.
- Acceptance validates with the studio's own `sourceError`. There is no projection: the disk already holds the content.
- `/_api/project/{history,undo,restore,undo-stack}` stop answering `legacy` for local projects.
- Version history for local projects (V2-1.9) reads the same store.
- If the lead or V2-1.9 rejects this, use the fallback in Q5.

### 5.7 Attribution — `attributeArtboards`

```ts
function attributeArtboards(file: string, before: string, after: string): {
  artboards: string[];              // DCArtboard ids
  scope: 'artboards' | 'file';
  reason?: 'imports' | 'module-scope' | 'artboard-set-changed' | 'parse-error';
};
```

- **Parse:** parse both sides (oxc), find each `DCArtboard` element and its id, and each named declaration outside every artboard (top level, or local to the canvas component).
- **Change ranges:** a change inside an artboard's element marks that artboard. A change inside declaration D marks **every artboard whose JSX transitively references D**.
- **Artboard set:** an added, removed or renamed artboard marks that id with `artboard-set-changed`.
- **Whole file:** imports, module-level statements and a parse error give `scope: 'file'`.
- **Never text-match:** the regex matches `<DCArtboard` inside string literals (§6).
- **Uses:**
  - live rings: per staged write, the dashed spark on claimed ∪ touched artboards;
  - the run's `touched` set, which feeds the A4 queue and leases of V2-1.15;
  - `project:action.artboards`, the Undo history highlight, Version history rows, Made by AI.
- **Cache:** results per `actionId` are cached in the index service (V2-1.17) and recomputed from the store's before / after blobs on a miss.
- **"AI works here":** `collab/ai-activity.ts` entries gain `runId` and `artboards`. `artboard-activity-overlay.tsx` keeps rendering, with the artboard set coming from §5.7 instead of `diffArtboardIds`.

## 6. Evidence

Prototypes (not committed), run through `scripts/v2-test-lane.sh`:

**Multi-target undo on today's kernel.**
- Setup: one canvas, chat run 1 `A0→A1`, chat run 2 `B0→B1`, then a manual edit `C0→C1`, all by Alice.
- **One proposal** with `history.undo r2` + `history.undo r1`: accepted (200, `kind: undo`), but the result is
  `A0 · **B1** · C1`. Run 2's change came back, and the stored `undoes` names only `r1`.
  - Cause: the second compensation rebases through the **stored** effects, including run 2's, and overwrites the first compensation made earlier in the same proposal.
- **Two proposals:** `A0 · B0 · C1`, which is correct, but two versions and two steps. This is why `actionIds[]` (§5.2) is needed.

participants publish as one action. That is the behaviour 03 "Several AI chats at once" forbids.

## Decisions

- `decision:maude/v2-V2-1.5-one-op-log`: the kernel's action log is the single op log for every project.
  Local projects run the same kernel in-process over `bun:sqlite` under `_state/`. Rejected: git as the log, a
  second local log, client-only stacks.
- `decision:maude/v2-V2-1.5-undo-is-a-projection`: ⌘Z / ⇧⌘Z / Undo history are a shell-owned
  projection of your own actions per canvas, ordered by `madeAt`. An AI run is one entry, and the kernel does
  peer-safe compensation. This reconciles "⌘Z includes AI", "per-user stacks" and "one AI run = one
  version". Rejected: AI writes in the DDR-050 iframe stack, Y.UndoManager.
- `decision:maude/v2-V2-1.5-per-run-stages`: one held stage per run, composed per run by three-way merge.
  An overlap is refused with `run-overlap`. Stop / Quit publishes partial; error / crash holds. Rejected: the
  single project-wide stage (merges concurrent chats), publishing every AI write live.
- `decision:maude/v2-V2-1.5-multi-target-undo`: kernel `history.undo { actionIds[] }` = "as if these
  never happened", for Undo this chat and undo-to-here as one version, plus `origin.runId`, `chatId` and `madeAt`
  kept by the kernel. Proven needed: two undo ops in one proposal re-apply the newer run. Rejected:
  sequential per-run undos (several versions, partial failure).
- `decision:maude/v2-V2-1.5-ast-artboard-attribution`: artboard attribution by AST reference closure.
  "Made by AI" is derived from the op log, never stored. Rejected: the `diffArtboardIds` regex (lights
  every artboard for 92–94 % of out-of-artboard changes and matched inside a string literal), a versioned
  made-by-AI field.
