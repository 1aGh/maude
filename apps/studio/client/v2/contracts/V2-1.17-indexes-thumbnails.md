## 1. Question

> One index service for Home, ⌘K, usage, kind counts, recent, picture descriptions (A20/B6 budgets): build,
> incremental update, crash-safe staleness, cloud "Shared with you"/"not on this Mac" API; one thumbnail renderer

From the brief: `I-substrate-audit.md` #9 (snapshot files go stale after a crash; describe sidecars have no
classification, budget or rate cap); performance targets from V2-8.14 (a 93-canvas panel, index builds, 93 Home
thumbnails, 247 assets) measured on an unlinked copy of `~/Maude/alligators`; every new runtime path names its DDR-115
classification; the renderer never renders with the untrusted canvas origin's authority.

## 3. Options

| # | Option | Cost | What it breaks |
| --- | --- | --- | --- |
| **1** (plan default, chosen) | **One index module** in each project server: in-memory, updated from fs events, persisted as one snapshot per project in a machine dir that Home reads; **one renderer** = the capture spine in a warm headless Chromium on the project's **canvas** origin | new modules + a long-lived shim | nothing; `/_index-data` keeps its shape and becomes a view of the index |
| 2 | Keep per-request walks; Home walks every project live | none now | 20 projects × 160 ms per Home open; no artboards, no runtime artboards, no pictures, no staleness story |
| 3 | One machine-wide SQLite/FTS index for every project | an FTS engine | N writers + Home on one file (locks, WAL); every profile in one database — an existence oracle between accounts (L14); a linear scan already meets the budget (9 ms over 5,900 rows) |
| 4 | Pictures captured by the user's live canvas iframe (DDR-231 browser lane) and posted to the server | no browser process | the untrusted canvas chooses the bytes for any key; only runs while that canvas is open; costs the user's frame budget |
| 5 | Pictures from WKWebView snapshots of hidden Tauri windows | no Chromium | desktop only (no browser shell, no CLI); objc; an untrusted canvas inside a Tauri window is one capability mistake away from IPC |
| 6 | Pictures from the cloud render service (`apps/render`) | no local engine | network + paid compute per edit; the least-trusted shared worker (DDR-230) |

## 4. Decision (DDR draft)

**Title:** One index service per project, persisted per project in a machine cache; one thumbnail renderer that
captures on the canvas origin with the server's authority.

**Context.** v2 surfaces read the same facts many ways: the Canvases panel at 93 canvases, ⌘K across projects with
artboards, the artboard jump list and kind counts, recents and pins, Home, the Assets tab with usage and "Not used",
the Design system canvas's "Update N canvases", Version history pictures, search inside pictures (B6). Today each
reads the disk on its own (`/_index-data` walks per request) and nothing renders a picture of a canvas. The static
reader misses most artboards: on Alligators, 10 canvases make artboards a parse cannot see — in code (`.map` over
data) or through a local wrapper module (`ui/club-web/_render.tsx`) — so a parse sees **201** of the **667** artboards
that render.

**Decision.**

1. **One module, `apps/studio/index/`** (pure TS, importable by Bun and Node 24): a static extractor (oxc parse →
   canvases, literal artboards, kinds, design system, asset and token references), the runtime-artboard merge (from
   the renderer's harvest), the snapshot (read / write / stamp), the matcher (`match.ts`, the shared `fold()`), and an
   extractor registry so V2-1.6 (design-system usage) and V2-1.5 (attribution cache) plug in instead of walking again.
2. **The project server owns its index**: built at boot (≤ 250 ms on Alligators), updated per fs event (one canvas
   ≈ 6 ms), served on `GET /_api/index` (main origin; filtered by V2-1.16 `sees` in cells) and announced on `/_ws`.
   `/_index-data` keeps its shape (nothing deleted) and is computed from the index.
3. **Persisted per project** in a machine cache `~/.maude/index/v1/projects/<pid>/` (`MAUDE_INDEX_DIR`): `index.json`
   (the cross-project projection Home and ⌘K read), `thumbs/`, `describe/`. Outside every project, so no DDR-115 list
   changes; written only by that project's server (and by the Home server for rebuild-of-closed and GC); cells write
   none.
4. **Crash-safe by fingerprint, not by trust in the writer**: the snapshot carries a stamp over (path, size, mtime) of
   every canvas source and meta; a reader recomputes it (3 ms) and treats any mismatch as stale. Writes are atomic.
5. **One renderer, `apps/studio/thumbs/`**: one long-lived shim per project server drives headless Chromium through
   the existing capture spine, **always on the project's canvas origin** (`?hide-chrome=1`), with keys, targets,
   sizes and storage decided by the server and the returned bytes validated before they are stored. The same renderer
   makes canvas covers, artboard pictures, version pictures (V2-1.9) and asset tiles. Cells render nothing in v2.0.
6. **Picture descriptions (B6)** are opt-in per project per person, made by a read-only describer on this Mac with
   the person's Claude account, budgeted and rate-capped, stored only in the machine cache, never synced, never
   treated as instructions.
7. **The cloud lists** ("Shared with you", "not on this Mac yet") are Home-only and come from `GET /api/home`
   (V2-1.1 §5.7); the index service only derives which cloud projects have a local copy.

**Consequences.**

- `/_index-data` drops from 156 ms to an in-memory read; the Canvases panel, ⌘K, counts and Home share one source.
- Runtime artboards (the 70 % a parse misses) appear once a canvas has been rendered once; until then a canvas with
  code-built artboards is flagged `dynamic` and lists its literal artboards only.
- A Chromium process runs per project server while it has pictures to make (closed after 60 s idle).
- L21 (exports render untrusted code on the main origin) is not fixed here, but the renderer shows the fix's shape:
  the same captures, from the canvas origin, look the same (89 of 94 covers byte-identical, the rest a frame apart)
  and cost the same.

**Rejected alternatives.** Options 2–6 (§3). Also rejected:

- **Thumbnails inside the project (`_cache/`, already a runtime class)** — Syncthing and folder copies would duplicate
  and churn them, and Home would read every project tree.
- **One machine-wide content-addressed store shared by all projects** — dedup across projects is an existence oracle
  between profiles (V2-1.16 L14); per-project storage costs little (33 KB per cover).
- **Static-only artboards** — misses 466 of 667 artboards on the reference project.
- **Rendering on the main origin like exports** — L21.

### 5.5 Update triggers

| Trigger | Work | Budget |
| --- | --- | --- |
| Boot | full static build; read the previous snapshot to reuse runtime artboards and covers whose `srcHash` is unchanged | ≤ 250 ms (Alligators) |
| `fs:any` on a canvas `.tsx` (create / change / delete / move) | re-extract that canvas; mark its pictures dirty; queue its cover | ≤ 20 ms per canvas |
| `.meta.json` change | re-read kind, DS, `artboardMeta`, Present order (cover choice) | ≤ 5 ms |
| A non-canvas module or CSS a canvas imports (`_kit.tsx`, `_layout.css`, tokens/components CSS) | recompute `depsHash` of the canvases that import it (resolved relative specifiers, `canvas-imports.ts` vocabulary); their pictures re-key and re-render lazily | ≤ 30 ms |
| `config.json` reload (`fs:json`) | full rebuild (groups may change) | ≤ 250 ms |
| `assets/` add / remove / change | asset rows; usage rescan | ≤ 15 ms |
| `_canvas-state/_pins.json`, `_recent.json` change | user fields; `changed` event | ≤ 2 ms |
| Renderer harvest | `mergeRuntime` (runtime artboards for that `srcHash`) | ≤ 2 ms |
| Version recorded (kernel action / commit) | asset refs of the new version added to the history-refs cache | ≤ 5 ms |
| Access narrowed or ended (`maude.access`, HTTP 401/403 `access-withdrawn` \| `not-in-scope`) | rebuild **and** delete pictures + descriptions no longer referenced, **before** the access-ended state is emitted (L14) | ≤ 300 ms, synchronous |
| Graceful shutdown | flush the snapshot | ≤ 15 ms |

Snapshot writes: debounced 2 s after the last change, at most one per 10 s under constant churn, always on shutdown.

**History refs (12 › Not used).** An asset referenced by any retained version is used. Per immutable
(canvas, `rev`|`sha`) the asset references of that source are extracted once and cached in
`projects/<pid>/history-refs.json`; a background scan fills it for existing history. Until the scan has finished, "Not
used" shows "Checking older versions…" and lists nothing — a false "used" is safe, a false "not used" is not. V2-1.9
calls `forgetVersion` when it prunes.

### 5.6 Staleness and crash recovery

- **Stamp** = `sha256` over sorted lines `rel \0 size \0 trunc(mtimeMs)` of every canvas `.tsx` and `.meta.json` in
  the canvas groups (and `config.json`), first 32 hex. Recomputing it is a stat walk (3.1 ms on Alligators).
- **Write**: `index.json.tmp-<pid>-<rand>` → fsync → rename. `seq` grows per write within a boot; `bootId` is random
  per boot. Temp files older than 1 h are swept by any reader.
- **Read** (Home, the broker, the server at boot): parse (failure = missing) → recompute the stamp →
  - equal → fresh;
  - different → serve the rows with `stale: true` and rebuild: if the project's server runs (Home passes the running
    pids), wait for its write (≤ 10 s); otherwise the Home server runs the static extractor over the closed project
    (≤ 250 ms) and writes the snapshot itself, keeping runtime artboards and covers for canvases whose `srcHash` did
    not change; a changed canvas falls back to static artboards and keeps its last cover with `ofSrc` ≠ `srcHash`
    (the picture shows the last render until the project opens).
- This covers a crash between an edit and the debounce, edits made while no server ran (terminal Claude Code, git,
  Syncthing, the CLI) and a server that died mid-write.
- A project root that is gone keeps its snapshot; Home shows "isn't where it was" (V2-1.1).
- **Format version** = the directory: `v1/`. A breaking change writes `v2/`; the Home server deletes old version
  directories at boot (a rebuildable cache needs no migration).

**GC** (Home server, at boot and daily; the project server for its own project on access changes):

| What | Rule |
| --- | --- |
| `projects/<pid>/` | the pid is not in the registry and was not opened for 30 days → delete |
| `thumbs/` | a key referenced by neither the snapshot nor the version-picture LRU (`thumbs/_versions.json`, ≤ 2,000 keys) for 7 days → delete |
| `describe/` | a sha no longer among the project's assets for 30 days → delete |
| per project | ≤ 500 MB total, least recently read first |
| access narrowed / ended | immediate, before the card (§5.5) |

### 5.7 The matcher — `apps/studio/index/match.ts`

- `fold(s)` = NFD, strip `\p{M}`, lower-case — the one accent fold every search uses (panel search, ⌘K, marks).
- Query = folded words (split on whitespace); **every word must match** (any order). Row fields: `name` (strong) and
  `meta` (folder, parent canvas for an artboard row, project for a cross-project row).
- Per word: contained in `name` → 3 (+1 when it starts a token); in `meta` → 1; else, for words of ≥ 4 letters, a
  token within one edit (insert, delete, substitute or swap of two neighbours) of the word or of the token's prefix of
  the word's length → 0.5 and the row is `close`. A word that matches nothing drops the row.
- Order: score ↓, then `openedAt` ↓, then name. Marks are returned as ranges mapped back to the unfolded string.
- Rows: canvases, artboards ("artboard in LetakA6 · print"), registry actions (label + `search.keywords`, V2-1.3),
  places, assets (name, tags, and — with consent — the picture's caption, tags and text, weight 1), canvases that use a
  matching picture (weight 0.5, "matches a picture"). Groups and order per 01 `cf-search-k` / 11 `pn-k-across`: this
  project first, other projects by group, "Tools and settings", "Ask AI" last.
- When every row is `close`: "Nothing called "unifromy". Showing close matches for **uniformy**." No rows: CONTRACT
  §4 "Nothing called "pricng". Try another word, or ask AI to find it."
- ≤ 50 rows per group, ≤ 200 in all.

### 5.8 The thumbnail renderer — `apps/studio/thumbs/`

**Interface** (project server; agreed with V2-1.9):

```ts
export interface ThumbRequest {
  canvas: string;                                   // designRoot-relative
  artboard: string | null;                          // null = cover: first artboard in canvas order (C31; Present order if set)
  at?: 'now' | { rev: number } | { sha: string };   // version pictures (V2-1.9)
  size: 'card' | 'row';                             // 480 / 160 px long side, JPEG q80
  priority: 'visible' | 'background';
}
export type ThumbResult =
  | { status: 'ready'; key: string; url: string; w: number; h: number }   // url = /_api/thumb/<key>
  | { status: 'pending'; key: string }                                    // later: /_ws {type:'thumb-ready', key}
  | { status: 'unavailable'; reason: 'no-engine' | 'failed' | 'not-in-scope' | 'no-artboard' };
export function thumb(req: ThumbRequest): Promise<ThumbResult>;
export function assetTile(rel: string, size: 'card' | 'row'): Promise<ThumbResult>;
```

**Key** = `sha256('thumb/1' ‖ size ‖ theme ‖ canvas ‖ (artboard ?? 'cover') ‖ srcHash ‖ metaHash ‖ depsHash)`, full
64 hex (DDR-145 F3), where `srcHash` = the canvas TSX + its CSS lane **at the version**, `metaHash` = its `.meta.json`
at the version, `depsHash` = the **current** resolved relative imports and the design system's tokens/components CSS,
`theme` = the project's `themeDefault`. Consequences: an unchanged artboard across 50 versions is one picture; a kit or
token change re-keys every picture and they re-render lazily ("shared modules render as they are now", as history
builds already do). Asset tiles: `sha256('asset/1' ‖ size ‖ sha256(bytes))`. The key is computable without building.

**Process.** One shim per project server, `bin/_thumbs-playwright.mjs`, started on the first job with
`resolveExportRuntime()` (the bundled Bun, DDR-177) and `launchChromium()` (engine resolution as exports: Playwright's
Chromium, else `_ensure-browser --no-download`); one browser, ≤ 4 pages; NDJSON over stdio:

```
→ {"op":"render","id":17,"url":"<canvasOrigin>/_canvas-shell.html?canvas=…&hide-chrome=1&tokens=…[&sha=r812]",
   "targets":[{"artboard":null,"px":480},{"artboard":"pozvanka-story","px":160}],"hasArtboards":true,"deadlineMs":20000}
← {"id":17,"ok":true,"runtime":{"artboards":[{"id":"…","label":"…","kind":"print","w":2480,"h":3508}]},
   "shots":[{"artboard":"…","w":480,"h":300,"jpeg":"<base64>","partial":false}]}
```

Idle 60 s → the browser closes; the shim dies with the server; while an export job runs the queue pauses.

**Steps per job** (the page decides nothing):

1. Navigate on **`ctx.canvasOrigin` only** (asserted; the main origin is refused — L21). The context aborts every
   request whose origin is not the canvas origin (second leg behind the canvas CSP and `CANVAS_SAFE_API`).
2. Wait for `#canvas-root > *` (≤ 20 s). If the index says `hasArtboards` (the canvas **or a module it imports**
   uses `DCArtboard` / `DesignCanvas` — `ui/club-web/*` has no literal `<DCArtboard>` yet renders 98), wait for
   `[data-dc-screen]` (≤ 10 s) and for the artboard count to hold across two animation frames + 250 ms (code-built
   artboards mount late). Otherwise it is a specimen: one more frame, no blind wait. Fonts ready (≤ 3 s).
3. Harvest `window.__maudeCanvasRects()` artboards → `runtime` (feeds `mergeRuntime`; never trusted for anything but
   names and sizes in this project's own index).
4. Per target: zoom the world to the target size, pin the artboard at (0, 0), hide the others, decode images
   (≤ 3 s); a video comp seeks to its poster time (`.meta.json` `artboardMeta[id].poster`, S7; else frame 0) through
   the comp seek hooks with `strict: false` (≤ 3 s) — on timeout the shot is `partial` and retried once later.
   A specimen (no artboards) is captured from `#canvas-root`, clipped to 16 : 10 from the top.
5. JPEG screenshot of the clip.

**Server-side validation before storing**: JPEG SOI/EOI markers, dimensions ≤ requested + 1, ≤ 1 MB; atomic write to
`projects/<pid>/thumbs/<k0k1>/<key>.jpg`; covers update the snapshot.

**Asset tiles**: raster only (png, jpg, jpeg, gif, webp, avif) through the canvas origin's `/assets/` lane on a blank
capture page; SVG, PDF, PSD, HEIC show their kind glyph (SVG is scriptable, DDR-145; S8's converters turn the others
into pictures first). Video assets: a frame at 0.5 s when `readyState ≥ 2` within 3 s, else the glyph.

**Queue and pacing**: `visible` (keys the client reports on screen) > recently opened canvases > background in
`openedAt` order. Background: one job at a time. Visible: ≤ 4 pages. Historical (`at` ≠ now): ≤ 12 renders per 10 s so
the live DiffView keeps headroom under `serveHistoricalCanvas`'s global limiter (24 / 10 s).

**Failures**: a build error → `unavailable: 'failed'` (the row shows its kind glyph; S11's render-error card is
separate), retried when `srcHash` changes; three failures for one key stop retries until the next change. No engine →
`unavailable: 'no-engine'`, never a silent 94 MB download (§9 Q1).

**Security invariants** (tests in §7):

| # | Invariant |
| --- | --- |
| R1 | Renders only on the project's canvas origin; a canvas that fetches a privileged route during a render gets `403 Forbidden (canvas origin)`. |
| R2 | Keys, targets, sizes and paths come from the server; the page's only output is bytes the server validates. |
| R3 | No IPC, no cookies: a separate Chromium process, a fresh context per project. |
| R4 | Pictures are served only on the main origin (`/_api/thumb`) or the Home server (V2-1.1 §5.3); never on the canvas origin (absent from `CANVAS_SAFE_API` and the canvas routes map). |
| R5 | Raster JPEG only, `Content-Type: image/jpeg`, `X-Content-Type-Options: nosniff`. |
| R6 | Storage per project; served only for keys a snapshot (or a version the caller may see) references; missing and forbidden give the same 404; no route answers "is key X cached" (L14). |
| R7 | Cells render nothing; a cell-side renderer later renders only for sessions that see the canvas (L14). |

### 5.9 Picture descriptions — search inside pictures (B6)

- **Consent**: once per project, per person, on this Mac — `<designRoot>/_canvas-state/_describe.json`
  `{ "v": 1, "on": true, "since": 1760000000000, "dailyCap": 200 }` (existing `_canvas-state/` class). Offered by the
  line "Let AI describe your pictures so search can find what's in them" (CONTRACT §7) in Assets and in an empty
  search; off by default. No AI connected → search falls back to names (CONTRACT §7).
- **Who describes**: the desktop only (A5: no server-side AI). The S12 `asset-describer` agent (V2-1.18, read-only)
  runs headless through the bundled `claude` with the person's account (A2): tools = Read only (no Bash, Web, Write or
  MCP), working directory = an OS temp dir holding only the batch's pictures, downscaled by the renderer to ≤ 1024 px
  JPEG — never a project path. It returns `maude.agent-handoff/1` with `results: [{ sha256, caption, tags, text }]`.
- **Validation**: JSON schema; control characters stripped; `caption` ≤ 140 chars; ≤ 12 tags of ≤ 32 chars
  (`[\p{L}\p{N} -]`, lower-case); `text` (words visible in the picture) ≤ 280 chars; unknown keys and results for a sha
  outside the batch are dropped.
- **Storage** `~/.maude/index/v1/projects/<pid>/describe/<s0s1>/<sha256>.json`:

```json
{ "format": "maude.describe", "v": 1, "sha256": "…64 hex…", "source": "image",
  "caption": "Player in a green number-50 jersey at the start line of the 40-yard dash",
  "tags": ["football", "combine", "jersey"], "text": "10-YD SPLIT 0.00 40-YD DASH 0.00",
  "lang": "en", "model": "claude-…", "at": 1760000000000 }
```

- **Budget and rate**: ≤ 10 pictures per batch; one batch in flight per Mac; ≥ 20 s between batches; ≤ `dailyCap`
  (default 200) pictures per project per day (`describe/_usage.json {day, count}`); each picture ≤ 1024 px and
  ≤ 400 KB; raster images and video posters only. Pauses when offline, when the account is "used up until HH:MM", or
  when AI is disconnected; resumes by itself. Progress in Assets › Advanced: "Describing 12 of 193 pictures" with
  **Stop**.
- **Never**: synced, versioned, sent to the hub, exported, or given to a model as instructions. When search results
  with captions reach an AI chat they are quoted as untrusted data (the DDR-130 guard wording).
- **AI path**: the consent toggle is human-only (§9 Q9); re-describing is `maude design describe [--asset <rel>]
  [--dry-run]` (effect `external` → the permission card, V2-1.11).
