# V2-1.7 — Hub roles + per-canvas ACL (Gate 0 A6, A19, C30, C33)

Spike contract note. Plan: `.ai/plans/feature-maude-v2-redesign.md` (V2-1.7 → S9; default approach "Roles (1.7)").
Topic owner: `.design/ui/v2/10 Share and Collaboration.tsx` (`co-share-roles`, `co-share-advanced`, `co-ask-edit`,
`co-access-ends`, `co-browser-view`, `co-trashed`, `co-bring`). Binding notes it composes with: V2-1.12 (declared-format
fence, 426 doors, project store, H1–H5) and V2-1.2 (`ModeCaps`, Viewing, `minRole` per tool). Its leak closure is
V2-1.16 (`V2-1.16-acl-leak-matrix.md`, rows L1–L21); this note defines the model those rows enforce.

## 1. Question

> Can view role (or viewer sub-flag), trash vs clear-out split, canvas-scoped membership, link roles, access requests,
> self-hosted capability report; migration of existing members

Brief additions: A19 — Can view is refused every download/export route on the server, and the DDR says plainly that
this is a courtesy limit, not DRM. Rule 12 — whatever the UI hides for a role, the server or hub also refuses. Hub and
cloud changes are additive and v1-compatible. Inventory `C-advanced-share.md` §10 is the checklist.

## 2. What exists today

**One matrix, three roles.** `apps/hub/src/role-matrix.mjs`:

- `ROLES = ['owner','member','viewer']`, `CAPABILITIES` = read · session · edit · comment · annotate · export · invite ·
  delete · mirror.
- In `MATRIX`, `viewer` holds read, session, comment and export. `member` also holds edit and annotate. `invite`,
  `delete` and `mirror` are owner-only.
- An unknown role gets `NONE`. `isReadOnlyRole = !can(role,'edit')`.
- `projectRoleForAccount` translates account roles (`users.mjs`: `admin | member`) into project roles; `admin` maps
  to `owner`.

Consumers:

- `studio-manifest.mjs` `decide(method, path, role)`: the cell's deny-by-default proxy table.
- `browser-auth.mjs`, `auth-routes.mjs` (`/auth/login` mints `role` + `readOnly` on the peer token).
- `server.mjs` `browserSession`: an unrecognised role means no session.
- `render-token.mjs`: claim `r`. A token without `r` "fails toward the floor" = viewer.

**A second table in the control plane.** `apps/cloud/project-access.mjs` has its own `ROLES` and `CAPABILITIES`
(view · edit · comment · invite · billing · mirror · share · delete, with no `export` row), plus `decideAccess`.
`apps/cloud/membership.mjs` repeats `ROLES` (weakest first) in `decideMembershipChange`, where a demotion revokes
sessions. The D1 schema (`apps/cloud/migrate.mjs` v4/v5) pins the strings:

- `project_members.role CHECK (role IN ('viewer','member','owner'))`
- `project_invites.role CHECK (role IN ('viewer','member'))`

The owner is the `projects.account_id` column, not a member row.

**Tokens.**

- Cloud access token (`apps/hub/src/cloud-identity.mjs`):
  - `accessClaims` = `{email, project, role, iat, exp}`, signed `<body>.<sig>`. Mirrored by `apps/cloud/cell-token.mjs`
    `mintProjectToken`.
  - `verifyAccessToken` returns `role: claims.role ?? 'member'`, so a missing role defaults upward.
- Hub peer token (`apps/hub/src/tokens.mjs`): columns `scope` (a documentName-or-file-path prefix, DDR-053 §3),
  `read_only`, `role`, `owner`, `expires_at`. Every human session is minted with `scope: '*'`. One `scope` string
  cannot name a canvas's Y.Doc (`ws/<w>/<b>/<slug>`) and its files (`ui/…`) at once. `file-manifest.mjs` admits that a
  narrower token "sees no plane-B files at all".
- Revocation (`apps/hub/src/revocations.mjs`) is per email and monotonic, compared against the token `iat`. The cloud
  feeds it from `member_revocations` (v10).

**Enforcement layers** (decision `d_820067712f8334f84fa39c30`, "Read-only is a capability on the peer token, enforced in
three layers"):

1. Yjs: `onAuthenticate` → `connectionConfig.readOnly`, re-fenced per message by `hub-integration.mjs` `fence`.
2. One HTTP gate in `onRequest`: `readOnlyAllowedPath` = `/auth/logout`, `/api/export`, `/api/studio/comments` (no
   handler exists behind it — a stale string), `/auth/browser/signout`.
3. The studio's own gate (`http.ts` `projectReadOnly` / `readOnlyRefusal` / `READ_ONLY_ALLOWED_WRITES`). It is a bool,
   allows `/_comments`, every export route and `/_api/export-history`, and on the desktop asks
   `sync/hubs-config.ts` `isHubReadOnly(url)`, which is `record?.role === 'viewer'`. That string test is exactly what
   the matrix's own comment forbids.

**Doors.**

- `apps/cloud/handoff.mjs`: the app lane refuses viewers (`viewer-not-supported`); the browser lane admits them.
- The proxy injects `x-maude-role` / `x-maude-readonly` / `x-maude-user` / `x-maude-session` / `x-maude-canvas-token`
  after stripping inbound `x-maude-*` (`studio-proxy.mjs` `upstreamHeaders`).
- One studio child serves every browser member, per request (DDR-209).

**Trash today.**

- Studio `deleteCanvas` moves the sidecar set to `_trash/<stamp>__<slug>/`; `_trash/` is per-Mac runtime state
  (DDR-115).
- The hub file door `DELETE /api/file/<rel>` quarantines, then tombstones. Members spend the delete budget; owners are
  outside it (`file-door.mjs` `ownerDelete = role === 'owner'`; decision `d_5b98bf7df47572947d0b6de8`).
- `/_api/sync/trash` prunes only `≥ 1 day` and is refused in a cell.
- There is no shared Trash list and no clear-out.
- The matrix's `delete` (owner) guards no hub route. The cloud uses it for project deletion and download
  (`project-admin.mjs`).

**Links, requests, self-hosted.**

- The 2026-09 share-link feature: a link is a location, not a token ("people need access to this project to open the
  link", `client/share-dialog.jsx`).
- No access-request record exists anywhere.
- A self-hosted hub has account roles `admin | member` only (`users.mjs`), so no Can comment and no Can view.
- `/health` advertises `capabilities: ['ledger','annotations-v2']` publicly.

**Decisions that constrain this.**

- `d_b219fd3d7a46532d40cab867`: one role matrix at the cell; both surfaces are clients; comment is the one write a
  viewer holds; annotate sits with edit; an unknown role gets nothing.
- `d_39bd12253f8ee17739312974`: translate at one boundary.
- `d_e589fb91311c432b287ec751` (proposed, Gate 0 A6 signed it): Can view = look only; Ask to edit → owner.
- `d_8df2557385a9f833f58b0697`: project invites are their own table; per-project routes are their own module; audit
  every membership change.
- DDR-204 (membership is a control-plane fact; offline token verification).
- DDR-209 (one studio, three shells; role per request).
- DDR-210 (canvas capability; role on the session).
- DDR-053 §3 (token scope).
- DDR-054 (hub untrusted to peers; the canvas origin is segregated).
- DDR-115, DDR-226 (file plane; the classifier is the oracle), DDR-241 (kernel fence).
- V2-1.12 §5.4 (writers declare; 426 rather than 403 for old-client-visible refusals).

## 3. Options

1. **Plan default: one role below `viewer` + a path-scoped grant** (chosen, with the extensions below). Add `observer`
   (= Can view) to the one matrix. `viewer` keeps meaning Can comment. Canvas-scoped access is a grant list carried on
   every credential and resolved by one predicate module. *Cost M–L* (D1 table rebuild, token v2 envelope, the
   V2-1.16 checks). *Breaks:* nothing for existing members — their role strings and tokens are untouched.
2. **Viewer sub-flag** (`viewer` + `lookOnly: true`). *Cost S* (no D1 CHECK change). *Breaks:* **fails open.** Every
   old cell, hub and desktop ignores an unknown claim and treats a Can view person as Can comment, so they could
   comment and export. This is rejected on rule 12 alone.
3. **Rename the wire vocabulary to v2 words** (`view | comment | edit | owner`). *Breaks:* every v1 token, the D1
   rows, `hubs.json`, `isHubReadOnly`, the cell manifest and handoff codes, all at once. A flag day on a fleet that
   rolls only on tags.
4. **Capability lists on the token instead of a role.** This makes a second matrix (the token's own) that drifts from
   the cell's, and old verifiers ignore the list.
5. **A separate cell per shared canvas** (copy the canvas out). Isolation by construction, but the canvas is no longer
   live with the project. *Breaks:* co-share-roles ("opens in an Alligators brand tab"), presence and comments.

For canvas scope inside option 1:

- (a) **Reuse `tokens.scope`.** Rejected: it is one prefix string over two namespaces, so it can't select a document
  and its files together (V2-1.16 L1/L2).
- (b) **Filter in the UI only.** Rejected by rule 12.
- (c) **A grant list + one predicate + a server-computed file closure** (chosen).

## 4. Decision (DDR draft)

**Title:** Four roles, one matrix, grants per canvas — Can view is a role below Can comment, scope is a grant list
resolved at every door.

**Context.**

- v2 draws four roles: Owner · Can edit · Can comment · Can view.
- Two scopes: This canvas · Whole project.
- Links that give at most Can comment, an Ask-to-edit request, and a trash that editors fill and only owners empty.
- A self-hosted hub with no view-only accounts.

The hub has three roles; `viewer` already means Can comment. Every credential is project-wide. A viewer can download
the whole project source today (`/_api/export-jobs` with `project-raw`, `/_project-file/`, `/api/history/file`, the
`v1/lane` and `blobs` routes). Two role tables exist (hub, control plane), and the desktop gate tests a role string.

**Decision.**

1. **One new role, `observer` = Can view**, ranked below `viewer`:
   - The order is `observer < viewer < member < owner`.
   - Wire ids never change. UI words map one to one: Owner · Can edit (`member`) · Can comment (`viewer`) · Can view
     (`observer`).
   - The client's minRole levels (V2-1.2 `Role`) are `observer → 'view'`, `viewer → 'comment'`,
     `member | owner → 'edit'`.
2. **The matrix moves to the studio tree** (`apps/studio/access/roles.ts`) **and stays the one table.**
   - `apps/hub/src/role-matrix.mjs` re-exports it, so every import and test is unchanged.
   - `apps/cloud` imports it, which deletes the `project-access.mjs` `CAPABILITIES` copy and the `membership.mjs`
     `ROLES` copy.
   - The studio's local gate imports it, which deletes the `isHubReadOnly` string test.
   - Why the studio tree: the npm package ships `apps/studio` but not `apps/hub`, and the hub already imports studio
     `.ts` (`lanes.mjs`). The authority is still the cell's enforcement; only the file location moves.
3. **New capabilities:**
   - `trash` (owner, member): move to the trash.
   - `summon` (owner, member): Bring everyone here, C33.
   - `request` (observer, viewer): Ask to edit.
   - `delete` (owner) is redefined as "delete for good": clear out the trash, delete the project. Its id is kept for
     v1.
   - `observer` holds only `read`, `session` and `request`.
4. **A19.** Every route that hands project bytes away as a file — export, render jobs, ZIP, raw project files, raw
   source, history blobs — requires `export`, so `observer` is refused.
   - Observers are never minted a peer token, so they never get a local file-plane copy. A v2 desktop opens their
     project as a cell-served tab (browser door).
   - **This is a courtesy limit, not DRM.** A viewer's browser still holds every byte it renders — the built canvas
     module, its assets, its fonts — and anyone can screenshot or save it.
5. **Grants per canvas:**
   - An access claim = a project role (or `null` for canvas-only) plus up to 256 canvas grants.
   - The effective role on canvas `c` is `max(projectRole, grant[c])`. A grant adds and never lowers.
   - A canvas-only session sees its granted canvases and their **closure**: own files, import closure, design system
     and referenced assets, computed on the server. It can write only its canvases' own files and new assets. It never
     holds project-level capabilities (`invite`, `delete`, `mirror`, create canvas, project export).
   - One predicate module (`apps/studio/access/scope.ts`) is imported by the hub, the studio, the cloud and the cell
     DO. The doors V2-1.16 lists call it.
6. **Credentials carry the claim, and old verifiers refuse it by format:**
   - **Cloud access token v2** = `m2.<body>.<sig>` (three parts). An old cell's parser requires two parts and answers
     `malformed`. The control plane mints v2 only when the claim needs it (observer, canvas-only, or any grant); every
     other token stays byte-identical v1.
   - **Hub peer tokens** gain an `access` column (JSON claim).
   - **Render tokens** gain `g` (grants). Their floor becomes `observer`.
   - The proxy injects `x-maude-access`.
7. **Clients declare.** `/auth/login` and the cloud handoff exchange read `X-Maude-Access: 2`.
   - A claim a v1 client can't honour (observer, canvas-only, grants) without the declaration gets **426** with the
     copy "Update Maude to open this project". 426, not 403, for the V2-1.12 reason.
   - Observer + declared gets **409 `browser-door`** with the cell URL, so the v2 app opens a cell tab.
8. **Links** are a control-plane table:
   - Scope: canvas or project. Role: `observer` or `viewer` only.
   - `who` is `team` (a location; no grant) or `anyone` (any **signed-in** Maude account holding the link secret).
   - Optional expiry. An `anyone` link redeems into a grant with `source = 'link:<id>'`.
   - Turning a link off, or its expiry, deletes those grants and revokes the sessions.
   - A self-hosted hub has no links.
9. **Access requests** are a control-plane table: one open request per person per scope. The cell forwards the
   request and notifies owner connections. Approval writes a `member` grant at the request's scope and pushes
   `maude.access` to the requester, who re-exchanges.
10. **Clients learn what a hub supports from `/health`:** capability `roles-v2` + public posture
    `access: {authority, roles, scopes, links, requests}`. Cloud cells report all four roles. A self-hosted hub reports
    `['owner','member']` and `links: false`. The Share sheet renders from it.
11. **Migration rewrites no role.**
    - Existing `viewer` rows already mean Can comment.
    - D1 `project_members` and `project_invites` are rebuilt to admit `observer`. New tables: `canvas_grants`,
      `share_links`, `access_requests`, and `handoff_codes.access`.
    - Existing tokens keep working.
    - The 1.x compat release (V2-2.18) carries the matrix import into the desktop gate and the hub's capability-based
      HTTP gate.

**Consequences.**

- A Can comment person keeps today's powers exactly, including the whole-project raw ZIP. "Look, comment and download"
  is Michal's signed wording. A Can view person can look and ask, nothing else, on every door.
- Canvas-only editors get a local copy limited to the closure, so AI (A5, A13) works on their canvas. The peer door
  must therefore filter (V2-1.16). Observers and observer-led claims stay on the browser door only.
- A canvas that imports a shared local module or a design system reveals that module's source to whoever can see the
  canvas (V2-1.16 L19). The Share sheet states it once when a canvas has such imports.
- The cloud gains the public `/health.access` posture. It names only what the hub software supports, never tenant
  data.
- No new runtime-state class: grants live in D1, the hub token store and the request body; nothing goes under
  `.design/`. The four DDR-115 lists are unchanged.

**Rejected alternatives.** Options 2–5 and (a)/(b) above, for the reasons listed there. Also rejected:

- **Refusing observers on the desktop entirely.** The canvas draws Petra's Mac at Can view (`co-ask-edit`); a cell tab
  gives her that without files.
- **Capability-gated minting alone** (minting `observer` only to cells advertising `roles-v2`). It is kept as a UX
  check, but the format change is what makes an old cell fail closed even if the check is wrong.
- **Letting the cell decide membership changes in cloud mode.** That would contradict DDR-204. The cell forwards; the
  control plane re-decides the actor's role from D1.

### 5.1 Role vocabulary

| UI word (CONTRACT §6) | Wire id | Rank | V2-1.2 `Role` level | Self-hosted account role |
| --- | --- | --- | --- | --- |
| Owner | `owner` | 3 | `edit` (+ owner capabilities) | `admin` |
| Can edit | `member` | 2 | `edit` | `member` |
| Can comment | `viewer` | 1 | `comment` | — |
| Can view | `observer` **(new)** | 0 | `view` | — |

- Ids are never shown in the UI. "View only" (V2-1.12 §5.8) and "Linked library — view only" (C18) are access-state

### 5.2 The matrix (`apps/studio/access/roles.ts`)

| Capability | owner | member | viewer | observer | What it covers (registry `minRole`) |
| --- | --- | --- | --- | --- | --- |
| `read` | ✓ | ✓ | ✓ | ✓ | look: canvases, comments, Version history words and thumbnails, presence |
| `session` | ✓ | ✓ | ✓ | ✓ | your own place: camera, tabs, prefs, tree state, bug report (DDR-115 per-user) |
| `request` **new** | — | — | ✓ | ✓ | Ask to edit |
| `comment` | ✓ | ✓ | ✓ | — | comment, reply, resolve your own thread |
| `export` | ✓ | ✓ | ✓ | — | every download and export, render jobs, ZIP, raw source / code view (`/_api/canvas-source`), history blobs, raw project files |
| `annotate` | ✓ | ✓ | — | — | stickies, marker, arrows, stickers, sections |
| `edit` | ✓ | ✓ | — | — | change artboards, insert, import, Use AI (C30: no AI panel below this) |
| `trash` **new** | ✓ | ✓ | — | — | move to the trash |
| `summon` **new** | ✓ | ✓ | — | — | Bring everyone here (C33) |
| `invite` | ✓ | — | — | — | invite, change roles, remove, links, approve requests |
| `delete` | ✓ | — | — | — | **clear out the trash**, delete for good, delete the project |
| `mirror` | ✓ | — | — | — | GitHub copy, push |

```ts
// apps/studio/access/roles.ts — pure, zero deps; imported by hub (re-export in role-matrix.mjs), cloud, cells, studio.
export const ROLES = ['observer', 'viewer', 'member', 'owner'] as const;   // weakest first
export type ProjectRole = (typeof ROLES)[number];
export const CAPABILITIES = ['read','session','request','comment','export','annotate','edit',
                             'trash','summon','invite','delete','mirror'] as const;
export type Capability = (typeof CAPABILITIES)[number];
export function can(role: string | null | undefined, cap: Capability): boolean;  // unknown role → false for all
export function isReadOnlyRole(role: string | null | undefined): boolean;        // = !can(role, 'edit') — unchanged
export function rankOf(role: string | null | undefined): number;                // -1 for unknown/null
export function maxRole(a: string | null, b: string | null): ProjectRole | null; // unknown ignored
export const FLOOR_ROLE: ProjectRole = 'observer';          // render-token and any "missing role" floor
export const PROJECT_ONLY: readonly Capability[] = ['invite', 'delete', 'mirror']; // never via a canvas grant
export function projectRoleForAccount(role: string | null | undefined): ProjectRole | null; // unchanged semantics
export function levelOf(role: ProjectRole | null): 'view' | 'comment' | 'edit' | null;     // the V2-1.2 bridge
export function matrixRows(): Array<{ role: ProjectRole } & Record<Capability, boolean>>;  // strongest first
```

Invariants:

- **(R1)** An unknown role or `null` holds nothing.
- **(R2)** `can(observer, x)` holds only for `read`, `session` and `request`.
- **(R3)** The `viewer` row equals today's row for every pre-existing capability: the v1 parity test.
- **(R4)** `trash ⊆ edit` holders and `delete ⊆ owner`.
- **(R5)** `request` is held exactly by the roles without `edit`.
- **(R6)** Every capability any door names exists in `CAPABILITIES`. The import-time sanity check in
  `studio-manifest.mjs` stays.

### 5.3 Grants and the access claim (`apps/studio/access/scope.ts`)

```ts
export interface Grant { c: string; r: 'observer' | 'viewer' | 'member' }
//   c = canonical designRoot-relative canvas path ('ui/2026/combine/Combine-kampan.tsx'), the same key
//   sync/canvas-path.ts uses; never a slug. A grant never carries 'owner'.
export interface AccessClaim { v: 1; role: ProjectRole | null; grants?: Grant[] } // ≤ 256 grants, sorted by c
export interface Access {
  readonly role: ProjectRole | null;          // project-level role; null = canvas-only session
  readonly canvasOnly: boolean;               // role === null && grants.length > 0
  roleFor(canvas: string | null): ProjectRole | null;       // max(role, grant[canvas]); canvas null → role
  can(cap: Capability, canvas: string | null): boolean;     // PROJECT_ONLY needs role !== null
  seesCanvas(canvas: string): boolean;                       // role !== null || canvas ∈ grants
  minted: { declaredAccess: 1 | 2 };                         // what the client said it understands
}
export function resolveAccess(claim: AccessClaim | null, opts?: { declaredAccess?: 1 | 2 }): Access;
export function legacyClaim(role: string | null): AccessClaim;  // v1 token → {v:1, role: projectRoleForAccount(role)}

// File-level visibility needs the project's files — computed where they are (hub checkout/journal, studio child):
export interface ProjectReader { list(): Iterable<string>; text(rel: string): string | null; head(): string }
export interface Closure {
  head: string;                    // journal head / tree hash the closure was computed at (cache key)
  owned: ReadonlySet<string>;      // per granted canvas: .tsx, .meta.json, .annotations.json(.svg), same-name group
                                   //   .css, <base>.registry.json / .edl.json, _comments/<slug>.json
  read: ReadonlySet<string>;       // owned ∪ relative import closure (.tsx/.ts/.jsx/.css under designRoot, transitive)
                                   //   ∪ system/<ds>/** of the canvas's meta.designSystem (excluding preview/*.tsx
                                   //   specimens and ui_kits/*) ∪ statically referenced assets + their sidecars
}
export function closureFor(access: Access, project: ProjectReader): Closure;   // only for canvasOnly sessions
export function sees(access: Access, closure: Closure | null, rel: string): boolean;
export function writes(access: Access, closure: Closure | null, rel: string, o: { exists: boolean }): boolean;
export function seesDoc(access: Access, documentName: string, slugOf: (canvasPath: string) => string): boolean;
```

Rules:

- **(G1) Never lowers.** The effective role is the higher of the project role and the grant. A canvas grant to someone
  who already holds that role or higher is stored but changes nothing (co-share-roles caption).
- **(G2) Canvas-only sessions:**
  - Sees: only the granted canvases plus their closure.
  - Writes (`edit` on that canvas): only `owned` of a granted canvas, plus **create-only** new files under `assets/`.
  - A photo-edit sidecar of an existing asset is writable only when every canvas referencing that asset is in the
    session's edit grants.
  - Never: code modules (already owner-only), design-system files, shared modules.
  - Refusal copy is generic and never says why: "Ask the owner to change this."
- **(G3) Static closure.** Assets or modules referenced only at runtime (a computed URL) are not in the closure, and
  the canvas-only member gets a 404 for them. The Share sheet warns when the scanner finds a dynamic reference. The
  scanner reuses `http.ts` `localDepsFromSource` (moved into `access/closure.ts` and imported back by `http.ts`, so the
  build and the ACL agree on one import graph), `canvas-lib.tsx` `ASSET_REF_RE`, `annotations/constants.ts`
  `ASSET_IMAGE_HREF_RE` and the `photo/schema.ts` ref.
- **(G4) Cache.** The closure is cached per `(sorted grants, head)`, recomputed lazily on the next request after the
  head moves, and computed on the server only.
- **(G5) Moves.** A canvas move or rename (`doc.move`, `fs-move`) rewrites the grant's `c` in the same transaction —
  control-plane rows through the cell's existing move signal; self-hosted in `users.access`. A trashed canvas keeps
  its grants until it is cleared out; a restored canvas gets them back.

### 5.4 Credentials

**Cloud access token** (`cloud-identity.mjs` + `cell-token.mjs`; the shape is still shared, never redeclared):

| Format | When the control plane mints it | Claims | Old cell (pre-`roles-v2`) | New cell |
| --- | --- | --- | --- | --- |
| v1 `<body>.<sig>` | `role ∈ {owner, member, viewer}` and no grants | `{email, project, role, iat, exp}` — byte-identical to today | accepts (unchanged) | accepts; **refuses** a v1 body carrying `grants`, `role: 'observer'` or no `role` (`malformed`) |
| v2 `m2.<body>.<sig>` | `role === 'observer'`, `role === null`, or any grant | `{v: 2, email, project, role, grants?, iat, exp}` | `malformed` (`parts.length !== 2`): **fails closed** | accepts |

- The same HMAC key (`projectTokenKey`) signs both formats.
- **H-1 (hardening, ships in V2-2.18):** `verifyAccessToken`'s `claims.role ?? 'member'` becomes "no role → refuse".
  Every mint path (`accessClaims`, `mintProjectToken`) already sets a role, and a test pins that.

**Hub peer token** (`tokens.mjs`):

- New nullable column `access TEXT`: the JSON `AccessClaim`, written at mint, preserved by `rotateToken` exactly like
  `role` and `read_only` (with its own red-first test).
- `NULL` means `legacyClaim(role)`.
- `read_only` stays the projection "no `edit` on any canvas". It is still what old code reads, and the 1-bit Yjs fast
  path.
- `scope` keeps its DDR-053 meaning and is never used for canvas scope.

**Peer-token mint door** (`/auth/login`, browser-auth mint, cloud handoff exchange):

| Claim | `X-Maude-Access: 2` declared? | Result |
| --- | --- | --- |
| v1-expressible (`owner`/`member`/`viewer`, no grants) | either | 200, today's token. `viewer` now also on the app lane when declared (handoff stops refusing) |
| has grants, `role` null or ≥ viewer, every grant ≥ viewer | yes | 200, peer token with `access` |
| has grants or observer | no | **426** `{ error: "Update Maude to open this project.", reason: 'access-version', minAccess: 2 }` |
| `role === 'observer'`, or canvas-only with any observer grant | yes | **409** `{ reason: 'browser-door', url: '<cell door url>/c/<canvas>' }`. The v2 app opens a cell tab; no peer token exists |
| revoked / expired | — | today's 401 `access-withdrawn` |

**Render token** (`render-token.mjs`):

### 5.6 Routes (one JSON API, two authorities)

The client always calls **its project server** (the hub, via the desktop studio's proxy, or the cell door):

- **Self-hosted:** the hub is the authority and decides with `users.mjs` + `invites.mjs`, extended by an `access`
  column on users and invites.
- **Cloud:** the hub forwards to the control plane at `/internal/projects/:p/access/*`, using the cell secret plus the
  **vouched actor email** taken from the verified session. The control plane re-decides the actor's role from D1 and
  never trusts a role the cell states.

Each forwarded call is rate-limited (invites ≤ 50/day/project) and audited (decision `d_8df2557385a9f833f58b0697`).

Hub stateless messages (Hocuspocus per connection, the `maude.mode` envelope family V2-1.12 already uses):

- **`{ type: 'maude.access', epoch, change: 'raised' | 'narrowed' | 'ended', reason?: 'removed' | 'link-off' | 'expired' }`**
  - Sent only to connections whose verified email is the affected person.
  - It carries **no grant data**: the client re-exchanges and reads `/api/access/me`.
  - `narrowed` / `ended`: the hub waits `switchGraceMs` before kicking (`kickSessionsForLabel`), so the client's flush
    lands first ("Your last changes were saved first").
- **`{ type: 'maude.access-request', id, from: { name }, canvas?: c, at }`**: sent only to connections whose session
  role is `owner` (toast "Petra asks to edit Combine-kampan" → Review).
- **`maude.files`** stays one-integer (`d_820067712f8334f84fa39c30`'s ctl rule). It never carries access traffic.

**Cloud, D1 (the authority).**

- New tables (5.8) back `/internal/projects/:p/access/*`.
- **The link redeem lives on the control plane** (`cloud.maude.sh/l/<id>.<secret>`). An `anyone` link requires sign-in
  (signed out → the existing sign-in page with return-to). Redeem upserts a grant (`source: 'link:<id>'`) and runs the
  handoff browser lane to the canvas.
- The link page sets `Referrer-Policy: no-referrer`, POSTs the redeem, and replaces the URL (the hub invite rule: a
  token in a URL leaks via Referer).
- The control plane notifies the cell at `POST /internal/access-changed { email }` (cell secret), which sends
  `maude.access`. The 10-minute revocation sweep stays as the backstop.

### 5.7 The studio's local gate (desktop and cell child alike)

- `projectReadOnly(req)` keeps its name and fail-closed workspace default. It is derived as

- `READ_ONLY_ALLOWED_WRITES` splits by capability:

### 5.8 Data and migration

**D1** (`apps/cloud/migrate.mjs`, next versions). SQLite cannot alter a CHECK, so the two tables are rebuilt the
standard way inside one migration: create `_v2`, copy, drop, rename, recreate indexes, under
`PRAGMA defer_foreign_keys = on`.

```sql
-- project_members_v2: role CHECK (role IN ('observer','viewer','member','owner')) — rows copied verbatim
-- project_invites_v2: role CHECK (role IN ('observer','viewer','member')) + canvas_path TEXT NULL
CREATE TABLE canvas_grants (
  project_id  TEXT NOT NULL REFERENCES projects (id) ON DELETE CASCADE,
  account_id  TEXT NOT NULL REFERENCES accounts (id) ON DELETE CASCADE,
  canvas_path TEXT NOT NULL,
  role        TEXT NOT NULL CHECK (role IN ('observer','viewer','member')),
  source      TEXT NOT NULL,                 -- 'invite' | 'request:<id>' | 'link:<id>' | 'owner'
  granted_by  TEXT, granted_at INTEGER NOT NULL,
  PRIMARY KEY (project_id, account_id, canvas_path)
);
CREATE TABLE share_links (
  id TEXT PRIMARY KEY, project_id TEXT NOT NULL REFERENCES projects (id) ON DELETE CASCADE,
  canvas_path TEXT, role TEXT NOT NULL CHECK (role IN ('observer','viewer')),
  who TEXT NOT NULL CHECK (who IN ('team','anyone')), secret_hash TEXT,   -- NULL for 'team'
  created_by TEXT NOT NULL, created_at INTEGER NOT NULL, expires_at INTEGER, revoked_at INTEGER
);
CREATE TABLE access_requests (
  id TEXT PRIMARY KEY, project_id TEXT NOT NULL REFERENCES projects (id) ON DELETE CASCADE,
  account_id TEXT NOT NULL, canvas_path TEXT, created_at INTEGER NOT NULL,
  decided_at INTEGER, decision TEXT CHECK (decision IN ('approved','declined')), decided_by TEXT
);
CREATE UNIQUE INDEX access_requests_open ON access_requests (project_id, account_id, IFNULL(canvas_path,''))
  WHERE decided_at IS NULL;
ALTER TABLE handoff_codes ADD COLUMN access TEXT;      -- the AccessClaim captured at mint, re-decided at exchange
ALTER TABLE projects ADD COLUMN default_invite_role TEXT;  -- "New people join as" (NULL = 'member')
```

## 9. Open questions (conservative default in bold)

1. **Anonymous link visitors.** May an `anyone` link open without a Maude account?
   **Default: no — sign-in is required.** Every session stays attributable for presence, audit and revocation; Vojta
   signs in once with Google.
2. **What `team` links mean when the role row says Can view** (co-share-advanced draws both).
   **Default: a `team` link is a location (today's behaviour) and grants nothing; the role applies to `anyone` links
   only.**
3. **Grants from an expired link.**
   **Default: they end with the link** (the link is the access); the expiry sweep writes revocations.
4. **Re-asking after "Not now".**
   **Default: the request closes silently; the requester may ask again after 24 h; the button reads "Asked" until
   then.**
5. **A project observer holding a `member` grant on one canvas.**
   **Default: a cell tab for the whole project** (the peer door never syncs a project an observer may only look at);
   they can edit that canvas in the tab, without AI.
6. **The removed person's local copy after "access ends".**
   **Default: after the final flush lands, the app removes the cloud project's local copy from that Mac and from the
   Home index; if the flush fails, the copy stays unlinked and the card says so.**
7. **Self-hosted Can comment / Can view.**
   **Default: not in v2.0** (the report says no); the posture makes adding them later a server-only change.
8. **Approve scope.** Does "Let Petra edit" grant at the request's scope or the whole project?
   **Default: the request's scope** (the canvas she asked from, or the project).
9. **Dynamic asset references in a shared canvas.**
   **Default: not shared, with a one-line warning in the Share sheet** "1 picture here is chosen while it runs and won't
   show for people who only have this canvas."

## Decisions

- `decision:maude/v2-1.7-observer-role-below-viewer`
  - **What:** add the project role `observer` (UI: Can view) below `viewer`, which keeps meaning Can comment. The order
    is `observer < viewer < member < owner`. Wire ids never change; UI words map one to one.
  - **Why:** a sub-flag fails open on every old cell and desktop; renaming the wire vocabulary is a flag day.
  - **Rejected:** a viewer `lookOnly` sub-flag; renaming to view/comment/edit; capability lists on tokens.
- `decision:maude/v2-1.7-one-matrix-in-studio-tree`
  - **What:** the role matrix moves to `apps/studio/access/roles.ts`. `apps/hub/src/role-matrix.mjs` re-exports it; the
    cloud and the studio local gate import it. The control plane's second table and the desktop's `role === 'viewer'`
    test are deleted. New capabilities: `trash` (owner + member), `summon` (owner + member), `request` (viewer +
    observer). `delete` means delete for good / clear out (owner).
  - **Why:** two tables already drifted (no `export` row in the cloud); the npm package ships the studio tree; the hub
    already imports studio `.ts`.
  - **Rejected:** twin tables with a parity test; leaving `delete` overloaded.
- `decision:maude/v2-1.7-can-view-refused-every-download`
  - **What:** every byte-handing route requires `export`, which observers lack. That covers export, render jobs, ZIP,
    raw project files, raw source, history blobs, `v1/lane` and `v1/blobs`. Observers are never minted a peer token: a
    v2 desktop opens them as a cell tab. The DDR states this is a courtesy limit, not DRM.
  - **Why:** A19 and rule 12. Today a viewer's cookie works as a Bearer on every hub GET, and a local copy is itself a
    download.
  - **Rejected:** UI-only hiding; a local read-only copy for observers.
- `decision:maude/v2-1.7-canvas-grants-and-closure`
  - **What:** an access claim = a project role (or null) + ≤ 256 canvas grants. The effective role is the max of the
    two (a grant never lowers). A canvas-only session sees its canvases plus a server-computed static closure, writes
    only those canvases' own files plus new assets, and never holds project-level capabilities. One predicate module,
    `apps/studio/access/scope.ts`, serves every door.
  - **Why:** the token `scope` prefix can't express one canvas across documents and files.
  - **Rejected:** reusing `tokens.scope`; UI filtering; one cell per shared canvas.
- `decision:maude/v2-1.7-token-v2-fails-closed-on-old-cells`
  - **What:** claims needing v2 semantics (observer, canvas-only, grants) travel as `m2.<body>.<sig>`; old verifiers
    reject them as `malformed`. Every other token stays byte-identical v1. Hub peer tokens gain an `access` column
    (preserved by rotate); render tokens gain `g`, and their floor becomes `observer`; the proxy injects
    `x-maude-access`. Clients declare `X-Maude-Access: 2`; otherwise 426 "Update Maude to open this project", and
    observers get 409 `browser-door`. H-1: a missing role is refused, not defaulted to member.
  - **Why:** capability-gated minting alone is a promise; a format the old parser refuses is a property.
  - **Rejected:** minting gates only; reusing the v1 envelope with extra claims.
- `decision:maude/v2-1.7-access-api-two-authorities`
  - **What:** one JSON API on the project server, `/api/access/{me,people,invites,links,requests}` +
    `/api/trash/clear`. A self-hosted hub decides locally. A cloud cell forwards to the control plane with the cell
    secret + the vouched actor email, and D1 re-decides the role. The hub sends stateless `maude.access` (no grant
    data) to the affected person and `maude.access-request` to owner connections. Links are a control-plane table
    (role ≤ viewer, `team` | `anyone`; `anyone` needs sign-in; off/expiry revokes link-sourced grants). Requests are a
    control-plane table, one open per person per scope.
  - **Why:** DDR-204 (membership is a control-plane fact) and "one code path, two configurations".
  - **Rejected:** the cell deciding membership in cloud mode; the desktop calling the control plane directly for
    sharing (two client APIs); anonymous link sessions.
- `decision:maude/v2-1.7-hub-comment-door`
  - **What:** a viewer's comments reach a hub through `POST /api/comments` (needs `comment` on the canvas). The hub
    applies the op to the canvas doc's `comments` lane server-side and stamps the author from the session. It replaces
    the handler-less `/api/studio/comments` allowlist string.
  - **Why:** Hocuspocus read-only is per connection, so a viewer's Y connection drops comment updates. Once v2 admits
    viewer desktops their comments would vanish.
  - **Rejected:** making viewer Y connections writable and filtering lanes (no per-lane read-only in the protocol).
- `decision:maude/v2-1.7-capability-report`
  - **What:** `/health` advertises `roles-v2` and the public posture
    `access: {authority, roles, scopes, links, requests}`. Self-hosted reports `['owner','member']` with no links or
    requests; the Share sheet renders only what is reported.
  - **Why:** A6 — a self-hosted hub without view-only accounts hides Can view and links.
  - **Rejected:** inferring support from the hub version string.
- `decision:maude/v2-1.7-migration-rewrites-no-role`
  - **What:** existing roles keep their meaning (`viewer` = Can comment, R3). The D1 `project_members` and
    `project_invites` tables are rebuilt only to admit `observer`. New tables: `canvas_grants`, `share_links`,
    `access_requests`, `handoff_codes.access`, `projects.default_invite_role`. Project-level members get no grant
    rows. The app lane admits declared-v2 viewers. Release order: hub/cell/cloud → 1.x compat → v2 clients; v2 tokens
    only for cells reporting `roles-v2`.
  - **Why:** additive and v1-compatible (plan "Branching", V2-2.18).
  - **Rejected:** remapping existing viewers to Can view; a flag-day token re-issue.
