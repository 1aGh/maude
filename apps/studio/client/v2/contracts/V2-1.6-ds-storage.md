## 2. What exists today

**A system is a folder.** `system/<ds>/` holds:

- `colors_and_type.css`, `README.md`, `SKILL.md` (and `CONTRACT.md` for maude-v2);
- about 40 specimens `preview/*.tsx` with sibling `.css` files;
- `preview/_components.css`, `preview/_layout.css`;
- `assets/`, including DDR-141's `assets/logos/<sha8>.(svg|png)` and `preview/logo.*` / `preview/iconography.*`.

`config.designSystems[]` and `defaultDesignSystem` list the systems (DDR-048).

**How a canvas picks its system:**

- `api.ts` `buildIndexData` builds `canvasDesignSystems`. A path under `system/<ds>/` wins; otherwise
  `meta.designSystem`; otherwise the default (DDR-093).
- `client/canvas-url.js` `canvasUrl` sets `tokens=` and `components=`.
- `plugins/design/templates/_shell.html` fills `<link id="canvas-tokens">` and `<link id="canvas-components">` and
  hot-swaps them when the file changes.
- Every canvas renders the live file. Nothing is pinned, and there are no revisions or `tokens.json`.

**Who writes the token CSS today:**

- `/design:setup-ds` (from the template);
- `maude design import-tokens` (DDR-172, `_import-tokens.mjs`): theme-block-scoped `locateThemeBlock` +
  `patchDeclarationInBlock`, atomic tmp+rename, realpath containment, backup to `_history/_system/`;
- hand and agent edits.

**Sync** (`sync/file-membership.ts` `classifyProjectFile`):

- `system` is a canvas group.
- A group `.tsx`, its `.meta.json` and its same-name `.css` are `canvas-owned` (Plane A).
- `colors_and_type.css`, `_components.css` and `_layout.css` are `companion-text` (Plane B).
- Any `.json` outside `COMPANION_SIDECAR_SUFFIXES` is `never`, so `tokens.json` would not travel today.

**The two planes:**

- **Plane B** is whole-file. Conflict = rename-aside + propagate (DDR-226 §1). A same-hash append is a no-op (§2).
  There is no order across files.
- **Plane A meta** merges per key through `mergeJson` (`apps/hub/src/project-transactions/lanes.mjs`). Nested
  objects merge. A key changed on both sides is `{ok:false}` (base-conflict). Arrays merge only by `id`.

**One user action = one version:** `sync/action-stage.ts` `createActionStage` for hub projects (DDR-241),
`_history/` locally. V2-1.5 owns the unified model.

**Serving on the canvas origin** (`http.ts`):

- The static lane serves `.css` under designRoot, never `.json` (`CANVAS_ASSET_EXTS`).
- `_`-prefixed segments are refused.

**Cells.** `apps/hub/src/project-config-door.mjs` gives a cell only `{name, path, tokensCssRel}` per system.

**Why not git** (`.ai/plans/notes/v2-inventory/I-substrate-audit.md` #4). Git-based pinning (`dsRev` + `git show`)
breaks in four places:

- non-git local projects;
- cloud cells and browser shells;
- shallow clones;
- a per-Mac `_state` base: generated files sync, so every peer gets spurious "changed outside" reviews.

The plan's Reuse cell for S10 ("the git service for `dsRev`") predates this audit, and the plan's default approach
overrides it.

**Decisions:**

- kg `d_2588c6db…` (the design system lives on a board), `d_622299e3…` (three tiers), `d_0aa8c126…` ("content-addressed
  DS revisions instead of git").
- DDR-226 (two planes, classifier as the single oracle, conflict-aside), DDR-223 (emptiness never beats content),
  DDR-102 (cold start), DDR-115 (runtime taxonomy), DDR-054 (hub and peers untrusted), DDR-243 (a cell's disk is a
  cache), DDR-172, DDR-141, DDR-093, DDR-048.
- `kg search "design system pinning"` finds no prior pinning decision.

## 3. Options

1. **The plan default, refined by what canvas 13 draws** (chosen): content-addressed revisions
   `system/<ds>/revisions/<id>.json`, `meta.dsRev` on a left-out canvas, a versioned base, "Update N canvases"
   rewriting `dsRev` in one version, libraries copying revisions in. Five refinements, each forced by an artboard:
   - **Followers render the published head revision, not the live file.** 11 `ds-truth-outside`: "Keep makes them
     part of the system. Canvases then follow after the usual review."
   - **Pending in-app edits live on the Design system canvas** (`dsPending` in its `.meta.json`, Plane A, merged per
     token), not in the files. 12 `ds-truth-conflict` draws "On this canvas: Deeper azure" against "In
     colors_and_type.css: Sea blue" while "canvases keep Azure" — three distinct values.
   - **A revision is pure content** (no time, author or parent), so the same content is the same bytes on every
     peer. Plane B appends it once and it never conflicts. Who and when go into the pointer file's log.
   - **A revision embeds the files it freezes, and has two deterministic `.css` siblings.** The canvas origin's
     static lane, the exporters, remote render and cells all serve it unchanged.
   - **One small mutable pointer file per system**, `revisions/head.json` (head, base, drafts, log, library).

   Cost M–L. Breaks nothing for unconverted systems; they behave as today.
2. **Git-based pinning.** Breaks per I #4.
3. **A per-Mac base in `_state/`.** Breaks per I #4: spurious reviews on every peer.
4. **Frozen copies inside each left-out canvas** (old values inlined into its TSX or meta). N copies; the components
   CSS can't be frozen per canvas cheaply; TSX churn fights Claude's edits; no dedupe.
5. **Pending edits written straight into the working files.** Leaks unpublished values to code and git; can't draw
   `ds-truth-conflict`; Cancel has to rewrite files.
6. **Head, base, pending and log all in the DS canvas meta.** Systems without a DS canvas would have nowhere to pin;
   every follower would depend on one canvas's meta; the log would grow the meta.
7. **Revision JSON only, plus a canvas-safe route to serve its CSS.** Needs a canvas-origin route (both allowlists,
   DDR-088), a new `_shell.html` param grammar, and changes to `exporters/index.ts`, `exporters/remote.ts` and the
   render service. The siblings avoid all of it.

## 4. Decision (DDR draft)

**Title:** Design systems on a canvas — content-addressed revisions, a head pointer, pending edits on the canvas,
per-canvas pins.

**Context.** A9 and A15 turn a system folder into an editable canvas whose files are generated from it, while the
files remain the API for code and agents (A13). B9 needs canvases that keep old values when left out of an update,
a review for outside edits, and a conflict pick. All of it must hold on every transport: local, git, Syncthing, the
hub's two planes, cloud cells and browser tabs. Git cannot carry it (I #4).

**Decision.**

1. **The Design system canvas is a real canvas file**, `<ds.path>/design-system.tsx` (+ `.meta.json`), identified by
   its path. Its section artboards have fixed ids. It is written at conversion or creation and renders from the
   system's model.
2. **Working files** are the API for code and agents: `colors_and_type.css` (`tokensCssRel`),
   `preview/_components.css`, `tokens.json`, `components.json`. A **revision** is an immutable, content-addressed
   snapshot of those four files.
3. **A system is converted when `revisions/head.json` exists.** Unconverted systems follow today's rules (A15
   phase α). Converted systems publish revisions (phase β).
4. **Pointers.**
   - `head` = the published revision; canvases that follow the system render it.
   - `base` = the last revision the app wrote to the working files; it is the outside-change baseline.
   - Both live in versioned `revisions/head.json`, so every peer has the same baseline.
5. **Pending in-app edits** live in the Design system canvas's meta (`dsPending`, per token). Reviews publish them.
6. **A left-out canvas** stores `meta.dsRev = <the head it was following>` and renders that revision's CSS siblings.
   An element can carry `data-ds-rev="head" | <id>` for per-instance updates.
7. **Every review effect is one action:** publish, Keep, Undo, pick, convert, library update, trash.
8. **The generator patches the existing CSS** (DDR-172 D7 discipline) and emits from the template structure only
   for a system made on the canvas.
9. **The usage index** is a per-Mac derived cache hosted by V2-1.17's index service.
10. **Team libraries** are a full local copy: revisions copied in by id, working files materialised, a `library`
    record in `head.json`, view only locally.

**Consequences.**

- An outside edit no longer changes canvases until someone keeps it and runs "Update N canvases".
- Each publish adds about 55 KB of text per system (§6).
- Several new files: the C1 classifier entries now cover `system/<ds>/revisions/*.json`.
- No new runtime-state class.
- v1 peers stay read-only (V2-1.12) and render the working files.
- Partial publishes and per-token pins are not offered.

**Rejected alternatives.** Options 2–7 above. Also rejected:

- Per-token or per-component pins (composing several revisions per canvas). One revision per canvas, plus an
  element attribute for single instances, covers every drawn case.
- Automatic garbage collection.
- Automatic conversion of `system/<ds>/` folders.

### 5.1 File layout

```
system/<ds>/                         (= designSystems[].path; must lie inside a canvas group)
  design-system.tsx                  the Design system canvas            canvas-owned  · Plane A
  design-system.meta.json            its layout + dsPending              canvas-owned  · Plane A
  colors_and_type.css                working file (tokensCssRel)         companion-text · Plane B
  tokens.json                        working file: the token model       companion-text · Plane B (C1)
  components.json                    working file: V2-1.13 §5.4          companion-text · Plane B (C1)
  preview/_components.css            working file: the class contract    companion-text · Plane B
  preview/_ds.tsx                    optional @maude/ds overrides        code-module (unchanged)
  preview/*.tsx · *.css              specimens (unchanged)               canvas-owned
  README.md · SKILL.md · CONTRACT.md · assets/…  (unchanged)
  revisions/
    head.json                        pointer record                      companion-text · Plane B (C1 ext.)
    <id>.json                        immutable revision, id = 64 hex     companion-text · Plane B (C1 ext.)
    <id>.tokens.css                  deterministic sibling               companion-text · Plane B
    <id>.components.css              deterministic sibling               companion-text · Plane B
```

- **Converted:** a system is converted iff `<ds.path>/revisions/head.json` exists. Conversion refuses a system whose
  path is outside every `canvasGroups[].path`: its canvas would not be a canvas.
- **Working files** are the four files a revision freezes. Everything else in the folder is untouched by publishing.

### 5.2 Where the Design system canvas lives

**Path.** `<ds.path>/design-system.tsx`, with the usual `.meta.json`, `<slug>.annotations.json` and `_comments/`. It
is path-authoritative:

- The Canvases panel pins the canvas of every `config.designSystems[]` entry as the "Design system" row.
- ⌘K and the inspector's "Uses <name>" link resolve the same path.
- No meta flag marks it.

**UI name.** "Design system". With several systems in use, each canvas shows its system's display name: `tokens.json`
`$extensions["sh.maude"].label`, else `designSystems[].name` (CONTRACT §7).

**Source** (written once at conversion or creation, then edited like any canvas):

```tsx
/** @canvas Design system @ds <ds> */
import { DesignCanvas, DCArtboard } from "@maude/canvas-lib";
import { DSSection, Specimen } from "@maude/ds/board";   // S10 builds; the names are reserved here
export default function DesignSystem() {
  return (
    <DesignCanvas>
      <DCArtboard id="ds-brand" label="Brand" width={560} height={620}><DSSection kind="brand" /></DCArtboard>
      <DCArtboard id="ds-colour" label="Colour" width={1000} height={620}><DSSection kind="colour" /></DCArtboard>
      {/* ds-type · ds-space · ds-motion · ds-components · ds-patterns */}
      <DCArtboard id="ds-own-ui-kits-desktop-showcase" label="Desktop showcase" width={1440} height={900}>
        <Specimen src="preview/ui_kits-desktop-showcase.tsx" />
      </DCArtboard>
    </DesignCanvas>
  );
}
```

**Fixed artboard ids:**

- sections: `ds-brand`, `ds-colour`, `ds-type`, `ds-space`, `ds-motion`, `ds-components`, `ds-patterns`
  (sizes from 13 `SECS`);
- own artboards (showcases and specimens kept as they are, 29 `ds-edge-migrate`): `ds-own-<specimen slug>`;
- AI directions (14 `ds-make-directions`): `ds-dir-<a|b|c|…>`.

**Rendering.** `DSSection` renders from the working files plus `dsPending`. The canvas's tokens link is the working
CSS — the path-owned `canvasDesignSystems` branch, unchanged. Pending values are overlaid by a board-scoped
`<style>`, so the canvas shows the system "as edited". An outside change shows its new values marked (11).

**Several systems (A12):**

- one Design system canvas per system folder;
- `draft` is derived: no canvas uses it (§5.13);
- the default for new canvases = `defaultDesignSystem`, plus 24's folder rule (all canvases in a folder share a
  system → that one);
- an AI direction is a draft revision on the same system (`head.json` `drafts[]`), not a separate system (18
  `ds-many-switch` note).

**Conversion** (25 `ds-multi-migrate`, 29 `ds-edge-migrate`) is one action, with Restore in Version history. For
each system:

1. write `design-system.tsx` + meta (sections + own artboards for the specimens the dialog maps);
2. snapshot R0 from the working files;
3. write `head.json` with `{head: R0, base: R0}`.

Nothing is visually different: followers now render R0's siblings, which are byte-identical to the working CSS.
"The files stay exactly where they are."

### 5.3 The token model — `system/<ds>/tokens.json`

DTCG-compatible (`$type` / `$value`); Maude data sits under `$extensions["sh.maude"]`. A14 supersedes C1: the **CSS
schema name is the identity** (`css`), and designer names are display data.

```json
{
  "$schema": "https://raw.githubusercontent.com/1aGh/maude/main/apps/studio/schema/ds-tokens-v1.schema.json",
  "$extensions": { "sh.maude": {
    "schemaVersion": 1, "system": "studio-site", "label": "Studio site system",
    "themes": ["light", "dark"], "defaultTheme": "light", "rootClass": "studio-site", "colorSpace": "oklch",
    "source": "canvas",
    "fonts": [ { "family": "New York", "src": "assets/fonts/1a2b3c4d.woff2", "weight": 600, "style": "normal" } ] } },
  "color": {
    "accent": {
      "$type": "color", "$value": "oklch(0.50 0.190 255)",
      "$extensions": { "sh.maude": { "css": "--accent", "tier": 1, "label": "Accent",
        "modes": { "dark": "oklch(0.60 0.175 255)" },
        "valueNames": { "light": "Deeper azure", "dark": "Deeper azure" },
        "darkFollows": true } } },
    "fg": { "2": { "$type": "color", "$value": "…",
      "$extensions": { "sh.maude": { "css": "--fg-2", "tier": 1, "label": "Quiet", "modes": { "dark": "…" } } } } },
    "x": { "line-fine": { "$type": "color", "$value": "var(--x-line-mid)",
      "$extensions": { "sh.maude": { "css": "--x-line-fine", "tier": 3, "label": "Linka — jemná",
        "trashed": { "replacement": "--x-line-mid", "at": "2026-10-09T10:00:00Z",
                     "by": { "kind": "person", "name": "Tereza" }, "previous": { "light": "…", "dark": "…" } } } } } }
  },
  "dimension": { "radius": { "md": { "$type": "dimension", "$value": "10px",
    "$extensions": { "sh.maude": { "css": "--radius-md", "tier": 1, "label": "Corner M" } } } } },
  "palette": { "1": { "$type": "color", "$value": "…",
    "$extensions": { "sh.maude": { "css": "--palette-1", "tier": 2, "kind": "palette", "index": 1, "label": "Yellow",
                                   "modes": { "dark": "…" } } } } },
  "alias": { "w-semibold": { "$value": "{fontWeight.weight.semibold}",
    "$extensions": { "sh.maude": { "css": "--w-semibold", "alias": true, "canvasUse": "autofix" } } } }
}
```

**Group paths.** The DTCG path is the CSS name without `--`, split at its first segment into a group. The group
follows the registry type: `color`, `dimension`, `duration`, `cubicBezier`, `fontFamily`, `fontWeight`, `number`,
`shadow`. Tier-2 and Tier-3 names go to their own groups (`palette`, `display`, `x`, …), and native aliases to
`alias`. Two tokens may never share a `css`.

**Fields** (in `$extensions["sh.maude"]` unless noted):

| Field | Meaning |
| --- | --- |
| `css` | the identity: the CSS custom-property name |
| `tier` (1 / 2 / 3), `kind`, `index`, `role`, `pairsWith` | from the V2-1.13 registry |
| `label` | the designer's name for the token ("Accent", "Klubová zelená", "Corner M"); ≤ 64 printable chars |
| `valueNames.<theme>` | the colour's own name ("Azure", "Deeper azure", "Sea blue"); ≤ 64 printable chars |
| `$value` (DTCG) | the default theme's value |
| `modes.<theme>` | every other theme's value |
| `darkFollows: true` | tells the editor to recompute dark when light changes (6 `ds-edit-colour`); no rule is stored |
| `locked: true` | a frozen brand value (5 `ds-board-gator`); the editor refuses changes until it is unlocked |
| `trashed` | a tombstone: `{replacement, at, by, previous}` (§5.11 e). The CSS keeps `--name: var(--replacement)`, so canvases follow the replacement with no source edits. Tier-1 roles can't be trashed |
| `alias: true` | a native name kept for production code, with its v1 target as a DTCG `{group.path}` reference |

Value rules:

- **Concrete values.** Every value is stored per theme, never as a computed rule.
- **Exact text.** Values are the CSS value text exactly as the CSS declares it (round-trip safe), including `var()`
  and `color-mix()`. A DTCG `{group.path}` reference is used only for a declaration that is exactly `var(--name)`.
- **Labels and value names are data** (DDR-172 D8). An agent reads them as content and never as instructions.

**Determinism.** Keys are sorted; 2-space indent; LF; one trailing newline.

**`source`:**

- `"css"` (phase α): written by `maude design ds-check --emit` from the CSS. It keeps existing `label` /
  `valueNames` / `locked` values, matched by `css`.
- `"canvas"` (phase β): written by the app at each publish.

### 5.4 The source of truth, per system (A15)

| Phase | When | Source | `colors_and_type.css` | `tokens.json` | Canvases render |
| --- | --- | --- | --- | --- | --- |
| α — not converted | no `revisions/head.json` | the CSS (+ `_components.css`) | written by hand, agents, `import-tokens`, `setup-ds` | emitted by `ds-check --emit` (setup-ds, `maude migrate v2` `ds.tokens`), `source: "css"` | the live working CSS, as today |

- **Outside edits in β are allowed** — the files are the API. They arrive as a review (§5.10, §5.11 a).

### 5.5 The generator → `colors_and_type.css` and `preview/_components.css`

`apps/studio/ds/generate.ts`:

```ts
export function generateTokensCss(prev: string | null, model: TokenModel, cfg: { rootClass: string;
  themes: string[]; defaultTheme: string }): string;                       // deterministic, pure
export function generateComponentsCss(prev: string, edits: ComponentEdits): string;
export function emitTokensJson(model: TokenModel): string;                  // §5.3 bytes
export function parseSystem(files: SystemFiles): TokenModel;                 // css-scan (V2-1.13 §5.1) + tokens.json labels
```

**Patching** (`prev` present — every converted, hand-authored file). The generator follows DDR-172 D7: a block is
located top-level only and comment- / string-aware, a value is replaced span-only, and a block that can't be
located is a hard refusal.

- A changed token gets its value replaced in each theme's top-level block where it is declared. An invariant token
  is patched in the rule where it is declared.
- A token new to a block is inserted before that block's closing `}`. The block's selector list carries
  `.ds[data-theme="<t>"]` (V2-1.13 §5.3.12).
- A trashed token's value becomes `var(<replacement>)`.
- Comments, order, `@font-face`, `@media (prefers-reduced-motion)` and non-token rules stay byte for byte.
- A block that can't be located refuses the publish: 409 `{code: "ds-generate-block"}`, nothing written.

**Fresh** (`prev === null` — a system made on the canvas, 13–17). The generator emits the template's block structure
from `core/colors_and_type.css.tpl`:

- one block per theme;
- the invariant block;
- the reduced-motion block (`1ms` for every `--dur-*`, including `--dur-signature-*`).

Values come from the model. DDR-043 holds: the template contributes structure only.

**Components.** A component master edit is a declaration patch `{selector, property, value}`, applied inside the
top-level rule whose selector list matches exactly. A missing declaration is appended before that rule's `}`; a
missing rule is appended at the end of the file.

**Invariants:**

- **G1.** `parseSystem(generate(prev, model)) ≡ model` for every token and theme.
- **G2.** `generate(prev, parseSystem(prev)) === prev` byte for byte, so an empty publish writes nothing.

### 5.6 Revisions — format, hash rule, siblings

`revisions/<id>.json` (schema `ds-revision-v1.schema.json`):

```json
{
  "files": {
    "colors_and_type.css":     { "sha256": "<64 hex>", "text": "…" },
    "components.json":         { "sha256": "<64 hex>", "text": "…" },
    "preview/_components.css": { "sha256": "<64 hex>", "text": "…" },
    "tokens.json":             { "sha256": "<64 hex>", "text": "…" }
  },
  "format": "maude.ds-revision",
  "schemaVersion": 1,
  "system": "studio-site",
  "v": 1
}
```

```json
{ "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://raw.githubusercontent.com/1aGh/maude/main/apps/studio/schema/ds-revision-v1.schema.json",
  "type": "object", "additionalProperties": false, "required": ["format", "v", "schemaVersion", "system", "files"],
  "properties": {
    "format": { "const": "maude.ds-revision" }, "v": { "const": 1 }, "schemaVersion": { "const": 1 },
    "system": { "type": "string", "pattern": "^[a-z][a-z0-9-]{0,63}$" },
    "files": { "type": "object", "additionalProperties": false, "minProperties": 1,
      "patternProperties": { "^(?!/)(?!.*\\.\\.)[A-Za-z0-9_][A-Za-z0-9 ._/-]{0,255}$": {
        "type": "object", "additionalProperties": false, "required": ["sha256", "text"],
        "properties": { "sha256": { "type": "string", "pattern": "^[0-9a-f]{64}$" }, "text": { "type": "string" } } } } } } }
```

**The `files` map.** Keys are relative to `<ds.path>`. The tokens key is the system's `tokensCssRel` relative to
`<ds.path>` (usually `colors_and_type.css`). A file missing at snapshot time is absent from the map, never `null`.

**Hash rule.** `id = lowercase hex sha256(UTF-8(canonical(body)))`. `canonical(v)` is defined as:

- objects: keys sorted by UTF-16 code unit at every depth, no whitespace;
- strings and numbers: serialized exactly as `JSON.stringify` does;
- arrays: in order.

The body carries no time, author, parent or message. The same content therefore gives the same id and the same
bytes on every peer.

**On-disk bytes** = the same sorted keys, 2-space indent, LF, one trailing newline.

**Integrity** (every reader, every time):

- `sha256(canonical(parse(file))) === <id in the filename>`, and every `files[k].sha256 === sha256(files[k].text)`;
- otherwise the revision is **invalid**: never rendered, never repaired, reported in Diagnostics.

A hub- or peer-supplied revision is untrusted (DDR-054). The integrity check is what makes it safe to render, and
it grants no new capability: the same peer could already push the live CSS.

**Siblings:**

- `<id>.tokens.css` = the tokens entry's `text`, byte for byte;
- `<id>.components.css` = `files["preview/_components.css"].text`.

They are never authoritative. A peer — or the studio at boot — that holds a valid `<id>.json` and a missing or
mismatched sibling rewrites the sibling. The bytes are identical, so Plane B treats it as a no-op.

**Immutability.**

- A revision file is never rewritten.
- A future revision format is new files with a new `v`. V2-1.12 R7 does not apply: these files are only ever added.
- A reader that meets an unknown `v` treats the revision as unreadable and falls back (§5.8).

**Size.** ≤ 2 MiB per revision (the `TOKENS_MAX_BYTES` precedent). A larger publish is refused with 413.

**Write order** (every writer):

1. `<id>.json`;
2. the siblings;
3. the working files;
4. `head.json`, last.

Each file is written tmp + rename (DDR-172 D7).

**Garbage collection.** Never automatic in v2.0. `maude design ds revisions --prune [--dry-run]` (owner on a hub)
moves revisions older than 30 days to `_trash/ds-revisions/<ds>/` when nothing references them. A reference is any
of:

- a `dsRev` in any meta;
- a `data-ds-rev` attribute in the usage index;
- `head`, `base` or `drafts[]`;
- the last 20 `log` entries;
- `library.upstreamHead`.

### 5.7 `revisions/head.json`

```json
{
  "format": "maude.ds-head", "v": 1, "system": "studio-site",
  "head": "<id>", "base": "<id>",
  "drafts": [ { "rev": "<id>", "label": "Warm paper", "direction": "b", "by": { "kind": "ai" }, "at": "2026-10-09T10:00:00Z" } ],
  "log": [ { "rev": "<id>", "parent": "<id>", "action": "publish", "at": "2026-10-09T10:02:00Z",
             "by": { "kind": "person", "name": "Michal" }, "summary": "Accent → Deeper azure",
             "updated": 4, "leftOut": 1 } ],
  "library": null
}
```

**Fields:**

- `head` — the published revision; followers render it. It is `null` only while a system is being made on the
  canvas (13–17: only `drafts`, no canvas uses it yet). A system whose head is `null` renders its working files.
- `base` — the last revision the app wrote to the working files.
- `log` — newest first, at most 50 entries; Version history keeps the rest.
  - `action` ∈ `publish keep pick convert make library upgrade restore`;
  - `by.kind` ∈ `person ai agent import peer`;
  - `by.name` is display only.
- `library` — §5.14.

**How the pointers move.**

- publish / convert / make / library / upgrade: head = base = the new revision.
- Keep / pick: base moves; head stays.
- Undo: rewrites the files from base; base stays.

**Writers.** Only the app's DS engine (`apps/studio/ds/engine.ts`, behind the routes and verbs of §5.12). Never a
hand edit — the hook (V2-1.18) refuses an agent edit of `head.json`.

**Concurrency.** `head.json` is one whole file on Plane B. Two Macs publishing from the same head at once end with
one copy renamed aside (DDR-226). The Design system canvas then shows "Published in two places" — a pick between the
two head revisions, drawn like 12. "Use this" is a publish whose `expectHead` is the surviving file's head. Nothing
is lost: both revisions exist.

### 5.8 Which revision a canvas renders

The server extends `buildIndexData` with `canvasDsRevs` (canvas → `dsRev`) and `systemHeads` (system → head id), and
`canvasUrl` resolves:

| Canvas | System | `tokens=` / `components=` |
| --- | --- | --- |
| specimen `<ds.path>/preview/*` | any | working files (today's path-owned branch) |
| the Design system canvas | converted | working files + the `dsPending` overlay |
| any other canvas, no `dsRev` | converted | `revisions/<head>.tokens.css` / `revisions/<head>.components.css` |
| any other canvas, `dsRev = R` | converted | `revisions/<R>.tokens.css` / `.components.css` |
| any canvas | not converted | working files (today) |
| previewing another system or a direction (18) | — | the session-only URL override `?dsPreview=<ds>` or `<ds>@<id>`; never stored |

**Fallback chain** when a revision is missing or invalid: `dsRev` → head → working files. The canvas shows the quiet
"Waiting for <peer>'s Mac" state (CONTRACT §7; DDR-226 `referenced-but-unoffered`) and re-renders when the revision
arrives.

**Element pins.** These implement 10 `ds-edit-instance`: Update brings the new corners to one instance, and "a new
one placed with Component (⇧I) arrives current". A canvas element may carry `data-ds-rev="head"` or
`data-ds-rev="<id>"`.

- **Loading.** For each distinct value other than the canvas's own revision, the shell loads that revision's
  siblings and rewrites them through the CSSOM:
  - **Token rules** (`:root`, `.ds[data-theme=t]`, `.<rootClass>[data-theme=t]`) are declared on the scope element:
    `:where([data-theme="t"]) [data-ds-rev="<v>"], [data-theme="t"][data-ds-rev="<v>"]`.
  - **Class rules** get `:is([data-ds-rev="<v>"], [data-ds-rev="<v>"] *)` appended to the last compound, before any
    pseudo-element. That adds one attribute of specificity, so the pinned rule beats its unpinned twin.
- **Writers:**
  - ⇧I on a left-out canvas adds `data-ds-rev="head"` to the new instance.
  - Update on one instance adds `data-ds-rev="head"` to it.
  - Updating the whole canvas (deleting `dsRev`) strips the now-redundant `data-ds-rev="head"` attributes.
  - Detach is S2: the instance stops being a component.
- **Exports.** The attribute is part of the design, so exports — which use the same shell — render it identically.

**Live updates.** When head moves, followers swap their two links through the shell's existing CSS swap. 8
`ds-edit-review` says "Tereza's open Pricing updates when she next looks at it". So in a window of anyone other than
the publisher, the swap waits for the next visibility change, canvas switch or artboard move. Present already defers
changes this way (A8).

### 5.9 Pending edits — `dsPending` in `design-system.meta.json`

A top-level key (V2-1.12 R6), on Plane A, merged per token:

```json
"dsPending": {
  "base": "<id of base when the oldest entry was made>",
  "tokens": {
    "--accent":      { "light": "oklch(0.50 0.190 255)", "dark": "oklch(0.60 0.175 255)",
                       "valueNames": { "light": "Deeper azure" }, "darkFollows": true,
                       "by": { "kind": "person", "id": "<collab id>", "name": "Michal" }, "at": "2026-10-09T09:52:00Z" },
    "--x-line-fine": { "trash": { "replacement": "--x-line-mid" }, "by": { "kind": "person", "name": "Tereza" }, "at": "…" },
    "--x-yearly-blue": { "add": { "tier": 3, "type": "color", "label": "Yearly blue" }, "light": "…", "dark": "…",
                         "by": { "kind": "ai" }, "at": "…" }
  },
  "components": {
    "Button": { ".btn": { "border-radius": { "value": "var(--radius-md)", "by": { "kind": "person", "name": "Michal" }, "at": "…" } } }
  }
}
```

**Values** follow §5.3: concrete, per theme. An entry equal to base's value is dropped.

**Concurrency.** Edits to different tokens on two Macs merge. The same token at the same time is a `mergeJson`
base-conflict: the later proposal is refused and the editor re-reads. There is no silent overwrite.

**The AI path (A13).** Claude proposes a change by adding an entry. A human then publishes it through "Update N
canvases". The PostToolUse check (V2-1.18) validates every entry against the registry types (V2-1.13 §5.3.1) and
refuses unknown names. `dsPending` is shared by everyone editing the canvas, as drawn ("Tereza is on Type; nothing
locks").

### 5.10 Derived states (computed, never stored)

All five states apply to a converted system:

- **`outside`.** The set of working-file sha256s differs from `base`'s `files[*].sha256`. It is evaluated only after
  `<ds.path>/` has been **quiet for W = 5 s**: no fs events and no inbound file-plane delivery for that prefix.
  - The quiet window absorbs Plane B's lack of cross-file order: `head.json` may land before or after the working
    files.
  - Because `base` is versioned, a peer that receives a publish compares against the same base the publisher wrote.
    It gets **no spurious review** (I #4).
- **`outsideChanges[]`.** The token-level diff base → working, per theme. Parsing uses `ds/css-scan.ts` per
  top-level block, `tokens.json` labels, and component declarations by selector + property. `otherChanges[]` holds
  non-token byte changes per file (comments, new rules); they are never silent.
  - **Attribution** goes to per-Mac `_state/ds-outside/<ds>.json`:
    - `agent` — the A13 `edit.touched` hook named the file ("Claude Code");
    - `git` — HEAD moved and the file differs; the author of the last commit that touched it ("Jonas · git pull");
    - `peer` — a file-plane delivery, using the journal row's source;
    - else `unknown`.
- **`pending`** = the `dsPending` entries.
- **`waiting`** = tokenDiff(head → base) ∪ pending. It drives the DS bar's "N changes waiting".
- **`conflicts`** = tokens present in both `pending` and `outsideChanges` with different values. Equal values
  auto-resolve: base := snapshot(working), and the entry is dropped.
- **`leftOut(canvas)`** = `meta.dsRev` is present and differs from head. It shows the update-available dot.

### 5.11 Review flows — data and effects

Every effect below is **one action**: one Version-history entry, one ⌘Z (V2-1.5). Read-only people see the states
with no actions; the server refuses the routes (rule 12).

**(a) Outside change** (11 `ds-truth-outside`):

```json
{ "kind": "ds-outside", "system": "studio-site", "base": "<id>",
  "files": [ { "path": "colors_and_type.css", "source": { "kind": "agent", "name": "Claude Code" }, "at": "2026-10-09T09:56:00Z" } ],
  "changes": [ { "css": "--fg-2", "label": "Quiet", "theme": "light", "before": "oklch(…)", "after": "oklch(…)" },
               { "css": "--radius-md", "label": "Corner M", "before": "10px", "after": "12px" } ],
  "otherChanges": [ { "path": "colors_and_type.css", "count": 1 } ],
  "conflicts": [] }
```

- **Keep** → write revision K = snapshot(working); `head.json` base = K; log `keep`. Canvases still render head
  until "Update N canvases".
- **Undo** → rewrite each changed working file from base's `text`; base is unchanged.

**(b) Conflict pick** (12 `ds-truth-conflict`):

```json
{ "kind": "ds-conflict", "system": "studio-site", "css": "--accent", "label": "Accent",
  "canvas": { "light": "…", "valueName": "Deeper azure", "by": { "kind": "person", "name": "Michal" }, "at": "…" },
  "file":   { "light": "…", "valueName": "Sea blue", "source": { "kind": "git", "name": "Jonas" }, "at": "…" },
  "canvasesKeep": "Azure" }
```

- **"Use this" (canvas)** → patch the working files to the pending value (§5.5), revision K, base = K, drop the
  pending entry.
- **"Use this" (file)** → base = snapshot(working), drop the pending entry.
- The value not picked stays in Version history. Canvases keep head throughout.

**(c) Update N canvases** (8 `ds-edit-review`, 9 `ds-edit-master` by folder, 7 `ds-edit-reach`) — the request body
of `POST /_api/ds/publish`:

```json
{ "system": "studio-site", "expectHead": "<id>",
  "changes": [ { "css": "--accent", "label": "Accent", "before": { "light": "…", "dark": "…" }, "after": { "light": "…", "dark": "…" },
                 "contrast": { "light": 5.6, "dark": 4.8 } } ],
  "canvases": [ { "path": "ui/Homepage.tsx", "folder": "ui", "state": "follows", "places": 14, "openBy": [], "ticked": true },
                { "path": "ui/Landing page.tsx", "folder": "ui", "state": "follows", "places": 9, "ticked": false } ] }
```

- **Defaults.** Followers are ticked. Canvases already left out are unticked ("keeps <old>"). `pinned` and `blocked`
  canvases (V2-1.13 §5.6) are unticked with their reason. "By folder" groups by `folder`. `contrast` is information
  only.
- **Preconditions.** `outside = ∅`, `conflicts = ∅` and `expectHead == head`. Otherwise the route answers 409
  `{code: "ds-outside-unreviewed" | "ds-conflict" | "ds-head-moved"}`.
- **Effect, in order** (one action):
  1. R = snapshot(generate(base files, all waiting changes)). Write R and its siblings.
  2. Write the working files.
  3. Unticked followers: `meta.dsRev = <old head>`. Ticked canvases that had a `dsRev`: delete it and strip their
     `data-ds-rev="head"` attributes.
  4. Delete the included `dsPending` entries.
  5. `head.json`: head = base = R; log `publish {summary, updated, leftOut}`.
- **Cancel** deletes the pending entries the review covered ("Cancel puts the swatch back").
- **⌘Z after Update** undoes the whole action; R remains, unreferenced.
- All waiting changes publish together: partial publishes are not drawn (§9 Q2).

**(d) Update-available dot** (10 `ds-edit-instance`):

```json
{ "kind": "ds-update-available", "canvas": "2026/combine/Combine-letak-registrace.tsx", "dsRev": "<id>", "head": "<id>",
  "diff": [ { "component": "Button", "label": "Tlačítko", "change": "corners 2 → 6" } ],
  "leftOutBy": { "kind": "person", "name": "Michal" }, "leftOutAt": "…", "leftOutWith": "2026/combine" }
```

- `diff` = the revision diff dsRev → head.
- `leftOutBy`, `leftOutAt` and `leftOutWith` come from the `log` entry whose `parent` equals `dsRev`, plus the
  folders of every canvas still at `dsRev`.
- **Update** (instance) → `data-ds-rev="head"` on it. **Update** (the canvas, from its menu) → delete `meta.dsRev`.
  **Detach** → S2.

**(e) A token moved to the trash** (27 `ds-edge-trash`): a pending `trash` entry plus a publish with every follower
ticked; the dialog is the review.

- `tokens.json` keeps a tombstone, and the CSS keeps `--name: var(--replacement)`.
- The Trash lists `{kind: "token", system, css, label, replacement, at, by}`, derived from the tombstones (S1's
  Trash index).
- **Restore** is a publish that puts `previous` back.
- **Clear out** (owner) deletes the tombstone record but keeps the alias line while the usage index shows a
  reference.

**(f) Library update** — §5.14.

**(g) Convert folders** (25 / 29): `{ "systems": [ { "name": "alligators", "path": "system/alligators", "canvases": 87,
"default": true, "to": "design-system" }, { "name": "alligators-2023", "path": "system/alligators-2023", "canvases": 0,
"to": "draft" } ] }`. The effect is §5.2's conversion, for every system, in one action.

**(h) Switch canvases to another system** (A12, 23 `ds-multi-switch`) — V2-1.13 §5.7: rewrite `meta.designSystem`,
delete `meta.dsRev` and the `data-ds-rev` attributes, write `meta.dsPairing`.

**Studio routes.** Main origin, privileged, never canvas-safe (a patch request for the route table):

- `GET /_api/ds/state?ds=` — head, base, drafts, waiting, outside, conflicts, left-out counts;
- `POST /_api/ds/publish`;
- `POST /_api/ds/outside {ds, action: "keep" | "undo"}`;
- `POST /_api/ds/pick {ds, css, use: "canvas" | "file"}`;

**CLI** — `maude design ds <sub>` (DDR-062). The verb calls the live studio's loopback route when `_server.json`
names one, and otherwise runs the same engine module in-process.

| Sub | Permission tier | Does |
| --- | --- | --- |

| `revisions list <ds>` · `revisions --prune [--dry-run]` | auto · card | §5.6 |

**Files Claude edits directly:**

- `dsPending` — to propose a change;
- the working files — they arrive as an outside-change review;
- the canvas TSX, including `data-ds-rev` on an element it places.

Claude never edits `head.json`, the revision files or `dsRev` by hand; it uses the verbs for those. The hook refuses
the hand edits.

**Server-side permissions** (rule 12):

- Publish, Keep, Undo, pick, convert and library update need edit rights on the whole project. A canvas-scoped grant
  is not enough (V2-1.7 / V2-1.16).
- Clearing a token out of the trash is owner-only (A6).
- A linked-library system refuses every write except library update and unlink.

### 5.13 The usage index (hosted by V2-1.17)

Per project and per Mac; derived and rebuildable. Path `_cache/index/ds-usage.json`. `_cache` is already in all four
DDR-115 lists, so there is no new class.

```json
{ "format": "maude.ds-usage", "v": 1, "builtAt": "2026-10-09T10:00:00Z",
  "sources": { "ui/Homepage.tsx": { "sha256": "<64 hex>" } },
  "systems": { "studio-site": {
    "draft": false,
    "canvases": { "ui/Homepage.tsx": { "follows": true, "dsRev": null, "elementPins": { "head": 0 },
                  "state": "switchable", "pins": { "literal-colour": 2 } } },
    "tokens": { "--accent": { "ui/Homepage.tsx": { "places": 14, "direct": 9, "viaComponents": 5,
                                                  "artboards": { "desktop": 9, "mobile": 5 } } } },
    "components": { "Button": { "ui/Homepage.tsx": { "instances": 3, "artboards": { "desktop": 2, "mobile": 1 } } } } } } }
```

- **`places`** = the direct `var(--name)` uses in the canvas's sources (V2-1.13 §5.7), plus the instances of
  components whose `_components.css` rules reference the token. The component → token map is derived from the
  system's CSS.
- **Artboard attribution** uses `DCArtboard id=` line ranges (the V2-1.5 rule).
- **`state` and `pins`** come from `ds-check` (V2-1.13 §5.6); this is where pins live, never in meta.
- **Incremental:** one canvas save re-scans that canvas; a system file change re-derives the component → token map.
- **Consumers:**
  - "Used in N canvases" · Show (6, 7);
  - the review's `places`;
  - ⌘K "used in 88 canvases" (2);
  - draft detection (21, 25);
  - the trash dialog's "40 canvases use it" (27);
  - the switch dialog (23);
  - the pruner (§5.6).
- **ACL.** Only canvases this Mac holds are indexed. A canvas-scoped member's checkout holds only their canvases, so
  counts never reveal others; V2-1.16 confirms the delivery side.

### 5.14 Team libraries (19 `ds-many-library`, 20 `ds-many-linked`)

**The library** is a system inside a cloud project. **A linking project** holds a full local copy:

- the working files, materialised from the linked head;
- `revisions/<id>.*`, copied in with the same ids (content addressing makes them byte-identical);
- a `head.json` `library` record:

```json
"library": { "hub": "https://alligators.cloud.maude.sh", "project": "<project id>", "system": "alligators",
             "label": "Alligators brand system", "linkedAt": "…", "linkedBy": { "kind": "person", "name": "Jonas" },
             "upstreamHead": "<id>", "checkedAt": "…" }
```

**Hub API** (S9 and the hub lane; capability `ds-library` in `/health`):

- `GET /api/projects/:id/v1/ds/:system/head` → `{head, log}` (the last 20 log entries);
- `GET /api/projects/:id/v1/ds/:system/revisions/:rev` → the revision JSON. The receiver verifies it (§5.6) before
  writing anything.
- **Authorization:** a read grant scoped to that system's `revisions/**` and `head.json`. Users of a library need
  not be members of its project ("others use it"). V2-1.7 / V2-1.16 define the grant; it reveals nothing else.

**Update:**

1. Check on project open, and every 30 min while online.
2. When `upstreamHead ≠ head`: "N updates waiting".
3. The review `{changes: diff(head → upstream), by, at}` (19).
4. Update: copy the revision in, materialise the working files, head = base = upstream, log `library`.
5. Then this project's own "Update N canvases" review (§5.11 c; unticked = left out at the old head).

**View only.** The Design system canvas renders read-only, and the studio refuses publish, pending, Keep and pick
for a linked system. An outside edit to its working files offers only Undo (re-materialise from head). The state
word is "Linked library — view only" (C18).

**Unlink** removes `library`; the copy becomes an ordinary local system, and its revisions stay.

**"Used by N projects."** The hub counts the distinct projects that fetched `head` in the last 90 days (S9).

### 5.15 Sync and peer behaviour

| Path | Class | Plane | Concurrent writes |
| --- | --- | --- | --- |
| `<ds>/design-system.tsx`, `.meta.json` (incl. `dsPending`) | canvas-owned (the existing group rule) | A | body CRDT; meta merged per key; the same token at once → base-conflict |
| any canvas `.meta.json` `dsRev`, `dsPinned`, `dsPairing` | canvas-owned | A | merged per key |
| `<ds>/colors_and_type.css`, `<ds>/preview/_components.css` | companion-text (existing) | B | renamed aside → seen as an outside change |
| `<ds>/tokens.json`, `<ds>/components.json` | companion-text (**C1**, V2-1.12 §5.7) | B | renamed aside |
| `<ds>/revisions/<64 hex>.json` | companion-text (**C1, extended**) | B | none: immutable, content-addressed, same-hash no-op |
| `<ds>/revisions/<64 hex>.tokens.css`, `.components.css` | companion-text (existing `.css` rule) | B | none: deterministic bytes |
| `<ds>/revisions/head.json` | companion-text (**C1, extended**) | B | renamed aside → "Published in two places" |

**Classifier entry.** It lands in both copies in the same commit, with the parity test
(`sync/file-membership.ts` and `apps/hub/src/file-membership.mjs`). Inside a canvas group, at exactly depth
`<group>/<ds>/…`:

- `<group>/<ds>/tokens.json`
- `<group>/<ds>/components.json`
- `<group>/<ds>/revisions/head.json`
- `<group>/<ds>/revisions/<64 lowercase hex>.json`

all become companion-text. Everything else stays default-closed. Receivers re-classify against their own tree, and
the revision reader re-checks integrity.

**Cross-plane order.** Metas (Plane A) can arrive before revisions or `head.json` (Plane B). The §5.8 fallback chain
and the §5.10 quiet window handle it; no write depends on arrival order.

**Emptiness never beats content** (DDR-223). A 0-byte or missing revision never replaces a valid one. The only
deletion is an explicit prune, and it goes through the owner tombstone path.

**v1 peers** (V2-1.12). A format-2 project is read-only for them, and they render the working files. Their classifier
materialises the `.css` siblings and ignores the JSON (V2-1.12 F3). A converted system looks the same to them except
while an outside change waits for review.

**Cloud cells.** The studio child runs the same code. Revisions ride the file plane with CAS durability (DDR-226
§6). The config door must carry `rootClass` and `themes` (V2-1.13 P-5).

**Git and Syncthing.** Everything is plain files. Two Syncthing peers that write the same revision produce identical
bytes, so there is no `.sync-conflict` copy.

### 5.16 Versions and fields (V2-1.12 rules applied)

**File versions:**

- `tokens.json` `$extensions["sh.maude"].schemaVersion: 1`;
- `components.json` `schemaVersion: 1`;
- revisions `v: 1` (immutable — only ever added);
- `head.json` `v: 1` (additive fields only, R1).

**Meta keys** (top-level, R6):

- `dsRev` — 64 hex, interpreted under `meta.designSystem`;
- `dsPending` — on the Design system canvas only;
- V2-1.13's `dsPinned` and `dsPairing`.

Patch request: add `dsPending` to V2-1.12 §5.1's reserved table (owner V2-1.6). `dsRev` is already there.

**`data-ds-rev`** is an additive attribute in canvas TSX, and display-ignorable for v1 (R2): a v1 renderer ignores it
and shows head, so only the pinned instance's old values differ.

**`maude migrate v2`.** The `ds.tokens` step emits `tokens.json` with `source: "css"`. Conversion to a canvas is never
a migration step (it needs consent). The reverse step removes what the forward step emitted. Revisions never exist
before a conversion.

- `_cache/index/ds-usage.json`;
- `_trash/ds-revisions/**`.

All of these fall under the existing `_state`, `_cache` and `_trash` prefixes in the four DDR-115 lists. The only
classifier change is the positive Plane-B entry in §5.15.

## 6. Evidence

Prototype `revision-proto.mjs` is in the spike scratchpad. It is read-only and run through
`scripts/v2-test-lane.sh -- node …`. It builds §5.6 revisions from the real working files:

| | maude-v2 | maude |
| --- | --- | --- |
| id (sha256 of the canonical body) | `e516e657…bd5088` | `53b4a5fc…091d75` |
| deterministic (two builds → same id, same bytes) | yes | yes |
| an edit to one token value changes the id | yes (`--radius-md` 10 → 12 px) | — (pattern not present) |
| revision file bytes (pretty) | 27,785 | 24,134 |
| siblings (tokens + components CSS) | 26,765 | 23,210 |

A publish therefore adds about 55 KB of text per system — well under the 2 MiB cap.

The revision JSON Schema (§5.6) compiles under Ajv 2020-12 strict mode, and §5.6's example revision validates against
it (`v2-1-13/schema-compile.cjs`, run through the lane).

**Code reads:**

- **Plane B is whole-file with conflict-aside, and has no cross-file order** (DDR-226 §1–§2) → content-addressed
  revisions plus a quiet window.
- **`mergeJson` merges objects per key and refuses arrays without `id`** → `dsPending` is a map keyed by CSS name,
  never an array.
- **The canvas origin serves `.css` but not `.json`** (`CANVAS_ASSET_EXTS`) → siblings instead of a new route.
- **`.json` is default-closed in `classifyProjectFile`** → the C1 entries are required, or revisions never reach a
  peer.
- **The hub config door drops `rootClass` / `themes`** → `tokens.json` carries them (§5.3) for cells.

**Census** (V2-1.13 §6). No canvas in this repo uses a Tier-1 name its system lacks. Converting maude or maude-v2
would therefore render identically from R0: R0's siblings are byte-copies of the working files.

## Decisions

- `decision:maude/v2-1.6-ds-canvas-path`
  - **What:** the Design system canvas is a real canvas at `<ds.path>/design-system.tsx` (+ meta), found by its path.
    Fixed section artboard ids `ds-brand … ds-patterns`, own artboards `ds-own-*`, directions `ds-dir-*`. It renders
    the working files plus `dsPending`. Conversion writes it plus R0 plus `head.json` in one action.
  - **Why:** comments, annotations, sync Plane A, Version history and ⌘K all already key off canvas paths (A9, A12).
  - **Rejected:** a virtual (fileless) canvas; a meta flag to mark it.
- `decision:maude/v2-1.6-content-addressed-revisions`
  - **What:** `revisions/<id>.json` with `id = sha256(canonical(body))`. The body is pure content: the four working
    files' text plus their sha256s, and no time or author. Two deterministic `.css` siblings; readers verify
    integrity; immutable; no automatic GC; write order revision → siblings → working → `head.json`.
  - **Why:** identical content gives identical bytes on every peer (Plane B no-op, no conflict copies). It works
    without git (I #4). The canvas origin and the exporters serve `.css` unchanged.
  - **Rejected:** git pinning; metadata inside revisions; JSON-only revisions behind a new canvas route.
- `decision:maude/v2-1.6-head-base-pointer`
  - **What:** versioned `revisions/head.json` holds `head` (published; followers render it), `base` (the last
    revision the app wrote; the outside-change baseline), `drafts` (AI directions), a 50-entry `log` and `library`.
    The app engine is its only writer.
  - **Why:** peers must agree on the baseline, or synced generated files raise spurious reviews (I #4).
  - **Rejected:** a per-Mac `_state` base; pointers in the DS canvas meta.
- `decision:maude/v2-1.6-followers-render-head`
  - **What:** for a converted system, a following canvas renders `revisions/<head>.*.css` and a left-out canvas its
    `dsRev`. Specimens and the DS canvas render the working files. An unconverted system renders the working files
    exactly as today.
  - **Why:** 11 `ds-truth-outside` — canvases follow an outside edit only after Keep plus "Update N canvases".
  - **Rejected:** followers rendering the live working file.
- `decision:maude/v2-1.6-pending-on-ds-canvas-meta`
  - **What:** in-app and AI-proposed token / component edits wait in `dsPending` (DS canvas meta, Plane A, merged per
    token). Publishing writes the files.
  - **Why:** 12 `ds-truth-conflict` draws the canvas value and the file value apart while canvases keep head;
    edits by different people merge per token.
  - **Rejected:** writing pending values straight into the working files.
- `decision:maude/v2-1.6-per-canvas-pins-with-element-override`
  - **What:** the pin unit is the canvas (`meta.dsRev` = the head it was following). `data-ds-rev="head" | <id>` on
    an element covers per-instance Update and "⇧I arrives current", through CSSOM-scoped revision CSS. The update
    dot means `dsRev ≠ head`.
  - **Why:** B9 per-canvas leave-out; 10 `ds-edit-instance`.
  - **Rejected:** per-token or per-component pins composing revisions; canvas-local frozen copies.
- `decision:maude/v2-1.6-token-model`
  - **What:** `tokens.json` is DTCG-compatible. The CSS schema name (`css`) is the identity; `label` and
    `valueNames` hold designer names (A14 supersedes C1). Concrete per-theme values, `darkFollows`, `locked`, and a
    `trashed` tombstone that aliases the replacement in CSS. `source` is `css` (phase α, emitted) or `canvas`
    (phase β, published).
  - **Why:** A14 / A15, and the swatch, label and value-name copy canvas 13 shows.
  - **Rejected:** designer names as keys (C1).
- `decision:maude/v2-1.6-patching-generator`
  - **What:** CSS is generated by patching the existing file with DDR-172 D7's theme-block discipline: value spans
    only, inserts before the block's `}`, a hard refusal when a block can't be located. A system made on the canvas
    is emitted from the template's structure. Round-trip invariants G1 / G2.
  - **Why:** hand-authored files keep their comments and structure, and an empty publish writes nothing.
  - **Rejected:** regenerating the whole CSS from `tokens.json`.
- `decision:maude/v2-1.6-usage-index-cache`
  - **What:** the per-Mac derived index `_cache/index/ds-usage.json` (V2-1.17 hosts it). `places` counts direct uses
    plus uses via components, attributed to artboards; it holds the canvas states and pins.
  - **Why:** canvas 13's "Used in N canvases", Show, the review counts and draft detection — without versioned
    churn, and with no new runtime class.
  - **Rejected:** writing usage into versioned meta or manifests.
- `decision:maude/v2-1.6-team-library-copy`
  - **What:** linking copies revisions in by id and materialises the working files. `head.json.library` records hub,
    project, system and upstream head. The copy is view only locally; updates come as a review, then "Update N
    canvases". The hub serves head and revisions under a scoped read grant (capability `ds-library`).
  - **Why:** 19 `ds-many-library` / 20 `ds-many-linked`. Code, agents and v1 peers in the linking project keep
    working on plain local files.
  - **Rejected:** rendering a linking project's canvases from the remote hub live.
