## 1. Question

> One persisted outbox for AI prompts, invites, comments, offline create and cloud exports: ordering, dedupe,
> expiry, replay against a target that is gone (trashed artboard, revoked role)

Also from the brief:
- I-substrate-audit #8: "five ad-hoc offline queues … no shared persisted outbox, ordering, dedupe, expiry, or
  replay-against-gone-target rule";
- CONTRACT §7 "AI offline": "Queued — sends when this Mac is online.";
- the 05 Empty States offline rows;
- 10's `co-sync-offline` / `co-sync-back`.

Deliverables: the record schema; storage and DDR-115 classification (all four lists); ordering, dedupe and
expiry rules; the replay-against-gone-target table with the user-facing words (CONTRACT §4 voice); the tests.

## 3. Options

**Option 1 — one outbox with two record kinds (recommended).**
- **The record kinds.**
  - The existing proposal chain stays exactly as it is — the same bytes, files and code — as the outbox's
    `content` lane.
  - A new **intent** record covers everything that must leave this Mac for a target that is *not* the
    kernel: AI on this Mac, the cloud or hub invite door, the render service, the handoff publish.
- **One home.** One root `_state/outbox/`, with intents in `intents/`. One store module, one gate and status
  model, one replay table, one Diagnostics list.
- **Cost:** one module, one record schema, three additive idempotency keys on target routes, and four fixes on
  the content lane.
- **What it breaks:** nothing. The proposal format is untouched, and 1.x ignores the subdirectory (§6).

**Option 2 — put intents into the DDR-241 chain as proposals.**
- The chain is strictly ordered, so an AI prompt waiting for an allowance reset would block every edit and
  comment behind it.
- The hub would need to understand invites, exports and AI, which are not kernel operations.
- Rejected.

**Option 3 — keep per-feature queues (today plus three new ones).**
- Five sets of rules, words and Diagnostics, and drift is guaranteed. This is exactly I-substrate #8.
- Rejected.

**Option 4 — a client-side outbox (localStorage / IndexedDB in the webview).**
- Nothing drains it while the window is closed.
- It is tied to the WKWebView data store, which changes per profile (V2-3.2 `data_store_identifier`) and can
  be cleared.
- It is invisible to the CLI and to Claude.
- Rejected. Browser shells keep unsent comment text as a per-tab draft only.

**Option 5 — an outbox on the hub or cloud.**
- Offline means it can't be reached.
- Rejected by definition.

## 4. Decision (DDR draft)

**Title:** One outbox per project, under `_state/outbox/`. Proposals are its content lane, unchanged. Intents
cover AI prompts, invites, Ask to edit, cloud exports and handoff publishes. Typed gates, per-lane ordering,
end-to-end idempotency, per-kind expiry, and one replay table for gone targets.

**Context.** v2 promises that offline is "a word, not a wall" (10). Prompts, comments, invites and cloud
exports wait in line and go by themselves, and canvases made offline sync later. Today only content changes
are durable, through the DDR-241 outbox, while prompts, invites and exports are dropped or refused. Even the
durable chain has three gaps:
- a body without a `status` field is retried forever and blocks everything behind it (proved, §6);
- the file plane has no 426 rule;
- entries are not bound to a project.

**Decision.**
1. **One outbox, two record kinds.**
   - The **content lane** is the DDR-241 proposal chain, byte-compatible. It covers every change to project
     files that the kernel accepts: edits, comments, annotation ops, canvas create, move, trash, restore,
     undo, AI stages.
   - **Intents** (`maude.outbox/1`) cover what leaves this Mac for another target: `ai.prompt`,
     `share.invite`, `share.ask-to-edit`, `export.cloud`, `export.handoff`.
   - A change to a project file is **never** an intent. A comment typed offline is a file write plus a
     proposal, and its "Queued" word is derived from the content lane.
2. **Where.** Intents live in `<designRoot>/_state/outbox/intents/<createdAt>-<id>.json`, written tmp + rename.
   - The location is per project and per Mac, and never synced.
   - It is under `_state/`, so it is runtime in all four DDR-115 lists already. No list changes.
   - 1.x drains only `*.json` at the outbox root and ignores the subdirectory (proved, §6), so a downgrade
     can't misread an intent as a proposal.
3. **Gates, not failures.** An intent waits on named gates: `online`, `hub`, `ai-connected`, `ai-ready`,
   `ai-allowance`, `signed-in`, `after`. A closed gate is not an attempt. Each gate has its fixed words
   (§5.4). When the gate opens, the record is sent by itself — the canvases' "starts by itself" / "sends
   when".
4. **Ordering.**
   - The content lane is one ordered chain, unchanged.
   - `ai.prompt` is ordered per chat.
   - Every other intent is independent.
   - Cross-lane, an intent waits for every content proposal made before it on this Mac (a watermark). AI then
     sees what you made offline, new canvases exist on the hub before a prompt or invite names them, and a
     cloud export renders them.
   - Content never waits on an intent.
5. **Dedupe.** The record `id` is the idempotency key end to end:
   - the run registry's `askId` (V2-1.15);
   - `Idempotency-Key` on the invite and export doors (additive);
   - the export `jobId`.
   A crash mid-send replays the same id and gets the first answer. Semantic dedupe per kind (§5.6) collapses
   repeats at enqueue.
6. **Expiry** is per kind (§5.7). The content lane never expires: work is never thrown away (DDR-241). An
   expired intent is not sent. It is shown once with what was kept: the prompt text in the chat, the invite
   in the Share sheet as "Not sent".
7. **Retry.** Transient answers (network, 5xx, 429, `retryable`) back off 1.5 s → 30 s with jitter until
   expiry. A **final** answer is never retried by itself. It follows the replay table (§5.9): `done`,
   `dropped` with words, or `needs-you` with one action. A manual Retry is "Retry <name>" (C20).
8. **Gone targets.** Each kind re-checks its target before sending:
   - a canvas or artboard in the trash, a removed element;
   - your role (removed, downgraded);
   - the project (relinked, unlinked, format raised, plan lapsed);
   - the account (AI disconnected).
   The answer, the words and what is kept follow one table. Nothing you made is deleted: content goes to its
   recovery slot or stays with the trashed canvas, a prompt stays in its chat, an invite stays as "Not sent".
9. **No generic enqueue route.** Each feature's own route decides "send now or queue" and calls
   `outbox.enqueue` in-process. The client never posts a raw intent, and Claude has no "act" verb
   (V2-1.11). The outbox has read, cancel and retry routes, and one read verb.
10. **The content lane gets four fixes** (V2-2.8 / V2-2.16):
    - a 4xx answer without `status` (413) is final and goes to recovery instead of blocking the chain;
    - entries are bound to the project id they were made for (an `unbound` entry never takes a later
      project's id);
    - a per-document pending view feeds the words;
    - `accepted-link.ts` writes a create to the outbox before its 25 ms batching window.

**Consequences.**
- Positive:
  - every drawn offline row has one mechanism behind it;
  - Diagnostics lists everything waiting, in one list;
  - restarts and crashes lose no intent;
  - double sends stop;
  - a relink can never deliver an old intent to the wrong project.
- Negative:
  - three target doors gain an `Idempotency-Key` (additive, v1-compatible);
  - one more directory under `_state/`;
  - the AI allowance reset time must be kept server-side (today it lives only in the client's usage state).
- Extends DDR-241 (the outbox gains intents and four fixes). It changes no proposal byte.

**Rejected:** options 2–5 (§3). Also rejected: intents for project-file changes (they would double-track
what the kernel already makes durable), and auto-retry of final rejections (C20).

## 5. Contract

### 5.1 Lanes

| Lane | Records | Order | Blocks | Delivered by |
| --- | --- | --- | --- | --- |
| `content` | DDR-241 proposals (`<createdAt>-<tx>.json` at the outbox root) | strict creation order, one chain per project | its own head only (after fix 10a no final answer blocks) | `transaction-client.ts`, unchanged protocol |
| `ai:<chatId>` | `ai.prompt` | FIFO per chat | that chat only | V2-1.15 `registry.ask` |
| `share` | `share.invite`, `share.ask-to-edit` | none (independent) | nothing | cloud / hub invite doors |
| `export` | `export.cloud`, `export.handoff` | start order = creation order, otherwise independent | nothing | render service / handoff publish |

A local project (no hub) has no content lane traffic and no `hub` gate. Its intents can still wait on
`online`, `signed-in` and the AI gates.

### 5.2 Intent record (`maude.outbox/1`)

```ts
type IntentKind = 'ai.prompt' | 'share.invite' | 'share.ask-to-edit' | 'export.cloud' | 'export.handoff';
type Gate = 'online' | 'hub' | 'signed-in' | 'ai-connected' | 'ai-ready' | 'ai-allowance' | 'after';

interface IntentRecord {
  format: 'maude.outbox'; v: 1;
  id: string;                         // /^i_[a-z0-9]{20}$/ — crypto random; the idempotency key end to end
  kind: IntentKind;
  createdAt: number;                  // this Mac's clock; order key within a lane
  actor: string;                      // who asked (the signed-in person of this project tab)
  device: string;                     // V2-1.5 origin.deviceId
  project: { id: string | null; hub: string | null };   // null/null = local project; bound at enqueue, never rebound
  lane: string;                       // 'ai:<chatId>' | 'share' | 'export'
  target: {                           // what must still exist when it is sent (§5.9)
    canvas?: string;                  // kernel doc entry (follows moves), or 'path:<repoRel>' before the op log
    artboards?: string[];
    elements?: ElementRef[];          // V2-1.4 (⌘/ selection)
    chatId?: string;
  };
  watermark: number | null;           // createdAt of the newest content-lane entry when this was enqueued
  gates: Gate[];                      // still closed, recomputed on every wake
  dedupeKey: string | null;           // §5.6
  expiresAt: number;                  // §5.7
  state: 'queued' | 'sending' | 'needs-you' | 'done' | 'dropped';
  attempts: number;                   // counted only while every gate is open
  nextAttemptAt: number | null;
  outcome?: { code: OutcomeCode; at: number; ref?: string };   // ref = askId / inviteId / jobId on success
  label: string;                      // the row's words: "Three reel covers", "Invite tereza@… · Can edit"
  payload: IntentPayload;             // per kind, below; validated by apps/studio/schema/outbox.v1.schema.json
}

type IntentPayload =
  | { kind: 'ai.prompt'; chatId: string; text: string; scope: { canvas: string; artboards: string[] | '*';
      elements?: ElementRef[] } | null; attachments: string[] /* content-addressed names in _chat attachments */;
      presentation: 'sent' | 'field' }      // 'field' = 03's "waits in the field" (setting up, used up)
  | { kind: 'share.invite'; email: string; role: 'view' | 'comment' | 'edit'; scope: 'project' | { canvas: string };
      message?: string }
  | { kind: 'share.ask-to-edit'; scope: 'project' | { canvas: string }; note?: string }
  | { kind: 'export.cloud'; spec: ExportSpec /* S8, the 09 sheet's fields */; saveTo: string }
  | { kind: 'export.handoff'; canvas: string; target: string };

type OutcomeCode =
  | 'sent'                // handed to the target, which answered
  | 'already'             // the target already had it (idempotent replay, already a member, …)
  | 'expired'
  | 'cancelled'           // by you
  | 'target-trashed' | 'target-removed' | 'target-missing'
  | 'access-removed' | 'access-reduced'
  | 'project-changed' | 'format' | 'plan'
  | 'refused';            // any other final answer from the target (its code in `ref`)
```

`label` and `payload.text` are personal and per Mac. They never leave this Mac except to the intended target
(C27 for prompts).

### 5.3 Storage and classification

- **Path.** `<designRoot>/_state/outbox/intents/<createdAt>-<id>.json`, one file per record. It is written
  `tmp` + `rename` before anything else happens (the DDR-241 rule). State changes rewrite the same name.
- **Prune.** `done` / `dropped` records are pruned 7 days after `outcome.at`, so Diagnostics can show recent
  ones. Cap 500 records per project; past it, the oldest `done` are pruned first. `queued` records are never
  pruned by the cap. A new intent past 500 queued is refused with "Too much is waiting to send. Go online or
  clear some in Diagnostics." (S11).
- **Classification.** `_state/` is runtime in all four DDR-115 lists (§2 table), so **no list changes**.
  V2-2.16 adds `_state/outbox/intents/x.json` and `_state/runs/x.json` (V2-1.15) to the tripwire fixture,
  where `isMaudeRuntimeState` and `isRuntimeStateRel` must agree. It also adds the planned
  `.gitignore` ↔ `gitignore-block.mjs` drift test.
- **Never.** Never exported, never in a handoff or ZIP, never on the file plane, never in `/_api/debug-bundle`
  in full. Diagnostics' "Copy diagnostic report" redacts `payload.text`, `email` and `message` (V2-2.9).

look." (10 `co-sync-back`; the second clause only when a conflict is waiting).

### 5.5 Ordering rules

- **O1** The content lane is one chain in creation order, unchanged (DDR-241).
- **O2** `ai.prompt` records of one chat go in creation order. A chat's next prompt waits until the previous
  one has become a run (V2-1.15: one active run per chat). Different chats are independent.
- **O3** `share` and `export` records are independent. Exports *start* in creation order when several
  release at once.
- **O4** An intent with a non-null `watermark` waits (gate `after`) until every content entry with
  `createdAt ≤ watermark` has a final answer.
- **O5** Content never waits on an intent. An intent never reorders content.
- **O6** A record made on a project never goes to another (`project` is bound at enqueue; §5.9 row
  `project-changed`).

### 5.6 Dedupe rules

| Kind | Idempotency (replay after a crash in `sending`) | Semantic dedupe at enqueue |
| --- | --- | --- |
| `ai.prompt` | `askId = id` in V2-1.15 `registry.ask` (idempotent) | same chat + same text within 2 s → one record (the double "Try again"). Otherwise two asks are two records. |
| `share.invite` | `Idempotency-Key: <id>` on the cloud and hub invite doors | `(project, scope, lower(email))`: the newer record replaces the queued one (role and message updated) and keeps the older one's place |
| `share.ask-to-edit` | `Idempotency-Key` | `(project, scope)`: one |
| `export.cloud` | `jobId = id` | `hash(spec)`: an identical queued export collapses into the existing row ("Export again" twice offline = one row) |
| `export.handoff` | `Idempotency-Key` | `(canvas, target)`: the latest wins |

### 5.7 Expiry (from `createdAt`)

| Kind | Expires | Why |
| --- | --- | --- |
| content lane | never | work is never thrown away (DDR-241) |
| `ai.prompt` | 7 days, or `resetsAt` + 1 h if later | a week-old ask is stale; a weekly allowance can reset later than 7 days |
| `share.invite` | 14 days | the cloud invite's own validity (`project_invites` +14 days) |
| `share.ask-to-edit` | 7 days | the hub invite default |
| `export.cloud`, `export.handoff` | 24 h | `MAX_JOB_AGE_MS`. A day-old render is "Export again", not a surprise |

Expired words:
- prompt: "Not sent — it waited a week. Your prompt is still here." + **Send** (it fills the field);
- invite: "Invite to tereza@… not sent — it waited 14 days." + **Invite again**;
- export: "Not exported — it waited a day." + **Export again**.

### 5.8 Retry

- A closed gate is not an attempt and has no backoff. The drain wakes on gate events (reachability, sign-in,
  AI login state, the `resetsAt` timer, content-lane progress), on enqueue, and on boot.
- **Transient answers** — network error, timeout, 5xx, 429 (honouring `Retry-After`), `retryable` — back off
  1.5 s → 30 s with ±20 % jitter, unbounded until `expiresAt`.
- **401** → the `signed-in` gate closes ("Sign in to send it.").
- **Final answers** → §5.9. Never retried automatically. A `dropped` or `needs-you` row in Diagnostics and in
  its own surface offers at most one action (CONTRACT §4).

### 5.9 Replay against a gone target

Each row is checked **before** sending (from the studio's own manifest, the project's last-known role, chat
state) and again on the target's answer. "Kept" says what survives on this Mac.

| --- | --- | --- | --- | --- | --- |

### 5.10 Studio API, bus, CLI (main origin only, never in either canvas allowlist)

| Route | Answer |
| --- | --- |
| `GET /_api/outbox` | `{ seq, content: { pending, oldestAt, sent, byDoc: Record<entry, {count, oldestAt, lanes: string[]}>, comments: string[] /* comment ids not yet accepted */ }, intents: IntentView[] }` — `IntentView` = the record without `payload.text` / `email` / `message` (the owning surface fetches its own record) |
| `GET /_api/outbox/:id` | the full record (the chat, Share sheet, Exports panel use it) |
| `POST /_api/outbox/:id/cancel` | `{state:'dropped', outcome:'cancelled'}`; content entries can't be cancelled (403 `content-lane`) |
| `POST /_api/outbox/:id/retry` | re-opens a `dropped: refused` / `needs-you` record once (C20 manual) |

- **No enqueue route.** These routes enqueue in-process when the target is not reachable:
  - the chat `prompt` WebSocket frame (S5);
  - the invite and Ask to edit routes (S9);
  - the export route with `render: 'cloud'` (S8);
  - the handoff publish (S8).
- **Bus:** `outbox:changed {seq}`. It feeds the comment pin "Queued", canvas rows "not sent" (10
  `DRESY_FOLDERS`), the Canvases panel foot, the Share sheet's pending invites, the Exports rows and the chat
  line.
- **CLI:** `maude design outbox list [--json]` (effect `none` → auto; for Claude and Diagnostics parity).
  `maude design outbox cancel <id>` (effect `shared` → prompt tier: it withdraws a queued invite or export).
  No enqueue verb exists: Claude asks through each feature's own verb, and that verb queues when offline. One
  example is `maude design export-cloud`, which answers "Queued — starts when this Mac is online" and exits 0.
- **Registry actions** (V2-1.3 / V2-1.11):
  - `outbox.list` — Diagnostics › Sync details › Advanced, ⌘K "Waiting to send" — cli `outbox list`;
  - `outbox.cancel` — the row's ⋯ — cli `outbox cancel` (prompt);
  - `outbox.retry` — the row's "Retry <name>" (manual, C20) — cli `maude design outbox retry <id>` (effect
    `shared` → prompt).

### 5.12 Content-lane fixes (V2-2.8 / V2-2.16; fail-first tests in §7)

- **a.** `transaction-client.ts` `settle`: a 4xx answer whose body has no `status` is **final** →
  `onRejected` with code `http-<status>` → recovery. Today a 413 is retried forever and blocks the chain
  (§6). A 401 stays as today. 408, 425 and 429 stay transient.
- **b.** `OutboxEntry` gains `projectId`, set at write once the project is known. An entry whose `projectId`
  differs from the bootstrapped project is never sent; it goes to recovery (G18). `unbound` entries bind
  **only** to the project the studio was linked to when they were written: the link record id is stored in
  the entry.
- **c.** The `byDoc` / `comments` pending view (§5.10). It is derived from outbox entries + the accepted
  head, so nothing new is persisted.
- **d.** `accepted-link.ts` `queueCreate` writes each create to the outbox before the batching window (or
  shortens the window to the outbox write), so a crash can't lose a create acknowledged as `{queued:true}`.

Client→studio hops on loopback are not outbox traffic, but they get one rule: **the sender keeps the item
until the studio answers.**
- The `comment-submit` composer keeps its text until the studio ACKs. Fix the `wsSend` silent drop by sending
  the `dgn` message through the HTTP route with retry while the sidecar restarts.
- Annotation ops keep `pendingRef` through a sidecar restart. A 403 shows the C30 denial line instead of
  "local-only".
- These go to S9 / S4.

## Decisions

- `decision:maude/v2-V2-1.14-one-outbox-two-kinds`: one outbox per project under `_state/outbox/`. The DDR-241
  proposal chain is its content lane, byte-compatible. Intents (`maude.outbox/1` in `intents/`) cover AI
  prompts, invites, Ask to edit, cloud export and handoff publish. A project-file change is never an intent.
  Rejected: intents as proposals, per-feature queues, a client-side outbox, a hub-side outbox.
- `decision:maude/v2-V2-1.14-gates-order-dedupe-expiry`: intents wait on named gates (not failures). The
  content chain is strictly ordered, prompts are FIFO per chat, everything else is independent, and an intent
  waits for the content made before it (watermark); content never waits. The record id is the idempotency key
  end to end (`askId`, `Idempotency-Key`, `jobId`). Expiry is per kind and content never expires; final
  answers are never auto-retried. Rejected: one global chain for everything, time-based retries of final
  rejections.
- `decision:maude/v2-V2-1.14-gone-target-table`: one replay table (G1–G26) decides the outcome, words and what
  is kept when a canvas or artboard is trashed, an element removed, a role removed or lowered, the project
  relinked or format-raised, or the plan lapsed. Nothing you made is deleted. Records never cross projects.
  Format and plan pauses don't drop intents. Rejected: silently dropping, sending to whichever project is
  linked now.
- `decision:maude/v2-V2-1.14-content-lane-fixes`: the content lane gets four fixes. A 4xx without `status` is
  final (today a 413 blocks the chain forever, proved); entries are bound to their project id; a per-document
  pending view drives the "Queued" / "not sent" words; creates are durable before batching. No proposal byte
  changes.
