# V2-1.2 — Mode and toolbar ownership

Spike of the Maude v2 run (plan `.ai/plans/feature-maude-v2-redesign.md`, Phase 1). Feeds P4 (V2-4.1, V2-4.3,
V2-4.5), S3, S2, S4 and the typed bridge V2-2.10. Precedence used throughout: Gate 0 register → `CONTRACT.md`
→ `04 Modes` (topic owner: modes, toolbars per mode, Present) → `15 Annotations` (Preview toolbar) / `14 Editing`
(Edit toolbar) → `_kit.tsx` → inventories.

## 1 · Question

> Shell owns mode; the iframe renders the two toolbars and tools; new `dgn` messages (`set-mode`, mode echo,
> `occluded-insets` for floating panels); one typed message table.

## 2 · What exists today

**Mode is iframe-owned.** `use-tool-mode.tsx` · `ToolProvider` holds `mode: CanvasMode = 'preview' | 'edit'`
next to `tool` (DDR-223). Its rules:

- The mode⇄tool invariant lives in the store. Arming `move` means Edit; arming `browse` means Preview; annotation
  tools are mode-neutral.
- `setMode` arms the mode's resting tool (`MODE_DEFAULT_TOOL`). `resetTool` (Esc, post-draw) arms the current
  mode's resting tool.
- Boot is Edit/`move`. Read-only (`?ro=1`, `read-only-mode.ts` · `isReadOnlyCanvas`) boots Preview/`browse` and
  keeps only `browse`/`move`/`hand` (`READ_ONLY_TOOL_IDS`).
- A UI canvas mounts **two** providers from separate bundles: `canvas-comment-mount.tsx` (→ `dist/comment-mount.js`)
  and canvas-lib's `MaybeToolProvider`. They agree on the tool through the document event `maude:tool-sync`
  (`TOOL_SYNC_EVENT`); mode follows only through the resting tools (kg
  `maude/canvas-tool-state-synced-across-providers`).

**The toolbar is in the iframe.** `tool-palette.tsx` · `ToolPalette` draws `.dc-tool-palette`, bottom centre:

- Mode segments Preview · Edit · Present (`palette-mode-preview|edit|present`).
- Nav `hand` + `comment`.
- Draw tools `pen` `highlighter` `shape` (kind popover) `sticky` `section` `arrow` `text` `eraser`, with a
  double-click sticky lock.
- `+` Insert Div/Text/Image (Edit only), Stickers (`open-sticker-picker`) and Export (`maude:open-export`).

Tool keys resolve in `input-router.tsx` · `classify()`: V H C B I R/O A N T ⇧S E, plus Esc.

**Present is shell-owned** (DDR-117). The palette posts `present-enter`. The shell (`client/hooks/use-canvas-bridge.jsx`)
honours it only from the active canvas, never with a modal open and never while already presenting. It then sets
`presentMode`, puts `.maude.is-present` on the shell root, and broadcasts `view-chrome {present}` to every iframe.
Esc (`client/hooks/use-keyboard-shortcuts.jsx`) and the trusted exit pill leave Present. `use-chrome-visibility.tsx`
treats `present` as a non-destructive master hide.

**The bridge is untyped and spread out.** It covers **105 message types, 173 send sites and 120 handle sites across
567 scanned files** (§6). Shell side, they live in one listener in `client/hooks/use-canvas-bridge.jsx` plus smaller
ones in `use-shell-core.jsx`, `app.jsx` and `embed-view.jsx`. Canvas side:

- independent `message` listeners in `canvas-shell.tsx`, `canvas-lib.tsx`, `annotations-layer.tsx`,
  `comments-overlay.tsx`, `canvas-comment-mount.tsx`, `video-comp.tsx`, `ai-banner.tsx`, `use-agent-presence.tsx`,
  `use-element-resize.tsx`, `use-spacing-handles.tsx`, `use-grid-track-handles.tsx` and `export-dialog.tsx`;
- three non-bundled scripts: `plugins/design/templates/_shell.html`, `inspect.ts` · `INSPECTOR_SCRIPT` (it also
  forwards ⌘K/⌘R/⇧⌘-chords as `toggle-palette`/`shell-shortcut`) and the hub's expiry page
  (`apps/hub/src/studio-proxy.mjs`).

The only shared validator today is `canvas-notice-message.ts` · `acceptCanvasNotice`, imported by the shell. Gates:

- **Shell side.** Every branch checks `origin === canvasOrigin`, and most add `e.source === activeWin`.
- **Canvas side.** Only the DOM-mutating and write-driving messages check `e.source === window.parent`
  (`apply-style`, `record-edit`, `freeze-and-set-kind`, `export-capture`, the `*-failed` replies). The view-only
  rest is "correctly ungated" per DDR-117.

**Fit and reveal assume the whole host is visible.** In `canvas-lib.tsx`:

- `computeFit(rects, hostEl, pad = 24)` and `fitRectIntoHost` (⌘0, `jumpTo`, ⌥⌘1–9, embed `zoom op:'artboard'`)
  fit into `hostEl.clientWidth/clientHeight`;
- `useViewportController` `reset`/`zoomIn`/`zoomOut` anchor at the host centre;
- `activeArtboardId` and `DCMiniMap` · `centerOnWorld` use the host centre.

`canvas-shell.tsx` · `revealElementViaCamera` reveals into the whole host rect (`revealAxisDelta`, margin 40).

Constraints from prior decisions:

- DDR-054 (canvas origin untrusted);
- DDR-088 (canvas-origin routes need `CANVAS_SAFE_API` **and** the `startCanvasServer` routes map);
- DDR-117 (Present is shell-level; the escape hatch must be trusted shell chrome; a canvas must not blank a
  modal or a security banner);
- DDR-187/DDR-223 (browse/move split, pass-through invariant, boot = Edit, posture tables kept verbatim);
- DDR-025 (canvas-lib single source);
- kg `maude/viewport-publish-is-settle-only` and `maude/live-viewport-prop-for-memoized-screen-space-chrome`;
- Gate 0 A7 (switch in the Share cluster, keys ⌥⌘P ⌥⌘↵ ⇧⌥⌘↵ L), A8 (override: AI changes live in Preview, also
  under the pointer; Present lands on move-on), D1/D2 (Browse and key moves), C12 (Stickers E), C14 (Marker tips),
  C26 (focus-scoped keys).

## 3 · Options

1. **Shell owns mode; the iframe executes and renders both toolbars** (the plan's default). The shell sends
   `set-mode` and the canvas echoes `mode-changed`; `ToolProvider` stays the executor; the toolbars are a re-skin of
   `tool-palette.tsx`.
   - *Cost:* a governed path in `ToolProvider`, about six new messages, and a window-level mode snapshot so both
     in-iframe bundles agree.
   - *Breaks:* nothing before Phase 4. The governed path is dormant until the shell sends its first `set-mode`.
2. **Canvas owns mode; the shell mirrors an echo** (today's model, extended).
   - *Cost:* small.
   - *Breaks:* the Share cluster switch, menus and panel folding depend on an async echo from whichever iframe is
     active. With no canvas (Home, a render error) mode is undefined. Background iframes diverge, and Present is
     already shell-level, so mode would live in two places.
3. **Toolbars render in the shell; the iframe only executes tools** (`tool-set`).
   - *Cost:* every tool key pressed in the canvas makes two hops (up for the decision, down to arm). The executor's
     tool state (sticky locks, shape kinds, inks, follow-pointer placement) splits across documents.
   - *Breaks:* re-litigates DDR-187/223's in-iframe store and its pinned posture tables; the plan's reuse table says
     re-skin `tool-palette.tsx`.
4. **Fit by shrinking the iframe instead of insets** (layout).
   - *Breaks:* V2-4.1 "canvas edge to edge"; the iframe would re-layout on every fold/unfold frame. Only "Pin panels
     to the side" (06 ad-pinned) shrinks the iframe, and insets then compute to 0 by themselves.

## 4 · Decision (DDR draft)

**Context.** v2 moves the mode switch into the Share cluster (A7, CONTRACT §7) and splits the one palette into two
toolbars, one per mode (CONTRACT §2). Floating panels overlay a full-width canvas iframe (V2-4.1). Today the mode
lives in the iframe and the shell↔canvas vocabulary is 105 untyped messages with per-branch gates.

**Decision.**

1. **The shell owns mode.** Modes are Edit (editors) or Viewing (Can view, Can comment), plus Preview and Present
   (Artboards one by one, or the Canvas). Mode is per project window, so a link to another canvas keeps Preview.
   The shell is the only writer while governed. It broadcasts `set-mode` to every canvas iframe, with the tool for
   the active one, and seeds a frame on `loaded` and when it becomes active.
2. **The iframe executes.** `ToolProvider` stays the tool store and executor. On the first gated `set-mode` it
   enters a **governed** path:
   - mode changes come only from `set-mode`;
   - same-mode tool changes stay local;
   - a cross-mode gesture posts `mode-request` and does not change mode locally;
   - every applied state is echoed once as `mode-changed`.

   Until that first `set-mode`, today's DDR-223 semantics hold byte for byte. That covers every test, the bare
   specimens and the embed until each moves. A standalone canvas (`window.parent === window`) applies requests
   locally.
3. **Both in-iframe bundles read one mode snapshot.** It lives on `window` under `Symbol.for('maude.canvasMode.v2')`
   (`bridge/canvas-mode-store.ts`). It is installed once per document and holds the single `set-mode` /
   `occluded-insets` listener. Both providers subscribe, so the comment-mount and canvas-lib providers cannot
   disagree on mode. `_shell.html`'s HMR applier reads the same snapshot for the A8 hold. Tools keep `maude:tool-sync`.
3a. **The canvas runtime gets a resolver seam.** `classify()` keeps pointer classification. Its keydown branch
   delegates to the V2-1.3 registry resolver, whose tool layer reads `MODE_TOOLS`. This was agreed with V2-1.3:
   one resolver per keydown, ending today's double fires.
4. **Two toolbars render in the iframe** as a re-skin of `tool-palette.tsx`: Edit and Preview, plus Viewing's
   reduced bar, with `ToolbarMorph` on mode change. Tool-option popovers render in the iframe; panels needing
   privileged data or network render in the shell (§5.6).
5. **Toolbars are drawn from one data table,** `bridge/canvas-modes.ts` · `MODE_TOOLS`. It is a data-only leaf with
   modes, tool ids, keys, labels, resting tools, More and `minRole` per row. The iframe toolbars, the input router
   (through the V2-1.3 registry's tool layer), ⌘K, "?" and the docs all read it.
6. **Floating panels report occlusion.** The shell sends `occluded-insets` (edge insets in iframe px). Every
   programmatic camera move honours them: fit, jump, reveal, zoom anchors, the active artboard and the minimap
   centre. An inset change alone never moves the camera.
7. **One typed message table,** `bridge/dgn-protocol.ts`. It covers all 105 existing messages plus the new ones,
   each with direction, payload type, validator, gate, status and owner. The shell imports it from `client/`; the
   canvas runtime and comment-mount import it from the studio root. Non-bundled scripts keep literals, and a
   coverage test built on `scripts/v2-dgn/dgn-inventory.mjs` closes the gap.
8. **Present's controls and exit stay trusted shell chrome** (DDR-117). Present·Artboards renders the lifted
   artboard in the iframe. In Present·Artboards, module updates are held until the presenter moves on (A8); every
   other mode shows them live, Preview under the pointer too.

**Consequences.**

- The shell bundle and both iframe bundles each carry a copy of the validators. Budget: ≤ 12 KB minified per bundle.
- v1 behaviour is unchanged until Phase 4 flips the shell to `set-mode`, so the characterization golden,
  `mode-toggle.test.tsx` and `tool-palette.test.tsx` stay green until V2-4.3/V2-4.5 rewrite them deliberately.
- A pre-existing confused-deputy gap gets fixed in a separate fail-first commit (§5.2): canvas-side `undo`/`redo`,
  `locked-set`, `tool-set` and `select-by-id` accept messages from sibling canvas frames.
- `04 Modes` · `md-edge-ai` and `md-model`'s row "What AI changes … never under your pointer" contradict signed A8
  and must be amended by the lead (Gate 0 wins).
- The registry (V2-1.3) owns chord forwarding (`key`) and canvas-executed actions (`run-action`). This table
  declares both as owned by V2-1.3.

**Rejected alternatives.**

- Option 2: mode is undefined without a canvas, and two owners exist once Present counts.
- Option 3: double hops per key and executor state split across documents.
- Option 4: contradicts V2-4.1 and re-layouts per animation frame.
- Renaming the v1 annotation tool ids (`shape`, `text`, `pen`) to free the names for the new Edit tools: churn in
  the `input-router` posture tables that DDR-223 keeps verbatim. New ids for new tools instead.
- A list of occluding rects with a largest-empty-rectangle fit: more precise for corner islands, but edge insets
  are how side-panel apps fit. Revisit only if corner islands cover a fit in practice.
- Initial insets in the iframe URL: a once-only boot re-fit rule is simpler and adds no URL contract.
- Zod/JSON-schema validators: a dependency in two bundles for ~105 small guards.
- One dispatcher for the whole canvas document: the canvas listeners live in separate bundles, so a shared
  `acceptFromShell` guard is used instead.

## 5 · Contract

### 5.1 Modules and how each document imports them

All four modules are new, under `apps/studio/bridge/`. They are leaves: no React and no DOM beyond the
`MessageEvent`/`Window` types; type-only imports are allowed.

| Module | Holds | Imported by |
| --- | --- | --- |
| `dgn-protocol.ts` | `ShellToCanvas`, `CanvasToShell` (below), `DGN_TABLE` (direction, gate, status, owner, `parse`), `acceptFromCanvas`, `acceptFromShell`, `postToCanvas`, `postToShell` | shell: `client/hooks/*` via `../../bridge/dgn-protocol.ts` (the `canvas-notice-message.ts` precedent) · canvas runtime: `canvas-shell.tsx`, `canvas-lib.tsx`, `use-tool-mode.tsx`, `annotations-layer.tsx`, `video-comp.tsx`, `use-*.tsx` via `./bridge/…` (bundled into the canvas-lib runtime module by canvas-build; canvas TSX itself still imports only `@maude/canvas-lib`) · comment-mount: `canvas-comment-mount.tsx`, `comments-overlay.tsx` (own copy in `dist/comment-mount.js`; React stays external, and this module has none) |
| `canvas-modes.ts` | `CanvasModeV2`, `ToolId`, `ModeCaps`, `MODE_TOOLS`, pure `toolKeyAction`, `escStep`, `baseMode`, `initialMode`, `clampMode`, `holdsModuleUpdates` | the same documents, plus the V2-1.3 registry (the tool layer derives `tool.<id>` actions from it) |
| `occlusion.ts` | `Insets`, `visibleRect`, `clampInsets`, `insetsFromIslands`, `MIN_VISIBLE_PX = 240` | shell (computes the insets) · canvas-lib and canvas-shell (consume them) |
| `canvas-mode-store.ts` | the window-level snapshot (`Symbol.for('maude.canvasMode.v2')`), `canvasModeStore(win)` with `get`, `subscribe` and an idempotent install of the one `set-mode` / `occluded-insets` listener | `use-tool-mode.tsx` (both bundles) · canvas-lib · read by key from `_shell.html` (plain JS) |

Not bundled, so they use literal strings and are covered by the coverage test (§7 T1): `_shell.html` inline
scripts, `inspect.ts` · `INSPECTOR_SCRIPT` and `apps/hub/src/studio-proxy.mjs`. The hub must never import
`apps/studio`. `bridge/` ships with `apps/studio` in npm `files`, is staged into the `.app` and is included in
`tsconfig` (`**/*.ts`).

### 5.2 The typed table

Gate vocabulary:

- **Shell side** (after `e.origin === canvasOrigin`):
  - `active`: `e.source` is the active canvas window;
  - `asked`: the frame the shell asked, correlated by `id`;
  - `frame`: any iframe the shell owns;
  - `any`: any canvas-origin window.
- **Canvas side:**
  - `parent`: `e.source === window.parent`;
  - `parent|self`: also the canvas document posting to itself;
  - `any`: no source check.

`acceptFromCanvas` and `acceptFromShell` apply origin, gate and `parse` in one place. A handler only ever sees
typed, validated payloads.

**Security note (pre-existing, found by this spike).** All canvas iframes share one `canvasOrigin`, and any frame can
reach its siblings via `window.parent.frames`. A background canvas (synced, untrusted, DDR-054) can therefore post
`undo`/`redo` into the active canvas, which then sends a legitimate `apply-edit` from the active window, and the
shell writes it. Likewise it can post `locked-set`, `tool-set`, `select-by-id`, `zoom` or `view-chrome`. The fix is
V2-2.10c: every shell→canvas message gates on `parent`, or `parent|self` for `force-clear`. It lands as its own
fail-first commit. V2-1.5 (undo) agreed: v2 undo moves to shell registry actions; the dgn `undo`/`redo` lane remains
only for the legacy DDR-050 stack until retired.

### 5.6 Occluded insets

```ts
// apps/studio/bridge/occlusion.ts
export interface Insets { top: number; right: number; bottom: number; left: number } // CSS px of the iframe viewport, integers ≥ 0
export const MIN_VISIBLE_PX = 240;
/** Visible rect of a w×h host. An axis whose visible span would drop below MIN_VISIBLE_PX ignores both its insets. */
export declare function visibleRect(w: number, h: number, ins: Insets): { x: number; y: number; w: number; h: number };
/** Shell side: per edge, the deepest overlap of any visible island declaring that edge, plus `gap`, rounded up. */
export declare function insetsFromIslands(
  frame: { left: number; top: number; right: number; bottom: number },
  islands: ReadonlyArray<{ rect: { left: number; top: number; right: number; bottom: number }; edge: 'top' | 'right' | 'bottom' | 'left' }>,
  gap?: number /* default 8 */
): Insets;
export declare function clampInsets(raw: unknown): Insets | null; // finite, 0…8192, rounded; else null
```

**Shell.**

- Every floating island root carries `data-occludes="top|right|bottom|left"`: the project pill and Share cluster are
  `top`, the Canvases/Layers/Assets panel is `left`, the AI chat, Inspector and Comments panels are `right`, and the
  timeline and ZoomUndo are `bottom`. Folded corner icons count as well.
- The shell measures islands with one ResizeObserver hook and computes `insetsFromIslands` against the iframe's
  rect. A pinned panel (06 ad-pinned) doesn't overlap the iframe, so it yields 0.
- It sends `occluded-insets` to every iframe only when the value changes, coalesced to one per animation frame, and
  seeds a frame on `loaded`.
- For a mode transition it sends the **target** layout's insets **before** `set-mode`. postMessage between the same
  two windows is delivered in order, so the canvas eases the camera into the post-fold visible area while the
  panels fold (04 md-motion: "the camera eases onto the artboard you were on").

**Canvas.**

- Effective insets are the per-edge max of the shell's insets and the canvas's local chrome: its own toolbar island
  (bottom) and the minimap/zoom pill when shown. Present uses 0.
- These honour them:
  - `computeFit(rects, host, pad, insets)` — ⌘0, `jumpTo`, ⌥⌘1–9, `zoom op:'fit'|'artboard'`, the mode-transition ease;
  - `reset` (⌘1) and `zoomIn`/`zoomOut` — anchored at the visible centre;
  - `activeArtboardId` — nearest the visible centre;
  - `DCMiniMap` · `centerOnWorld` — centres in the visible rect;
  - `revealElementViaCamera` — view bounds = visible rect, margin 40.
- **Never consumers:** hit-testing, export and capture, `__maudeCanvasRects` (world coords), and the persisted
  camera (view.json stays raw).

**Invariants.**

- **(I1)** An inset change alone never moves the camera.
- **(I2)** Boot re-fit, once only. If the first insets arrive while the camera is still the boot fit (no persisted
  viewport, no gesture yet), the canvas re-fits once.
- **(I3)** With all-zero insets, every consumer is byte-identical to today (§6, 15 000 random fits).
- **(I4)** An older `seq` is dropped.
- **(I5)** Payload ≤ 200 bytes, ≤ 1 message per frame.

### 5.7 Budgets and invariants of the mode lane

- **(M1)** Governed means the canvas changes `mode` only on a `parent`-gated `set-mode`.
- **(M2)** Each applied `set-mode` produces exactly one `mode-changed` with the same `seq`.
- **(M3)** A canvas-initiated mode crossing is a `mode-request` and is a no-op locally.
- **(M4)** The shell honours `mode-request` only from the active canvas, with no modal open and allowed by the role.
  This is the `present-enter` hardening, generalised.
- **(M5)** `set-mode` is ≤ 300 bytes. A key-initiated mode switch reaches the toolbar morph within 2 frames of the
  keydown. Measured in V2-4.5, it must stay inside the 220 ms `--dur-panel` morph start.
- **(M6)** Reduced motion turns the morph, the fold and the camera ease into a 1 ms cut.
