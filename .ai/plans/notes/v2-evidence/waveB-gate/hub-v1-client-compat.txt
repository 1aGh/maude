FINDINGS
  F1 (by design, note only) — a 1.9.1 desktop never receives the v2 DS manifests
     (tokens.json, components.json, revisions/head.json, revisions/<64hex>.json): 1.9.1 keeps bare
     .json default-closed; V2-1.12 C1 opened exactly those names on v2 only. It still receives the
     stylesheets, so a v1 peer renders the system it had. Consequence to know: the hub's per-file
     delivery for that peer never reports those paths present.
  F2 (DEFECT, named, not fixed) — a read-only (viewer) v1 desktop leaves a document STUB on the
     feat hub. Repro: v1.9.1 desktop with a readOnly token; create ui/viewer-local2.tsx locally;
     after ~25 s `GET /api/documents` on the feat hub lists `ui-viewer-local2` (48 bytes; decoded:
     only syncMeta.path = "ui/viewer-local2.tsx", no html — gate/stub.mjs). The SAME steps on the
     v1.9.1 hub (4795) list nothing new. A stub that a read-only peer creates is then advertised to
     every peer: a 1.9.1 desktop pulls every listed name as a canvas (sync/remote-docs.ts
     pullTargets). Not isolated to one slice: the WS door changed from `match.readOnly` to
     `door.readOnly` (S9.5, docDoor), plus the paused/accepted fences — the syncMeta-only write
     survives somewhere on that path. Needs an RCA (hub server.mjs onAuthenticate + Hocuspocus
     readOnly handling of SyncStep2), not a gate-time patch.
  F3 (rig only) — local-cell.mjs mints the desktop token as member but writes role "owner" into
     hubs.json, so a fresh local cell logs "the workspace did not take this project's config (403)".
     Harness artefact, not a product defect.
