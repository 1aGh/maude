## New findings

**N1 — Medium — any token can permanently block the owner's future code paths, and the owner is never told.**
- Where: `file-manifest.mjs:162-167` (the note is taken inside `hubCheckoutClass`), called through `checkoutFileClass` from:
  - the read route `:595`, where the class is checked before scope or existence
  - `resolveCheckoutFileWrite` `:468`, used by `file-door.mjs:420`, `asset-lane.mjs:696` and `upload-sessions.mjs:329`
- Scenario:
  1. While the hub is undeclared, a viewer, a canvas-only session or an editor sends `GET /api/project-file/lib/Foo.tsx` (or many such paths). The file does not need to exist.
  2. Every probe inserts a `class_holds` row with `code_sha = NULL` (`journal.mjs:316`).
  3. The owner later declares folders. Each probed path now classifies `never` for good. Only a matching owner sha lifts a hold (`:173`), and NULL never matches. So the owner's desktop push of real code there is refused at the door.
  4. `heldCodeEntries` skips files that are not on disk (`:207-212`), so the owner's held list stays empty.
- The owner's own pushes during the undeclared window plant the same holds with no attacker involved. A deleted owner file (latest row `deleted = 1`) also gets a NULL hold.
- The owner has no way to adopt a held path as code. The only fixes are restoring the exact bytes or adding the folder to the canvas folders.
- Arbitrary probes also grow the table and the in-memory `noted` set without bound. Every owner journal read walks all rows (`journal.mjs:883`, with an lstat and a hash per row).
- Fix:
  - Take the note only where a canvas body really exists or was written: the walk, `recordWrite`, and reconcile of an existing regular file. Never take it from a door or read classification.
  - Drop a hold when the file is gone.
  - Let a write from a project-wide owner token release the hold (that is the owner adopting it).
  - List NULL-sha holds whether or not the file is on disk.

**N2 — Low — holds taken since the last backup generation are lost when a cell wakes.**
- Where: `journal.mjs:1060-1068`. The write-behind tail carries only journal rows; `class_holds` reaches the bucket only inside a `journal.db` snapshot (up to about 6 h apart).
- Scenario:
  1. A teammate creates `brand/x.tsx` and it is noted.
  2. Within the same generation window the owner declares folders, and the cell then sleeps and wakes.
  3. The restored `journal.db` has no hold, while the checkout has both the declared config and the file.
  4. The boot walk-import (`server.mjs:2910`) journals the teammate's file as `code-module`. That is Att L1 again.
- Fix: write hold rows into the tail as well, or snapshot `journal.db` when the config door changes the groups. Alternatively, work out where a file came from using the document store (a document exists for that slug) instead of a side table.
