## What is over budget, with cause

1. **Covers: 206–245 s against 45 s.** Eight canvases never produce a cover: `unavailable:failed` for
   `ui/2026/combine/Combine-admin.tsx` and all seven `ui/club-web/*` (admin-details, admin-states, admin, flows,
   public-states, responsive, website) — the `kind="web"` canvases. Each is retried to the failure cap with the
   renderer's 10–20 s waits (`bin/_thumbs-playwright.mjs`), which is ~170 s of the total; the 87 that succeed take
   p50 0.58–0.86 s each (Phase 1: 0.15–0.18 s, so some of that is this Mac's load). V2-2.17 recorded 94/94 covers in
   35–38 s on the same project, so this is a regression or a clone difference — **not fixed here**: needs the renderer
   owner (reproduce: `bun scripts/v2-index-bench.ts --root <unlinked clone> --skip-artboards --skip-assets --skip-versions`;
   the JSON now lists the failed rels). Likely first stop: why a web artboard is not found/stable for the card shot.
2. **Version pictures 754/1477 ms against 300/800**: unchanged from V2-2.17 ("preferred fix: mount only the target
   artboard"); not attempted.
3. **Asset tiles look vacuous.** 189 of 194 tiles report `missing` (a glyph, no picture) in 2 ms each, where Phase 1
   rendered 193 real pictures (12 s, p50 49 ms). Either the bench lost access to `assets/` after the canvas-origin
   frame capability (C4) or the tile path is not drawing pictures. The ≤ 30 s budget is met trivially and means
   nothing until a tile of a real picture is seen. Needs the asset-tile owner.
4. **LOD / 64 boards at < 25 %**: the cost is the artboard render count (5,312–5,440 per gesture, pre-v2 2,944), not
   the annotation board: the same canvas with **0** annotations renders 5,312 times as well. See `V2-8.8-perf.md`
   Finding 1; the one fix tried (`DCArtboard` unused controller subscription) is committed, tested and gains ~2 % —
   the real cause is still open (V2-4.1).

### Causes found
1. **Covers.** The eight `kind="web"` canvases (`Combine-admin`, `ui/club-web/*`) import `ui/club-web/_frames.tsx`, which
   renders `DesignCanvas`. Since the C4 frame capability (decision `v2-gate-b-c4j-lead-never-inline-foreign-canvas`) a
   frame never inlines a canvas outside its own grant, so the module answers `403 not-in-scope` for EVERY opener and the
   shell writes the refusal into `#canvas-mount-error`. Nothing to do with web artboards hugging content: the canvas
   never mounts. The renderer waited the full 20 s for `#canvas-root` and the service retried to the cap (~170 s).
   **Fix:** the renderer races the mount against the shell's own error text and reports `canvas-failed` at once; the
   service does not retry it (the key changes with the source). **This is a product finding, not only a perf one:** those
   eight canvases do not open in a frame at all in this build (the wrapper is a canvas by content). Whether the closure
   rule should admit a module that only *wraps* `DesignCanvas` is a security decision for the lead; the project-side fix
   is to render `DesignCanvas` in each canvas file and keep `_frames.tsx` free of the word.
   Also: the cover sweep was serial (one background job at a time) and slept 250 ms in `settleCount` per canvas. Now the
   index's artboard count is sent with the job and the renderer stops at that count (settle 293 → ~55 ms), two background
   pages render at once, and `startBackground` treats Home's first 12 as on-screen (all four pages).
2. **Asset tiles.** The tile page was held and reused across tiles, but its frame capability names the ONE picture its
   URL was minted for (the gate reads it off the page's own URL, the Referer of what the page loads): every tile after
   the first was a 403 → `missing` → a glyph. The held page now re-enters the shell per picture. Then made fast: two
   renderer lanes, and the picture is scaled and JPEG-encoded in the page (canvas `toBlob`) instead of viewport +
   2 × rAF + screenshot (p50 186 → ~100 ms on this Mac).
3. **Version pictures.** The renderer now adds `?thumb-only=<artboard>` for a past-version picture of one artboard and
   `DCArtboard` (canvas-lib, shared file, separate commit) mounts only that board. The gain is **small** (A/B on the quiet
   mini, 4 pairs: warm p95 −7…−12 %, p50 within noise): the floor is the browser round trip, not the React render —
   even a 1-artboard canvas takes ~175–270 ms to mount warm because every canvas module inlines canvas-lib
   (**2 MB** in the source-booted dev build; the packaged server minifies, not measured here), plus ~100 ms settle and
   ~100–200 ms screenshot on software Chromium. p50 ≤ 300 ms is **not** met on this hardware; p95 ≤ 800 ms is met on the
   mini. The honest next lever is per-canvas module size (share canvas-lib between canvases), not artboard mounting.
