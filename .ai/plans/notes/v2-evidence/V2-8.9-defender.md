## M1 (medium) — hub-link confirm route has no caller check while the registry calls it human-only
apps/studio/routes/sync.ts:91-125 (`POST /_api/sync/link/confirm`) + sync/link-consent.ts:358. `sync.connect-link` is human-only in the registry, but the route relies only on the generic write gate (http.ts:512), which admits a request with no `Origin`. No `Sec-Fetch-Site: same-origin` check (unlike routes/cloud-move.ts:338); cli/lib/bash-guard.mjs:480 HUMAN_ONLY_ROUTES lists only cloud/move.
Exploit: attacker repo commits a `linkedHub` naming a hub this Mac holds a credential for (gate-b-sec4 M1 threat) + canvas/comment text steering the AI chat to `maude design curl-local --method POST http://127.0.0.1:<port>/_api/sync/link/confirm`; the permission card shows a loopback curl, not the hub; approved → link recorded, sync restarts with the victim's token → attacker files upload into the victim's hub and hub files land in an attacker-remote repo. The `link` verb (actions/verbs.ts:241, human tier) reaches the same consent inside an AI session gated only by the card.
Fix: refuse unless `sec-fetch-site === 'same-origin'` first (as cloud-move); add the route to HUMAN_ONLY_ROUTES; `maude design link` refuses when `isAiSession()` (cli/lib/confine-root.mjs); fail-first test.
