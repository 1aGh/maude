## Findings

### M1 — medium — a hub-pushed canvas path can land in runtime folders and `node_modules` on the cell's studio
- **Where:** `apps/studio/sync/index.ts:4222` and `:5086`; the gate at `:7210-7211`; the validator at `apps/studio/sync/canvas-path.ts:77` and `:192`.
- **The disagreement:** the hub boundary now allows a canvas outside the declared folders on every pull, including the strict post-boot pulls.
  - The validator's folder-name rule (`COMPONENT`) allows a leading `_` or `-`, and allows `node_modules`.
  - The classifier refuses all three (`DIR_SEGMENT`, `relShape`), and so does the new scan (`scanGroupPaths`, `index.ts:6870`).
  - The hub's kernel already accepts these paths when no folders are declared (`kernel.mjs:181`).
  - Before this range, the cell's studio only accepted such a path during the one-time first link of an empty folder.
- **Failure scenario:**
  1. A teammate with edit rights creates document `ws/<w>/main/_state-x`, with `syncMeta.path` set to `_state/x.tsx`. Rule 7 passes because the path turns back into the same slug, `_state-x`.
  2. The kernel accepts it, and the cell's studio writes `<designRoot>/_state/x.tsx` plus its siblings.
  3. The same works for `_history/<slug>/…`, `_comments/…`, `_untrusted/…`, `-x/…` and `node_modules/<pkg>/index.tsx`.
  4. The scan never lists these folders, so the pull pin at `index.ts:4853` is never released. The canvas keeps receiving hub writes for the life of the process — the same class of bug the comment above that line describes.
- **What limits the damage:** the overwrite guard (`existsSync`) means nothing existing is replaced. The build refuses imports of runtime state (`isRuntimeTarget`) and bare `node_modules` imports. Canvas-ness by path (`isCanvasFile`) refuses `_` folders and the skip-list folders, so none of this can be opened as a frame. That leaves stray writes into the runtime-state folders (DDR-115) and a wedged pin, but no code execution.
- **Fix:** while folders are undeclared, require the first path component to match the classifier: start with a letter or digit, and not be `node_modules` (case-insensitive). The cleanest place is `validateCanvasPath`, which the hub and studio share, so the kernel gets the fix too. Add a pull test for `_state/x.tsx`, `-x/y.tsx` and `node_modules/p/index.tsx`.

### L1 — low — the hub's own file writer (workspace agent) was not given the boundary
- **Where:** `apps/hub/src/workspace-agent.mjs:517-523`. It calls `resolveCanvasBodyRel` without `allowUndeclaredGroup`, so with no config it falls back to the default `system`/`ui` folders.
- **Scenario:** a teammate creates `components/new.tsx`.
  - The kernel accepts it.
  - The workspace agent turns down the path and writes the fallback `<root>/components-new.tsx`.
  - The cell's studio, under the boundary, writes `components/new.tsx`.
  - Both files have the slug `components-new`, a collision that takes the canvas out of sync.
- This is an integrity problem, not a confidentiality one. Severity depends on whether both writers really run against one checkout under cell pairing; the header in `cell-pairing.ts` suggests they do. Please verify.
- **Fix:** give the workspace agent the same `allowUndeclaredGroup` the kernel computes, after the M1 fix.

### L2 — low (an accepted risk worth recording) — shared `.tsx` modules in undeclared folders become editable by editors
- On an undeclared hub, a file like `components/Button.tsx` is now synced as a canvas document. Before, it was owner-only code.
- The import walk (`access/closure.ts:683-700`) still treats it as a module: it isn't marked as a canvas, has no meta, board or stored grant. So it is still inlined into the frames of other canvases that import it.
- This doesn't widen the per-canvas scoping (C4). Project-wide editors can already edit any canvas, and a canvas-only session can't write documents outside its grant. What changes: editors can now change shared component code that only the owner could change before.
- **Fix:** none needed if Michal's decision stands. Note it in the decision record.
