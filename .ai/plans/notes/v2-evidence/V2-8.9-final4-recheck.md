## New findings

**L1 — Low — at the 20 000 cap, holds fail open.**
- Where: `journal.mjs:345-352`. `insertHold` returns `false` and logs once to the server log. The path is not held. After a later declaration it classifies `code-module` and goes onto the code lane. That is Att L1 again.
- Scenario:
  1. While the hub is undeclared, an editor creates about 20 000 canvases through the doc lane. Holds need real files, and pruning frees slots, so the files must stay.
  2. The editor creates one more canvas, `lib/x.tsx`, which is not noted.
  3. The owner declares folders.
  4. The next studio report or walk journals the editor's bytes as owner code.
- The owner is never told. The warning goes only to the server log, and the held list does not show the overflow.
- Limits: needs editor rights, is very noisy, and is the same residual as the walk cap (info C).
- Fix: fail closed. Persist an "overflowed" flag in `journal_meta`. While it is set, either:
  - classify `never` every boundary-canvas path that has no owner code row, or
  - have the config door refuse a declaration until the owner confirms.
- Also show the overflow in the owner's held list.

**L2 — Low (rest of N1) — a hold with no owner sha never lifts while its file exists.**
- Where: the only lift is the same-sha check (`file-manifest.mjs:178-182`), and a hold with no owner sha (`code_sha = NULL`) can never match it. A door DELETE of the path fails at admission, because `resolveCheckoutFileWrite` returns `never` and the door answers 400 (`file-door.mjs:420-428`).
- Scenario:
  1. While the hub is undeclared, an editor creates canvases at paths the owner will use for code later (`lib/index.tsx`, `components/Button.tsx`).
  2. Each is a real teammate body, so holding it is correct (see "checked, clean").
  3. After the declaration the owner sees the paths as held, but cannot push code there or delete the file through the file plane.
  4. What is left for the owner: move the folder into the canvas folders, or remove the canvas through the doc lane. I did not verify that the second is reachable once the path is outside the declared groups.
- The owner's own boundary canvases from the undeclared window end up the same way.
- Fix (as proposed last round): let a project-wide owner-role write or delete through the door release the hold. That is the owner adopting the path, and it is the same bar as the config door.

## Infos
- **I1.** The `holding` awareness field is editor-only in meaning, but no strip set covers it: not `READ_ONLY_STRIP` (`room.ts:201-204`), not the format-gated strip, not the hub's `present-strip.mjs:23`. `personHoldsOf` (`holds.ts:49-70`) reads every state in the room, and the agent route refuses an AI write to a held element as `soft-locked`. So a viewer or a format-gated session can keep refreshing `holding` and block AI edits on one element at a time. This was already true for read-only sockets. Fix: add `holding` to `EDITOR_ONLY_FIELDS` in both copies.
- **I2.** On wake, a canvas created after the last generation is missing from the restored checkout bundle. The tail restores its hold, and the first walk then prunes it (`journal.mjs:1801`). That is safe only while no doc-to-disk writer puts the body back at a path that is now undeclared:
  - The workspace agent re-resolves through declared groups and falls back into a declared folder (`workspace-agent.mjs:506-522`). Its `pathIndex` is rebuilt from the checkout and dropped on retirement (`:410`, `:438`).
  - I did not trace the paired studio's own path memory.
  - Worth a test: wake, then the teammate edits the doc, then assert no `code-module` row appears.
- **I3.** Restore is a union, so a hold released since the last generation comes back after a wake (fail closed, documented at `journal.mjs:430-433`). The owner sees it again with reason `changed-as-canvas`.
- **I4.** Cost and compatibility:
  - Every tail flush rewrites the whole hold set: up to 20 000 paths, several MB per debounced flush.
  - An older hub replaying a new tail counts the hold line as malformed and logs "may be short of rows" on every wake. It is otherwise harmless (`replayTailFromTarget` ignores `malformed` for the epoch).
  - At the cap, the warning also fires for a path that is already held, because the cap is checked before `INSERT OR IGNORE`. Cosmetic.

## Checked, clean
- **Who can still create a hold:**
  - `studio-report` needs loopback plus a non-read-only token (`journal.mjs:1144-1160`), and is noted only when a regular file is on disk (`:607`).
  - `peer-put` is never noted. That is right, because the door refuses `code-module` from a token without the owner role (`file-door.mjs:484`) and has no canvas path.
  - `hydrate` only refills the journal's own file-plane rows, and `canvas-owned` is not a file-plane class (`file-membership.mjs:25`).
  - So every hold sits on a body that is really on disk. While undeclared, the walk notes every boundary canvas whoever wrote it, by design. A teammate cannot plant a hold on an empty path any more.
- **Delete and recreate to launder a hold:** `dropHoldIfGone` drops only on ENOENT/ENOTDIR (`journal.mjs:403-413`). Recreating the same path after a declaration has no hooked lane:
  - the door refuses non-owner code;
  - the kernel and the workspace agent refuse undeclared groups, and the agent falls back into a declared folder;
  - a retirement removes the agent's path entry, so a revived doc resolves its path again;
  - a move back to the path is refused.
  - An unhooked writer under teammate control (git, CLI, agent) already beats the code lane without any laundering.
- **A forged or tampered tail:**
  - A hold line is shape-checked: it must be an array, at most `maxHolds` long, each path `isProjectFileShape`, and malformed entries are counted (`journal.mjs:434-449`, `:953-959`).
  - It can only add holds: denial of service on owner paths, visible to the owner, and pruned when the file is absent. It can never set the lifting sha.
  - It cannot crash replay: `'holds' in` an array is false, null is guarded, and everything runs inside the transaction.
  - The tail key goes through the target's tenant prefix, which this change does not touch. Anyone with bucket write access already has more power through forged rows.
- **Counting:** `INSERT OR IGNORE` keeps `holdCount` right on a re-note (`journal.mjs:295-297`, `:355-358`). `noted` is cleared on release and on prune. Restoring a hold that already exists is skipped and not counted.
- **Tail consumers:** only `journal.mjs`, `journal-e2e.mjs` (now filters the hold line) and the `local-cell.mjs` help text read the tail.
