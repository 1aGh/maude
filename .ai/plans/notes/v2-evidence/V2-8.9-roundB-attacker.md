## Findings (0 high/critical, 4 low)

**A1 · Canvas text can make the AI's run capture the person's own edits (low).** A planted thread or canvas text
gets the agent to run any shell command that merely contains `maude design <verb with effect ≠ none>`. Examples:
`echo maude design export`, `grep "maude design annotate" docs`, or a command the person then denies. The stage
opens on the first `tool_call` (`acp/index.ts:428`), before permission is decided and with nothing written. With the
stage open, `action-stage.ts ownerOf` hands any watcher change to an existing canvas to the only open run. The
person's own outside edits during that turn (VS Code saves, git pull/checkout, a terminal verb) are then staged into
the AI run. They get published as "Made by AI" and folded into the AI's one-step Undo. If the run fails it is held,
and Discard reverts the person's edit.
The reverse gap: the regex misses `bash -c "maude design …"`, `$(which maude) design …`, absolute paths and
`maude-safe`. H1 is not bypassed, because approval goes through `audience.ts writerVerbCall`.
Fix: open the stage on `tool_call_update status:completed`, or once permission is granted; match the verb with
`writerVerbCall`'s tokenizer; let the verb `claim` its own writes, so the "only open run" fallback never applies to a
Bash-opened stage.

**A2 · Squatting a person's presence clientID after a disconnect (low).** `room.ts ownAwareness` lets a connection
claim any unowned clientID, and a disconnect frees it. Another connection in the room has seen that id in
broadcasts and claims it first, with the victim's name and colour. When the victim reconnects with the same id
(y-protocols keeps it across a reconnect), their updates are dropped as owned by another connection. The result is
impersonation plus lock-out. The forgery itself is narrower than before this change, but the lock-out is new. Fix:
bind the clientID to the verified person key, keep a short tombstone after disconnect, and allow reclaim only by the
same identity.

**A3 · The invite toast names the thread's author as the inviter (low).** `invitedHereWords` reads the thread's
stored author. The cloud only pattern-checks the invite's thread id (`access-forward.mjs:587-591`) and never checks
that the thread belongs to `invited_by`. So the inviter (owner-only) can point the invite at someone else's thread,
and the newcomer reads "<that person> invited you here — their comment is on X". Fix: name `invited_by`'s display
name in the toast, or refuse a thread whose author isn't the inviter.

**A4 · A stale or planted `_server.json` speaks through a trusted helper's output (low, creativity finding).**
`server-up.sh` reads `port`/`pid` with `jq -r` and accepts any string. A force-committed
`"port":"1@attacker.example/x?"` makes `curl http://localhost:$PORT/_health` reach the attacker's host. New this
round:
(1) a deliberately hanging host (curl 28), or a port such as 5432 on a local Postgres, makes the script refuse to
start every time (DoS of `/design:*`);
(2) the new echo lines print the file's PORT/PID into the agent's tool output;
(3) the probe can run up to 17 s.
Fix: require `^[0-9]{1,5}$` / `^[0-9]+$`, otherwise treat the file as stale; probe 127.0.0.1; never echo values read
from the file.

**Info (not counted).** The comment door is a new egress for a commenter's AI. Its comment now reaches the canvas's

`error` (up to 300 characters) is passed back to the verb's output. Keep the prompt tier, and consider returning
only the error code to AI callers.
