## Chains

### C1: A canvas can keep a real "Export failed" / "couldn't save" notice off the screen (Medium)
- **Preconditions:** a malicious canvas is the active one. No focus or gesture is needed: `annotation-to-comment` is gated on the active canvas only (`gate: 'active'`).
- **Steps:**
  1. The user starts an export, or a save or sync fails, and the shell posts a trusted error notice.
  2. The canvas posts `{dgn:'annotation-to-comment', id:'x<n>'}` in a loop.
  3. Each message makes a server call (`turnIntoComment`), and every refusal becomes a new *shell-authored* error notice (`use-canvas-bridge.jsx:932-935`, a fresh `notice-N` id each time, 10 s each, nothing limits the rate). Opening the AI chat in a browser does the same (`:963`).
- **Why r2 makes it worse:** `notifications.tsx:348-350` now shows one notice at a time, shell notices first, newest first. The flood counts as "shell", so it always beats the real notice. Hidden notices keep paused clocks, so the real one sits *behind* the whole flood: 360 bogus asks hide it for about an hour. Screen readers also announce every flood notice.
- **Impact:** the user keeps working after a failed save or export without knowing. This breaks the r2 promise in the code comment ("canvas text never pushes a trusted notice off the screen"), because canvas-*triggered* shell text counts as trusted. The trusted list in `entries` also grows without limit.
- **Fix:**
  - Give notices the canvas can trigger one fixed reused id each (e.g. `id:'annotation-to-comment'`), and rate-limit them like `notifyCanvasText`.
  - Rank only shell-originated notices above canvas ones.
  - Show waiting errors first-in, first-out, rather than newest first.

### C2: "New project" placed inside a folder an attacker controls (Medium, conditional)
- **Preconditions:** the user chooses Advanced › "Choose another folder…" and picks a folder inside a tree a collaborator controls. Plausible cases: a Syncthing or Dropbox team share, or a downloaded or cloned repo. `checkLocation` accepts any non-hidden, non-`Library` folder under home, or any `/Volumes/<drive>` (`create-local.ts:50-82`, `home/routes.ts:426`). Before r2 the base was always `~/Maude`.
- **Steps:**
  1. The attacker plants `.git/config` with `[core] fsmonitor = sh payload`, and/or a `CLAUDE.md`, at the share root.
  2. The user creates "a new project" there. To the user it reads as a fresh, empty project.
  3. Every system-`git status` with cwd inside the project finds the *parent* `.git` and runs fsmonitor. Two paths reach it:
     - The studio git service with `MAUDE_USE_SYSTEM_GIT=1`: `runGit` passes neither `core.fsmonitor=false` nor `GIT_CEILING_DIRECTORIES` (`git/service.ts:398-404`).
     - Claude Code's own git calls. This attack class is live: [THN, Sep 2026](https://thehackernews.com/2026/09/malicious-git-configs-can-make-claude.html), [CVE-2026-55607](https://www.sentinelone.com/vulnerability-database/cve-2026-55607/).
  4. Helpers that fall back to `git rev-parse --show-toplevel` when `CLAUDE_PROJECT_DIR` is unset (`bin/server-up.sh:45`, `prep.sh:58`, `bootstrap-check.sh:30`) resolve to the attacker's parent folder and its `.design/`. I did not check whether `MAUDE_SESSION_ROOT` pins these.
- **Impact:** code execution under the user's account (system git), or a parent `CLAUDE.md` steering the auto-approving ACP session. The latter is unverified: `bridge.ts:712` says the project CLAUDE.md "is read via a separate path".
- **Pre-existing vs new:** opening an existing folder already carries this risk. What r2 adds is the *create* path, which users treat as trustworthy.
- **Fix:**
  - In `checkLocation`, refuse (or warn on) a location with an ancestor `.git`, `.design` or `CLAUDE.md`.
  - Add `-c core.fsmonitor=false` and `GIT_CEILING_DIRECTORIES=<dirname(root)>` to `runGit` (as `acp/repo-private.ts:41` already does).
- **Sub-note (low, unverified):** `parts[0] === 'Library'` is case-sensitive. If `realpathSync` keeps the input's casing on case-insensitive APFS, `~/library/...` passes. Compare case-folded.

## Single findings

### F3: A canvas can open the native image picker whenever it likes, and the picked file goes to Assets, which syncs (Low)
- **How:** with the canvas focused, posting `tool-panel-open {panel:'image'}` (500 ms quiet period) opens the app's *native* picker (`image-pick.js:109`, `pickMediaFiles` "needs no page activation"). This is the first canvas-triggerable OS dialog. A pretext like "Maude needs a photo of your ID to verify export" works on it.
- **Result:** the chosen image goes into the project's Assets (`uploadAsset`) and syncs to every collaborator, so an image-only file leaves the machine.
- **Fix:** for requests the canvas starts, show a shell-drawn chip ("Choose a picture for <canvas>…") before the native dialog. Back off after two cancels.

### F4: Recent colours accept image references, share one key across projects, and are shared by everyone in a cell (Low)
- **Accepts `url(...)`:** `recentOk` (`recent-colours.js:15`) and `RECENT_COLOUR_RE` (`ui-prefs.ts:207`) both let `url(/_api/…)` and `image-set(…)` through. Hydrated values are drawn as swatch `background` in the *trusted shell*, which fires same-origin GETs (CSP `img-src 'self'` stops external hosts). Clicking one writes it into the source as a "colour".
- **Key collision:** the list key is `cfg.name` (`recent-colours.js:31`), which a collaborator sets in the committed config. Two projects with the same name share one Recent list.
- **Cells:** one `prefs.json` sits behind `/_api/ui-prefs` with `unsafe:'session'` (`apps/hub/src/studio-manifest.mjs:106`). Any member, viewer included, can plant entries that editors then see and click.
- **Fix:**
  - Accept only values that pass `isCssColor` or the `var(--x[, colour])` form, both on the server and on hydrate.
  - Key by project id or root hash, not by name.
  - Refuse `recentColours` in a cell, or store it per member.

### F5: The ds-check role-fallback exemption can be forced (Low, rule integrity only)
- **How:** set `'--bg-3': 'initial'` on the element, then use `background: 'var(--bg-3, #ff00ff)'`. The fallback always applies, the literal is exempt (`ds/canvas-check.ts:138-158`), and S1 / strict DS fidelity is bypassed. A canvas can then ignore a DS switch with no finding raised.
- **Fix:** keep the exemption only when the file never declares that role name itself. Flag a local declaration of a registry role, especially `initial`, `unset` or `revert*`.

## Checked, no finding
- **`place-image` forge, replay, redirect:** none.
  - The shell checks `e.source === window.parent`.
  - The shell picks the target canvas from `activePath` behind the focus, rate and edit-rights gates, never from the message.
  - It posts with `targetOrigin = canvasOrigin`.
  - The canvas can already send `edit-op image.place` itself, so forging `place-image` gains nothing.
  - The shell writes only through the existing `uploadAsset`.
  - Informational: in a browser, a dialog that never opens leaves `forCanvas` stale, so a file later handed to the input lands on that older canvas.
- **Mode-switch live region:** fixed `MODE_WORD` strings only.
- **Colour popover injection:** `isCssColor` refuses `;{}`, and `/_api/edit-css` writes into a JSX style string, so neither a planted token nor a typed value can break out of the declaration.
