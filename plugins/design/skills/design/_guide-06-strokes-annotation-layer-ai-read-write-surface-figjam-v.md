## Whiteboard annotation layer — AI read/write surface

Separate from element-pinned comments above: the **annotations** (stickies, text, shapes, arrows, marker strokes, images, stickers — the Preview tools) persisted as `<designRoot>/<slug>.annotations.json` — a file of flat element records with stable ids, where sections are containers (DDR-242; format in skill `whiteboard` § Overview). It is a **two-way medium** — the user sketches/brainstorms on it, and the agent both reads it (with artboard AND element context) and writes to it (stickies, labelled shapes, bound connectors, whole tidy templates). Both verbs go through `maude` (DDR-062), never a raw bin path.

**Full spec lives in skill `whiteboard`** (feature-whiteboard-ai-toolkit, DDR-151) — the geometry manifest (`maude design canvas-rects`), the READ verb's element-level context (`read-annotations --rects`), the WRITE verb's coordinate-free placement (`annotate --in`/`--pin`/pointer arrows), the registry-driven `update`/`move`/`reparent`/`reorder` element ops, the `--board` template engine (retro/kanban/social-calendar/roadmap/brainstorm/checklist/user-flow), and the trust model. Format 2 added optional fields an agent reads and writes through the same two verbs, never by hand: a sticky's `resolved` (`annotate --resolve`), an image's `sticker` (`annotate --sticker <pack>/<id>`), an arrow end bound to a canvas artboard or element (`annotate … "to": "el:<artboard>/<id>"`, read back as `toHost`), `parentArtboard`, `source` (a FigJam import: `import-figma --board <url> --into <canvas>`) and `timeRange`; `read-annotations --selection <ids>` resolves what the selected notes point at. Votes, ballots and stamps are people's — read, never written. `/design:board` drives the read→understand→author→verify loop end to end. Reach for it when the feedback references the user's sketches/stickies, asks to add a note/label to the canvas, or names a template ritual (retro, kanban, roadmap, …).
