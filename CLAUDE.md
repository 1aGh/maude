# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`Maude` — a Claude Code marketplace (defined by `.claude-plugin/marketplace.json`) shipping two plugins plus an npm-published CLI. Project was renamed from `md-claude` in v0.15.0; see [`docs/MIGRATING-MD-CLAUDE-TO-MAUDE.md`](docs/MIGRATING-MD-CLAUDE-TO-MAUDE.md).

- **`plugins/design`** — canvas-first iteration on TSX/JSX mocks under a project's `<designRoot>` (default `.design/`). Includes a Bun dev server (`apps/studio/server.ts`, DDR-009) that injects an inspector overlay for Cmd+Click element selection and tracks active-canvas state over WebSocket.
- **`plugins/flow`** — generic agentic workflow loop with a second-brain `.ai/` workspace. Project-agnostic via `<project>` placeholders + per-repo `.ai/workflows.config.json` (schema at `plugins/flow/.claude-plugin/config.schema.json`).
- **`cli/`** — `maude` CLI (entry `cli/bin/maude.mjs`, subcommands in `cli/commands/`). Published as `@1agh/maude` on npm. Bins: `maude` (primary), `mdcc` (legacy alias — prints deprecation warning, drop in v0.17.x), `maude-safe`/`mdcc-safe` (per-call platform-detection fallback), `claude-design-server` (direct dev-server alias).

The npm package, the design plugin, the flow plugin, and (since phase-32) the native desktop shell all share a single version — `package.json`, `plugins/design/.claude-plugin/plugin.json`, `plugins/flow/.claude-plugin/plugin.json`, **`apps/desktop/src-tauri/tauri.conf.json`** (drives the auto-updater's `{{current_version}}`), and **`apps/desktop/src-tauri/Cargo.toml`** `[package].version` (the native About box) must move together. `scripts/bump-version.sh` bumps all of them; `scripts/check-version-parity.sh` asserts them; CI enforces parity (`.github/workflows/version-parity.yml`). See [DDR-126](.ai/archive/decisions/DDR-126-native-distribution-auto-update-and-security-posture.md) for the desktop distribution + auto-update + signing-key model.

## Decision memory — this repo is kgai-active

**Before re-deriving why anything is the way it is, query the graph.** 523 nodes — 387 decisions (graph-native `/flow:record-ddr` writes plus the 226 archived DDR files) and 136 RCA / security-review / code-review / system-review verdicts — live in a [kgai](https://github.com/kgaidev/kgai) knowledge graph, scope-tagged `repo:maude` / `dept:dev`. `knowledgeGraph` in `.ai/workflows.config.json` turns it on; the resolver + recipes are the **`flow:kgai-backend`** skill.

```sh
kg search "<topic>"              # ← START HERE for "what did we decide about X"
maude kg context --about "<element>"   # why THIS element is the way it is
kg query "<cypher>"              # typed edges (SUPERSEDES / EXTENDS / EVIDENCE_FOR) live in LINK.kind
maude kg doctor                  # is the graph active here?
```

**`search` and `query` are `kg` verbs, not `maude kg` verbs** — `maude kg` passes through only `context` and `ingest` (its other verbs are `resolve`/`doctor`/`check-upstream`/`session-sync`/`sync`/`scope`/`import`/`record-log`), so `maude kg search …` exits with `unknown verb`. Reach for the bare `kg` binary for reads; use `maude kg` when you want the resolved scope + capability gate.

`kg context --about` on a broad area returns only that area's **head** decision (`dev-server` alone is linked from 19), so reach for `search` first on topical questions.

**A plan's own task list can lag reality.** `~/git` is a Syncthing tree with concurrent sessions (see the root `CLAUDE.md`), and work on a plan's files can land outside `/flow:execute`'s checkpoint loop with nothing updating the plan doc or the graph's per-task state. Before trusting a plan's checkboxes as "still open," check `git log --oneline -- <files it names>` — feature-fast-video-export (2026-08-12) turned out three-quarters shipped already.

**The graph holds the FULL decision text — it is self-sufficient.** Each node stores the entire source document (`rationale`) plus `path`, `date`, `tags` and typed edges, so "what alternatives did we reject, and why" is answerable from `kg` alone, with no file open. The committed log is ~7.5 MB for this corpus; that's the price of not depending on the working tree.

| | in the graph | on disk |
| --- | --- | --- |
| `.ai/archive/decisions/*.md` (226, highest DDR-225) | **full body** + tags + `SUPERSEDES`/`EXTENDS`/`REFERENCES` edges | committed. Still the **authoring surface** (kgai has no editor — you write the file, then ingest) and ~1175 references across 155 files point at these paths. |
| `.ai/archive/logs/**` (128) | **full body** + date + `EVIDENCE_FOR` edges to cited DDRs | **gitignored** — the graph is their only inheritable copy. |

After editing a decision file, re-ingest with `maude kg import` (safe — identity converges, props merge). There is **no `--only` flag**: import always walks the whole `.ai/archive/decisions/` corpus, so dry-run it first (`maude kg import --dry-run`) if you want to see the mutation count before writing.

**`/flow:record-ddr` writes to the graph when active** (deterministic `hash(kind:name)` identity — no DDR-number race). The prose now lives under **`.ai/archive/`** (moved 2026-07-28) — it is the authoring surface and a git-native backup, not something the graph depends on. `kg rebuild` replays the committed log, so graph-native decisions survive normal operation; only a wipe-and-reimport (a migration op) rebuilds from files.

**Store layout is load-bearing** (`.gitignore` near the top): `.kgai/store/log/*.ndjson` is **VERSIONED** — it IS the knowledge, one file per install id, `merge=union`, and a fresh clone restores the whole graph with `kg rebuild`. `graph.kuzu` (~80 MB projection) + `kg.config.json` (per-machine install identity) stay ignored — sharing the identity forks the shard. Don't add a blanket `.kgai/` rule; gitignore is last-match-wins and it silently kills the log. Same split in `~/git/.stignore` for Syncthing. Cross-repo trust model: [DDR-189](.ai/archive/decisions/DDR-189-kgai-cross-repo-shared-graph-trust-model.md); desktop bundling: [DDR-190](.ai/archive/decisions/DDR-190-kgai-native-bundling-in-the-signed-desktop-app.md).


There is **no test suite, lint config, or build step** in this repo — the plugins are pure markdown commands/skills/agents plus a zero-dep Node server. Don't invent a `test` script. If you need to verify a CLI change, run `node cli/bin/maude.mjs <cmd>` directly.

## Architecture

### Marketplace layout

`.claude-plugin/marketplace.json` is the entry point Claude Code reads when a user runs `/plugin marketplace add 1aGh/maude`. It lists the two plugins and their source paths. Each plugin has its own `.claude-plugin/plugin.json` manifest plus `commands/`, `agents/`, and `skills/` directories — these are surfaced as slash commands, subagents, and auto-loaded skills inside Claude Code.

### Dev server runtime contract (`apps/studio/server.ts`)

> **Bun is authoritative — [DDR-009](.ai/archive/decisions/DDR-009-bun-runtime-authoritative-for-dev-server.md):** the server runs on Bun (`Bun.serve` + `Bun.file` + `Bun.write` + `Bun.spawn`), distributed as per-platform `bun --compile` standalone binaries via npm `optionalDependencies` sub-packages (mirroring `@anthropic-ai/claude-code`). **There is NO Node fallback** — the pre-DDR-009 zero-dep `server.mjs` was deleted in the post-1.0 hardening pass (it silently served a years-stale feature surface when bun was absent); `maude design serve` from source now refuses loud without bun. **When writing new dev-server code, reach for `Bun.*` APIs instead of `node:http` / `node:fs.readFile` / `node:child_process.spawn`** — `node:path` and `node:url` stay (Bun supports them identically). Tests under `apps/studio/` use `bun:test`, not `node --test` (the `cli/` shim stays Node).

The server resolves the **target repo root** in this order: `--root <path>` arg → `$CLAUDE_PROJECT_DIR` → `process.cwd()`. It deliberately never uses `__dirname` for the project root, because the plugin can be installed centrally (npm global) and serve any repo.

**Path resolution rule ([DDR-045](.ai/archive/decisions/DDR-045-real-disk-path-resolution-for-compiled-dev-server.md)):** every dev-server module that needs a filesystem-relative path MUST import from `apps/studio/paths.ts` (`DEV_SERVER_ROOT`, `DIST_DIR`, `CLIENT_DIR`, `RUNTIME_BUNDLES_DIR`). NEVER compute `dirname(fileURLToPath(import.meta.url))` locally — inside `bun --compile` standalone binaries that resolves to the virtual `/$bunfs/root` and every `existsSync` against it silently returns false. Two production releases (v0.18.0 and v0.18.1) shipped broken because of this bug; the lesson is in DDR-045.

**Patch registration is per package-manager root ([DDR-176](.ai/archive/decisions/DDR-176-per-workspace-patch-registration-for-bun-compiled-sidecars.md)):** `apps/studio` installs via its OWN `bun install`/`bun.lock` (DDR-009), fully independent of the root `pnpm-workspace.yaml`. A `patchedDependencies` entry added at the root (e.g. the `css-tree`/`csso` bun-compile-compat patches under `patches/`) does NOT reach a dependency that also resolves inside `apps/studio`'s tree — it needs its OWN matching `patchedDependencies` entry in `apps/studio/package.json`. Skipping this shipped two broken releases (v0.44.0, v0.45.0: every compiled `maude-server` sidecar crash-looped on boot with `Cannot find module '../data/patch.json'`) before the lesson landed in DDR-176. When adding a root-level pnpm patch, check whether the patched package is also reachable from `apps/studio` and mirror the entry there.

It writes three runtime files into `<designRoot>/` that the orchestrator (`/design` slash command) relies on:

| File | Role |
| ---- | ---- |
| `_server.json` | `{ pid, port, url, started }` — orchestrator uses this to detect a live instance instead of starting a duplicate. |
| `_active.json` | `{ active, open_tabs, selected, last_change }` — the injected inspector pushes the user's currently-selected element here over WebSocket so `/design:edit "<feedback>"` can scope edits. |
| `_history/<slug>/` | Auto-snapshot stack per canvas, consumed by `/design:rollback`. |

These files are user-facing runtime state — when changing the server, keep the schemas backwards-compatible or update both producer and the consuming commands (`plugins/design/commands/*.md`) in the same change.

**Runtime-state taxonomy is canonical in [DDR-115](.ai/archive/decisions/DDR-115-per-user-camera-split-and-runtime-state-taxonomy.md).** What's IGNORED (per-machine/per-user runtime: `_canvas-state/` incl. the `<slug>.view.json` camera, `_state/`, `_chat/`, `_comments/`, `_untrusted/`, `_history/`, `_trash/`, `_draw/`, `_smoke/`, `_server.*`, `_active`/`_sync`/`_preflight`/`_locator`/`_export-history.json`) vs VERSIONED (`*.tsx`, `*.meta.json`, **`*.annotations.svg`**, `system/**`, `config.json`) must agree across FOUR lists — `apps/studio/git/service.ts` `isMaudeRuntimeState`, `cli/lib/gitignore-block.mjs`, the repo `.gitignore`, and (feature-sync-file-plane) `isRuntimeStateRel` in `apps/studio/sync/file-membership.ts` **+ its byte-identical `apps/hub/src/file-membership.mjs` mirror** (the file plane's `never` half — a runtime-state path that leaks here would SYNC to peers). They drifted once; when adding a new `_*` runtime path, update all of them together. The classifier copy has a tripwire — `apps/studio/test/sync-file-membership.test.ts` imports both `isMaudeRuntimeState` and `isRuntimeStateRel` and asserts agreement on a fixture list, so drift between those two is a red test; the `.gitignore`/`gitignore-block.mjs` pair still has no such pin. A canvas's pan/zoom (`viewport`) is NEVER in the versioned `.meta.json` — it lives in `_canvas-state/<slug>.view.json` (GET merges it back, PATCH splits it out; `last_modified` is stamped only on a layout change).

**Canvas-origin routes live in TWO allowlists — keep them in sync.** A route reachable from the (untrusted, DDR-054) canvas iframe must be added to BOTH `CANVAS_SAFE_API` (`http.ts`, gates the `fetch` fall-through) AND the `startCanvasServer` `routes` map (`server.ts`). Bun matches `routes` before `fetch`, so listing it only in `CANVAS_SAFE_API` makes the route **404 from the canvas origin** (the bug that bit Phase 23's `/_api/asset`). Guard it with a `GET → 405` assertion in `test/canvas-origin-gate.test.ts`. Conversely, a privileged route (file-write, export, `/_config`) must be in NEITHER. See [DDR-088](.ai/archive/decisions/DDR-088-canvas-media-vocabulary-and-asset-write-surface.md).

**Captures never render a canvas on the main origin — and the capture origin is not a third allowlist** (decision `v2-2.8-read-only-capture-origin`). While the origin split is on, the main origin answers **every** `/_canvas-shell(.html)` request with a **307 to the capture origin** — fail closed: the shell builds its module URL from the request's own `designRel` + `canvas`, so the server never tries to predict which module a URL loads. The capture origin is a third loopback listener (`startCanvasServer(0, { capture: true })`) that reuses the SAME `routes` map + `isCanvasSafeRoute`, behind one gate (`captureRefusal`, applied to the routes AND `fetch`): GET/HEAD only (every write → 405), no WebSocket upgrade, no service worker, loopback Host only — under the strict canvas CSP the render worker already captures with (DDR-232). Every headless caller — exporters (`canvasShellUrl`), `maude design screenshot`, smoke, perf, canvas-rects, visual-sanity — follows the redirect, so none of them names the capture origin; don't add its port to `_server.json` or point a new caller at the main origin. Planted canvas code inside a capture therefore reaches no privileged route and writes nothing. Two named exceptions stay on the main origin: Maude's own local harnesses, matched EXACTLY (`?canvas=_draw/<slug>.proof.tsx` / `_photo/<slug>.bgremove.tsx` with no other parameter — `isLocalHarness`; their content is still a residual, see V2-2.8), and everything when the split is OFF (`MAUDE_CANVAS_ORIGIN_SPLIT=0`, which also turns TSX sync off). Not in a cell (no capture listener; the render worker already captures on the canvas origin). `test/acl-l21-capture.test.ts` pins all of it. **Canvas-origin answers may also be narrower than the main origin's:** `/_api/git-committers` serves the canvas origins a no-e-mail projection (`canvasCommitters`, decision `v2-2.8-s6-committers-projection`) while the shell keeps the full list — when a canvas-safe route carries personal data, project it there rather than dropping the route.

The server fails loud if launched from a directory without `.design/` rather than serving an empty UI — preserve this behaviour, it's load-bearing for debugging "wrong project root" cases.

**Boot self-heal + the `MAUDE_NO_AUTOBUILD=1` escape hatch ([DDR-044](.ai/archive/decisions/DDR-044-marketplace-install-vs-npm-install-artifact-strategy.md)).** On a fresh marketplace-cache install the server runs `bun install --production` + `bun run build.ts` on first launch and writes `_server.json` only once the artifacts exist. Set `MAUDE_NO_AUTOBUILD=1` for read-only filesystems (the server then exits 1 with a remediation message instead of building) — and **use that flag for any in-session verification boot from this tree**, since the dev self-heal regenerates unminified bundles over the committed release artifacts (see the rebuild rule under "In-app What's New feed").

The shared canvas library (`DesignCanvas`, `DCSection`, `DCArtboard`, helpers, hooks) lives at **`apps/studio/canvas-lib.tsx`** — single source, ships with the dev-server install. Canvases import it via the virtual specifier `@maude/canvas-lib`, which the dev-server's Bun.build plugin resolves to that file. (Pre-v0.15.0 canvases used `@mdcc/canvas-lib` — the legacy specifier is no longer supported; update existing canvas imports if you upgrade from before the rename.) Edit there; the http-layer file-watcher broadcasts a hard reload to every open canvas iframe on change. Per [DDR-025](.ai/archive/decisions/DDR-025-canvas-lib-single-source-in-dev-server.md), there is no project-side copy — downstream projects that still carry a legacy `<designRoot>/_lib/canvas-lib.tsx` get a one-shot deprecation warning at boot and the file is ignored.

The **draw geometry engine** (`apps/studio/draw/`) is the "draw as code" layer behind `/design:draw` + `draw-agent` ([DDR-070](.ai/archive/decisions/DDR-070-svg-generation-geometry-engine.md)): pure-TS `primitives` → `geometry` (PCHIP splines / A* connector routing / optical corrections) → `palette` (WCAG + OKLCH) → `layout` (`diagram()`, label solver) → `serialize` (one node tree → SVG string **and** JSX, the DDR-067 single-source invariant) → `optimize` (SVGO — the one new dep, [DDR-071](.ai/archive/decisions/DDR-071-svgo-dependency.md)). React-free root (DDR-067); disk paths via `paths.ts` (DDR-045); reached at runtime through the `draw-build` / `draw-proof` / `svg-optimize` verbs. The `DrawProof` canvas-lib export renders a mark across the 16/24/48/256 × {light, dark, single-color flatten} verify ladder.

### Plugin command naming

Two conventions apply to every command, skill, and agent under `plugins/{flow,design}/`. See [DDR-004](./.ai/archive/decisions/DDR-004-flow-command-naming-prefix-convention.md) (group-prefix filename) and [DDR-191](./.ai/archive/decisions/DDR-191-revert-plugin-name-prefix-claude-code-now-namespaces.md) (bare `name:` — supersedes the now-wrong [DDR-006](./.ai/archive/decisions/DDR-006-plugin-namespace-in-name-frontmatter.md)).

**1. `name:` frontmatter MUST be the bare slug — no `<plugin>:` prefix.** Every file declares its unqualified name in the `name:` field — e.g. `name: resume`, `name: edit`, `name: a11y-auditor`. Claude Code adds the `<plugin>:` namespace itself at registration time (fixed upstream in Claude Code 2.1.216 — previously #22063 stripped it, which is why DDR-006 baked the prefix in by hand; that workaround now doubles it, e.g. `/design:design:new`). **Do NOT add the plugin prefix** — this is load-bearing the other direction now. Both `/flow:help` and `/design:help` parse `name:` and render `/<plugin>:<name>` (prefix added by the template, not present in the field). `subagent_type:` references to one of our own plugin agents DO need the prefix (`design:draw-agent`, `flow:security-auditor`, …) — the runtime's added namespace applies before the Agent tool ever sees the value, so callers must supply it even though the declaring file doesn't. `cli/lib/plugin-name-namespace.test.mjs` guards both halves of this rule.

**2. Non-daily filenames use `<group>-<verb>`.** Daily verbs (called every feature cycle) stay terse — `plan`, `execute`, `done`, `validate`, etc. Everything else gets a group prefix matching the command's `category:` field — `bug-fix`, `setup-prd`, `record-ddr`, `maintain-clean`. Categories are catalogued in [`plugins/flow/CATEGORIES.md`](./plugins/flow/CATEGORIES.md) and [`plugins/design/CATEGORIES.md`](./plugins/design/CATEGORIES.md). The strict prefix substitutes for the subdirectory namespacing that Claude Code [doesn't support](https://github.com/anthropics/claude-code/issues/2422) (closed not-planned; [#44678](https://github.com/anthropics/claude-code/issues/44678) is the open feature request) — typing `/flow:bug-` autocompletes only `bug-*` members.

**Lone exception:** `init` (both `/flow:init` and `/design:init`) is a bare-verb that mirrors Claude Code's built-in `/init`. The plugin-namespace prefix (`flow:` / `design:`, added by the runtime) keeps them unambiguous against the built-in, so the filename doesn't need a `setup-` group prefix. Documented in both `CATEGORIES.md` files. No other bare-verb exceptions without a DDR.

When adding a new command/skill/agent: pick the group from `CATEGORIES.md`, name the file `<group>-<verb>.md`, and set frontmatter `name: <filename-sans-md>` (bare, no plugin prefix), `category:`, `description:`.

Every flow command/skill is project-agnostic. They read `.ai/workflows.config.json` to resolve a `<project>` placeholder and feature toggles (`boundaries.*`, `motion.*`, `responsive.*`, `skills.*`, `integrations.*`). When adding or editing flow content under `plugins/flow/`, **do not hardcode this repo's specifics** — the same plugin runs against arbitrary downstream repos. Reach for the config; if a knob doesn't exist, extend `plugins/flow/.claude-plugin/config.schema.json` rather than hardcoding.

### `.ai/` skeleton vs. this repo's own `.ai/`

`plugins/flow/templates/ai-skeleton/` is the template that `maude init` copies into a target project. This repo also has its own `.ai/` directory at the root — that's Maude *dogfooding* flow on itself (see README "Local development" section). **The two are independent.** Edits to `plugins/flow/templates/ai-skeleton/` only affect future `maude init` runs in other repos; edits to this repo's own root `.ai/` only affect work on this repo.

`cli/commands/init.mjs` does string templating during the copy: it replaces `PROJECT_NAME` and rewrites the `$schema` ref in `workflows.config.json` from a relative path to an absolute GitHub raw URL (because after npm install the schema is no longer at a stable relative location). When changing the skeleton, keep this rewrite in mind for any files added to the `TEMPLATED` list.

### Published npm surface

`package.json` `files` is intentionally minimal — only `cli/`, `apps/studio/`, `plugins/design/templates/`, `plugins/flow/templates/`, the flow config schema, the per-plugin `dependencies.json` + `dependencies.schema.json`, `LICENSE`, and `README.md` ship to npm. The plugin commands/agents/skills/**hooks** (`plugins/*/commands/`, `plugins/*/hooks/`, etc.) are **NOT** published via npm — they reach users through the Claude Code plugin marketplace mechanism (`/plugin install`). When adding a new top-level directory that the CLI needs **at npm runtime**, add it to `files` or `maude` will break for end users. (Dep manifests ARE in `files` because `cli/lib/preflight.mjs` reads them at runtime; `hooks/hooks.json` is NOT, because only Claude Code's plugin loader consumes it, from the marketplace clone.)

### Dependency manifests + config health (`maude doctor`)

Phase A ([DDR-058](.ai/archive/decisions/DDR-058-maude-doctor-deps-config-quality.md)) added one umbrella diagnostic. `maude doctor` (`cli/commands/doctor.mjs`) reports, in one report: missing dependencies (per-plugin, sourced from `plugins/<plugin>/dependencies.json` via `cli/lib/preflight.mjs`), `.ai/workflows.config.json` schema errors (`cli/lib/config-lint.mjs`, Ajv 2020-12), stack drift, and missing quality-gate declarations (`cli/lib/stack-detect.mjs`). `--fix` is never silent (per-dep install prompt; config edits are additive and never overwrite a user value). **Slash commands call the libs directly — no `maude doctor` CLI roundtrip.** There is deliberately **no `maude quality run` / `maude config validate` / `maude config diff`** subcommand (see the `feedback-no-redundant-tooling-over-pnpm` memory).

**Quality gates** live in `workflows.config.json` → top-level `quality` (flat `gate → shell-command` map; `additionalProperties: {type: string}`, free-form names). Flow commands read it via `jq` + `eval` per the `flow:quality-gates` skill — `/flow:utils-verify` + `/flow:quick` run `format`+`lint`; `/flow:validate` runs `format → lint → typecheck → tests → build` then any custom gates; `.ai/release-guide.md` pre-flight runs all. The gate set is **per-project, user-owned** — never bake opinionated defaults into the flow plugin or the `ai-skeleton` template (skeleton has no `quality` block; `maude doctor --fix` fills it from detection). This repo's own block mirrors `quality.yml` (lint/typecheck/tests/build + parity/tarball/tokens/site-content drift). **`typecheck` is now present and green** — the v1.0.0 gate set (A2/A3) completed `apps/studio/tsconfig.json`'s `include` (it had no `*.tsx` entry, so 52 tracked files including `canvas-lib.tsx` were reached by NO checker), drove the surface to **0 errors**, and wired `bunx tsc --noEmit` + `scripts/check-tsc-coverage.sh` into `quality.yml` as a required step. The coverage script is the ratchet — it asserts `tsc --listFiles` still covers every tracked non-test `.ts`/`.tsx` under `apps/studio`, so the surface cannot silently shrink again. (The older note here said a tsc gate "would be permanently red"; that was true of the un-repaired surface and is no longer.) `quality.tests` is the **sync lane** (`bun test test/sync-*.test.ts`), matching `quality.yml`'s required job; the full studio suite runs in the separate `studio-suite` job, **blocking since V2-2.13** (its measured CI history named an empty quarantine list; `scripts/test/quality-gates.test.mjs` keeps `continue-on-error` out of `quality.yml` — a flaky test is fixed or quarantined by name in that job's comment).

## Release flow

1. `scripts/bump-version.sh patch` (or `minor`/`major`/explicit `X.Y.Z`) — updates all three version fields together.
2. `scripts/check-version-parity.sh` — sanity check (also runs in CI on PRs touching `package.json` or the design plugin manifest; note the workflow does not currently watch the flow plugin manifest, so don't bypass the local script).
3. `git commit -am "chore: release vX.Y.Z"` → `git tag -a "vX.Y.Z" -m "vX.Y.Z"` → `git push --follow-tags`. **Annotated (`-a -m`) is required** — `git push --follow-tags` only pushes annotated tags, so a lightweight `git tag vX.Y.Z` will silently stay local and *no* release workflow fires (main looks pushed, nothing is published or deployed). Same wording as `.ai/release-guide.md`, which is the authoritative runbook.
4. The `v*` tag triggers `.github/workflows/build-binaries.yml` (job `publish-main`), which re-runs parity, asserts the tag matches `package.json`, and publishes to npm with `--access public --provenance`. The same `v*` tag also triggers `.github/workflows/hub-image.yml` (multi-arch `ghcr.io/1agh/maude-hub`), **`.github/workflows/render-deploy.yml`** (the `maude-render` export service, DDR-230 — image to ghcr + Cloudflare at the tag `apps/render/wrangler.toml` declares, Worker deploy, `/_health` version poll) **and `.github/workflows/cells-deploy.yml`, which rolls the cloud fleet**: it waits for the hub image, builds the cell image at the tag `apps/cells/wrangler.toml` declares (`maude-cell:vX.Y.Z` — written by `bump-version.sh`, asserted against the release tag in CI), pushes it, and `wrangler deploy`s the data plane. **Only a release tag touches the fleet** — a push to `main` runs the data-plane tests and stops. It could never roll the fleet (a byte-identical container config is a no-op) but it *could* put a second set of bytes under an existing tag, and it derived the cell from a stale `maude-hub:latest` (the v0.57.0 failure). `wrangler deploy` is tag-gated too, which is *not* obvious: `wrangler.toml` NAMES the container image, so a deploy reconciles the container config — on the release commit the branch run uploaded the Worker and then failed the rollout with `IMAGE_REGISTRY_DOESNT_CONTAIN_IMAGE`, because only the tag run builds that image (v0.58.0). Urgent fleet changes go through `workflow_dispatch`. The tag CHANGE is what restarts cell instances (env applies at container start; a byte-identical config is a no-op) — never re-push content under an unchanged cell tag and call it deployed. Verify the rollout per `.ai/release-guide.md` § "Verify the fleet actually rolled".

**Release candidates (`vX.Y.Z-rc.N`, V2-2.0) are a separate, narrower channel.** `scripts/bump-version.sh X.Y.Z-rc.N` (then `rc` / `promote`) moves every manifest but leaves the wrangler.toml image tags on the last stable release and What's New entries pending. An rc tag runs only `build-binaries.yml` (npm dist-tag **`next`**, a **prerelease** GitHub release) and `build-desktop.yml`; the hub-image / cells-deploy / render-deploy / selfhost-images filters are `['v*.*.*', '!v*.*.*-*']`, so an rc never touches the fleet, render or `:latest`. The updater feed (`site/lib/updater-feed.mjs`) offers prereleases only to installs already on an rc. Plugins still ship from `main`, so an rc bump on `main` reaches marketplace users. Runbook: `.ai/release-guide.md` § Release candidates; asserted by `scripts/test/release-channel.test.mjs`.

Never bump versions by hand or with `npm version` — the script is the single source of truth for keeping all three manifests in lockstep.

**Import coherence is a release gate — `~/git` is a Syncthing tree with concurrent sessions.** `scripts/check-import-coherence.sh` (run automatically by `bump-version.sh`) asserts that every relative import in a tracked file has a **tracked** target. A `git add` of a SHARED file (`worker.mjs`, `http.ts`, `lib.rs`) can carry another session's in-flight `import './new-module.ts'` into main while the module itself stays untracked: green locally (the file is on disk), fatal in CI, and the failure reads as three unrelated bugs — `ERR_MODULE_NOT_FOUND` in node tests, `Could not resolve` in `bun build --compile`, `E0433/E0425` in Rust. This cost two tag moves in v0.51.0. Fix path when it fires: **land the missing module** (never strip the import from a shared file — that breaks the other session), verify with a clean clone (`git clone file://$PWD /tmp/x && cd /tmp/x/apps/studio && bun install && bun build.ts --release`), then force-move the tag. Stage specific files, never `git add -A`, and check content AFTER committing (`git show HEAD:<file> | grep <sentinel>`).

**The hub release image installs frozen — never add a fresh-resolution Dockerfile.** `apps/hub/Dockerfile` builds with `bun install --frozen-lockfile` against the committed `apps/hub/bun.lock` and copies the resolved `node_modules` into the runtime stage (no second install). This is load-bearing: the image is the one component DDR-054 designates "untrusted to peers," so a fresh `bun install` / `npm install <range>` at build time would let a poisoned transitive land in every self-hoster's hub (DDR-056-adjacent security finding). Bump hub deps via the lockfile, never by re-resolving in the Dockerfile.

**Runtime bundles (`apps/studio/dist/runtime/*.js`) are committed and authoritative for the release.** Both CI jobs (per-platform `build-binaries` matrix + `publish-main`) set `MAUDE_SKIP_RUNTIME_BUILD=1` on the build step, so `pnpm build` reuses the on-disk bundles verbatim instead of regenerating them. Reason: Bun.build's output for `motion`/`motion/react` is environment-sensitive — v0.22.0 shipped a 13 kB `motion_react.js` (working size 155 kB+) because Ubuntu CI's `pnpm build` overwrote the good local bundle with broken regen output. Whatever you commit is what ships. Dev builds skip the regen automatically whenever `dist/runtime/*.js` already exist (runtime bundles depend only on dependency versions, never on source). To regenerate deliberately after a dep bump: `cd apps/studio && MAUDE_FORCE_RUNTIME_BUILD=1 bun run build.ts --release` (release mode, so the output is minified like the committed artifacts). The `check-runtime-bundles.sh` step in CI validates every `dist/runtime/*.js` against the per-slug floor in `.min-sizes.json` — if a maintainer commits a bad bundle, the release fails loud before `npm publish`.

**The packaged app must stay self-contained — bundle the runtime AND the deps for every runtime-spawned surface ([DDR-177](.ai/archive/decisions/DDR-177-desktop-self-contained-runtime-and-bundle-completeness-gate.md)).** The `.app` (and `npm i -g @1agh/maude`) must work on a machine with **no `node`/`bun`/`brew`/`claude`** — the target user never opens a terminal. The ACP adapter and every `maude design <verb>` helper are runtime-spawned, so each needs, INSIDE the bundle, a JS runtime to run it AND its complete dependency closure. The runtime is the already-bundled compiled Bun via `BUN_BE_BUN=1` (adapter: `probe.ts`/`bridge.ts`; helpers: the `bun` shim in `cli/commands/design.mjs`) — never a user-installed one. Helper npm deps are staged **data-driven** from the import graph (`apps/desktop/scripts/helper-deps.mjs` → `stage-resources.mjs`) plus the same set in root `package.json` for the npm channel; the compiled `maude`'s pkgRoot is bridged to `Contents/Resources` (staged `cli/` + `package.json`, `resolvePkgRoot` `.app` probe, `MAUDE_PKG_ROOT`). **When you add a new `maude design <verb>` helper or any runtime-spawned code: its deps stage automatically via `helper-deps.mjs` — but you MUST verify `apps/desktop/scripts/check-bundle-completeness.mjs <built .app> --smoke` is green (runs every verb in a stripped PATH) before release.** This bug (ACP "Working…" hang + every helper "helper not found"/"bun required"/missing `happy-dom`/`svgo`) shipped through ≥2 releases because it was green in `tauri dev` and only broken in the packaged `.app` — the gate exists so that can't recur.

**`apps/studio/dist/client.bundle.js` is REBUILT at package time — the committed copy is NOT what ships.** `MAUDE_SKIP_RUNTIME_BUILD=1` pins only `dist/runtime/*.js` (guarded by `check-runtime-bundles.sh` size floors); the client bundle is regenerated by every `bun run build.ts --release`, so the artifact inside the `.app` routinely differs from `git cat-file -s HEAD:apps/studio/dist/client.bundle.js`. v0.51.1 shipped a desktop app that **opened to a blank window** this way: no crash, no log, React mounted nothing. Two properties hid it — the fault appears **only when `window.__TAURI__` is present** (so every browser check, screenshot helper and `/design:smoke` run is green) and **only in the minified build** (so `tauri dev` is green, and so was the committed bundle). `apps/desktop/scripts/check-client-boots.mjs <built .app>` is the gate: it boots the bundled `maude-server` on a throwaway project, loads the page through the bundled `agent-browser` with a Tauri global injected via `--init-script`, and fails if `#root` has no children. It runs in `build-desktop.yml` right after the self-containment gate. **Run it against the built `.app` before any desktop release** — a green browser and a green `tauri dev` prove nothing about the packaged UI.

This isn't only a "you booted the server" risk — `pnpm test:dev-server`/`bun test` in `apps/studio` has also been observed clobbering `dist/` this way with no server process running at the time (root cause unconfirmed). Run `git status apps/studio/dist/` before AND after any `bun test` run in this tree, not just before/after a server boot, and `git checkout -- apps/studio/dist/...` to revert if it shows unstaged changes you didn't intend.

## Working on plugin internals locally

For testing edits to plugin commands/skills/agents, the README's "Local development" section is the canonical recipe: point the marketplace at the local working tree (`/plugin marketplace add /absolute/path/to/maude`), then `/plugin marketplace update maude` + `/reload-plugins` after each edit. **Test in a scratch project** (`cd /tmp/scratch && claude`) rather than from this repo's directory — otherwise this repo's own `.ai/` workspace tangles with the plugin you're testing.

For dev-server code changes specifically: kill the running server (`lsof -i :<port>` → `kill`) and let the next `/design` invocation auto-restart it; the orchestrator checks `<designRoot>/_server.json` and respawns when stale.

**Testing plugin edits through Maude Desktop's own ACP chat panel** is a separate case from the recipe above: since [DDR-168](.ai/archive/decisions/DDR-168-acp-bundled-cli-and-plugins-always-win.md), the ACP session always injects the app's *bundled* `design`/`flow` plugin copy, unconditionally — a marketplace install pointed at your working tree is ignored (or, if registered under a marketplace alias other than `maude`, silently double-loaded alongside the bundled copy) inside that panel specifically (a plain terminal `claude` session is unaffected either way). To dogfood in-flight plugin edits via the ACP panel, run `pnpm dev:desktop` with `MAUDE_NO_PLUGIN_BOOTSTRAP=1` set — it reverts to the pre-bootstrap detect-and-guide posture so your marketplace-pointed-at-working-tree install loads natively instead.

## Desktop E2E (native app)

DOM-driven end-to-end scenarios for the bundled `Maude.app` (Tauri + WKWebView) live in **`apps/desktop/e2e/`** — WebdriverIO + `@wdio/tauri-service` (embedded WebDriver provider; the official Tauri E2E path). This is the native counterpart to `agent-browser`, which only reaches the web layer at `http://localhost:<port>`, never the native shell (first-run, Tauri menus, sidecar lifecycle, project switch). **DOM-driven only — never computer-use** (memory `feedback_prefer_dom_driven_e2e_not_computer_use`); scenarios find elements by `data-testid` (convention: `<area>-<thing>[-<id>]`, kebab-case; established hooks in `apps/studio/client/app.jsx`: `canvas-list` / `canvas-row-<slug>` / `canvas-frame`).

The Rust crate `tauri-plugin-wdio-webdriver` is registered in `apps/desktop/src-tauri/src/lib.rs` under **`#[cfg(debug_assertions)]`**, so the shipped release `.app` never starts a WebDriver server — only `tauri dev` and the `--debug` test build do. Run via the **`desktop-e2e` skill** / `/desktop-e2e <scenario>`, or: `pnpm test:e2e:desktop:build` (one-time / on source change) then `pnpm test:e2e:desktop`. Adding a new feature's UI that a scenario must reach? Add its `data-testid` in the same change. When studio-client testids change, rebuild the committed bundle release-minified (see the rebuild rule above) before the test build. Full spec: `.ai/plans/archive/feature-desktop-e2e-scenario-harness.md` + the skill.
